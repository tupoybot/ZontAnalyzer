# Мониторинг проверки M1

`#for-human`

`dashboard.json` — панель для Prometheus-источника в Grafana. При импорте выбрать
источник метрик своего стека. Окружения `dev` и `pilot` выбираются отдельно.
Панель показывает результат, возраст данных и длительность проверки.
Папка имеет UID `zont-m1`, панель — `zont-m1-overview`. Эти идентификаторы должны
различаться: при совпадении интерфейс списка Grafana может зациклиться при обходе
дочерних объектов и показать ошибку `too much recursion`.

Для повторяемой настройки использовать `infra/scripts/grafana_setup.py` в Docker
с образом `zont-m1-tools:local`. Смонтировать `infra/` только для чтения и передать
путь к отдельно смонтированному приватному JSON. Обязательные поля конфигурации:
`stack_url` и `service_account_token`; необязательные — `datasource_uid` и
`contact_point` (имя уже существующего канала). По умолчанию выбирается единственный
основной Prometheus-источник. Пример команды внутри контейнера:
`python /infra/scripts/grafana_setup.py /private/grafana-access.json`.

Сценарий создаёт либо обновляет только папку и объекты M1, проверяя их принадлежность
проекту. Общие политики и каналы уведомлений не меняются. Каждый запуск оставляет
правило приостановленным: включение выполняется отдельно после проверки данных
и доставки. Повторный запуск настройки активного мониторинга приостановит правило.

Runtime отправляет два измерения через OTLP: `zont_m1_probe_success` (0 или 1)
и `zont_m1_probe_duration_seconds`. Это результат инфраструктурной проверки,
а не показатель здоровья приложения. Проверка запускается раз в час.

Доступ хранится в ключе Lockbox `grafana_otlp_config`: JSON с полями `endpoint`,
`username` и `token`. `username` — идентификатор OTLP instance. В заголовке
`Authorization: Basic …` пара `username:token` закодирована Base64; это секрет,
а не шифрование. Значения не помещаются в Terraform или исходный код.
Runtime подключает ключ при `grafana_metrics_enabled=true`.

`alert-rule.json` — шаблон запроса API provisioning Grafana. Перед загрузкой
заменить `${datasource_uid}`, проверить `orgId` и создать папку `zont-m1`.
Правило для `dev` изначально приостановлено. Оно выявляет последний отказ либо
отсутствие измерений за два часа; условие должно сохраняться пять минут.
Ошибка запроса к источнику тоже считается отказом.

До включения правила выбрать канал владельца и проверить доставку. Не заменять
общую политику уведомлений стека: использовать отдельную маршрутизацию проекта
или канал в настройках правила. При штатном выключении расписания приостановить
правило, иначе отсутствие данных вызовет ожидаемый алерт.

Готовность требует отдельной проверки: реальный вызов контейнера → измерение
в источнике → отказ/восстановление правила → уведомление владельцу. Импорт панели
и успешная авторизация OTLP сами по себе эту проверку не заменяют.

## Эксплуатационный мониторинг M6

`m6-dashboard.json` и `m6-alert-rules.json` используют отдельную папку `zont-m6`
и панель `zont-m6-overview`. Настройка M1 сохраняет прежний контракт и не управляет
M6. Для M6 запустить внутри контейнера:
`python /infra/scripts/grafana_m6_setup.py /private/grafana-access.json`.
Исходники монтируются только для чтения; конфигурация и токен — отдельно, приватно.
Кроме полей доступа требуется `environment` — короткое имя окружения строчными
латинскими буквами, цифрами и дефисами. `contact_point` задаёт имя существующего
канала уведомлений, а не его адрес или секреты.

Сценарий сначала проверяет принадлежность всех существующих объектов, затем
сохраняет изменения. Конфликт обнаруживается до первой записи. Ошибка API уже
во время сохранения может оставить часть изменений: после устранения причины
нужно повторить запуск. Общие политики, каналы, источники данных и объекты M1
не изменяются. Новые правила приостановлены; у существующих сохраняются активность
и полные настройки доставки, даже если в конфигурации указан другой канал.
Для активного правила без отдельной доставки требуется `contact_point`.

Панель отделяет ошибку синхронизации и устаревшую телеметрию от результата задания.
Счётчики показывают вызовы, ошибки, токены, трафик и ограничения за час. Ошибка
прокси и ошибка внешнего API показаны отдельно. Кэшированные входные токены видны
отдельно; правило расхода суммирует только входные и выходные токены, чтобы не
считать кэш повторно. Длительности и результаты операций показаны отдельно.

Вверху панели показаны сформированная очередь публикации и ручные задания:
ожидающие, выполняющиеся и требующие разбора неизвестного результата AI-запроса.
Отдельно видны изменение размера очередей, возраст их состояния, время после
последнего замера и результат чтения. Счётчики очереди выбирают последний замер
для каждого вида очереди среди экземпляров приложения; они не суммируют копии
одного состояния. После ошибки последнего чтения или через 15 минут без свежего
замера вместо числа показывается отсутствие свежих данных, а не ноль.

Измерения передаются при завершении уже существующего минутного обслуживания
и при часовом мониторинге. После успешной публикации её очередь берётся из
сохранённого результата без нового чтения YDB; для ручных заданий читаются
только незавершённые записи. В остальных случаях выполняются два чтения:
индекса непубликованных отчётов и незавершённых ручных заданий. Каждое чтение
возвращает не более 1001 строки. При превышении предела показываются нижние
границы чисел и отметка «Нижняя граница»; возраст старейшего состояния скрывается.
Предел возвращённых строк не гарантирует такой же предел просмотренных строк:
поиск ручных заданий может просматривать завершённые записи в их диапазоне ключей.
Запросы снимка ограничены двумя секундами без автоматических повторов; получение
сессии ограничено одной секундой. Общая блокировка работ освобождается до чтения
метрик. Если до конца задания остаётся меньше восьми секунд, чтение пропускается
и отмечается как недоступное, сохраняя результат основной работы.

Время для публикации отсчитывается от постановки отчёта в очередь. Для ручных
заданий доступно время последнего сохранённого изменения состояния; исходное
время первого нажатия не хранится. Поэтому возраст состояния не всегда равен
полному времени ожидания. Пустая очередь или неизвестное время не создают
фиктивную дату. Ещё не обработанные изменения журнала публикации и будущие
задания планировщика в размер сформированной очереди не входят.

Начальные пороги правил: отсутствие измерений синхронизации — 48 часов, заданий —
два часа; возраст телеметрии — 30 часов, более 180 вызовов или 100000 токенов за час.
Порог вызовов учитывает ежеминутное обслуживание. Сбор телеметрии связан с дневным
отчётом, поэтому порог её возраста не предполагает частый опрос.
В приватном JSON можно задать `thresholds`: `stale` (секунды), `loops` (вызовы/час),
`tokens` (токены/час), `budget` (доля месячного бюджета; по умолчанию `0.8`).
Месячное правило учитывает потраченные и зарезервированные токены вместе.
Нулевой бюджет запрещает новые платные запросы AI. Отношение расхода к нулю
не вычисляется, поэтому это правило тогда не формирует сигнал.
Для пилота с ежечасным `/internal/monitoring` и выключенным обслуживанием порог
`loops` следует снизить в приватной конфигурации. Проверка `monitoring` следит
именно за этой операцией: другие успешные вызовы не скрывают остановку её таймера.
Отдельное правило `snapshot` выявляет ошибку чтения состояния после успешного
вызова контейнера. Правила `ydb` и `publication` выявляют ошибки хранения и
публикации; `model-overdue` — просроченный более чем на сутки пересмотр модели.
Ошибки прокси, ограничения исходящего доступа и разрешённый обход прокси имеют
нулевой допустимый порог. Это эксплуатационные сигналы, не остановка расходов.
Перед включением сверить пороги с расписанием и допустимым расходом. При штатной
остановке расписания правила отсутствия данных следует приостановить.
Ошибки запросов источника вызывают алерт; отсутствие событийных счётчиков не
подменяется ошибкой. Отсутствие обязательных сигналов здоровья вызывает алерт.

`increase()` требует минимум два измерения одного ряда. При первой отправке
процесс передаёт начальный нулевой отсчёт и текущее значение счётчика; приём обоих
измерений источником необходимо подтвердить живой проверкой. Редкие вызовы,
потеря экспорта и границы окна могут искажать часовые итоги. Счётчики не заменяют
платёжный отчёт. Сигналы результата задания используют измерения за последние
два часа, синхронизации — 48 часов. Отдельная отметка времени наблюдения выбирает
самый новый процесс внутри окружения/операции: восстановление не ждёт истечения
старого отказавшего ряда. Если два наблюдения имеют одинаковое время, отказ
имеет приоритет. Отсутствие самой отметки не считается успешным состоянием.
Возраст телеметрии рассчитывается по самой поздней отметке времени данных,
поэтому он продолжает расти между вызовами контейнера.

Состояние пересмотра моделей, предложения, месячный расход и резерв берутся из
хранилища. `zont_snapshot_success` показывает результат чтения этого состояния.
Непрерывная работа ZONT и котла и качество подтверждающих данных — факты последнего
отчёта, а не текущий счётчик доступности; рядом показано время формирования отчёта.

После проверки данных и согласования доставки включать только выбранные правила:
`python /infra/scripts/grafana_m6_setup.py /private/grafana-access.json --activate monitoring snapshot loops tokens budget egress fallback proxy ydb publication`.
Это отдельный режим: он не переустанавливает шаблоны, сохраняет настройки и
канал каждого правила и меняет только приостановку. Неизвестный объект, конфликт
принадлежности или отсутствие канала прерывают проверку до первой записи.
До появления расписания отчётов в M8 оставить `sync`, `stale` и `model-overdue`
приостановленными; общее правило `job` не заменяет адресную проверку `monitoring`.
Правило `proxy` объединяет готовность прокси по последней проверке мониторинга
и ошибки подключений за час. Готовность восстанавливается по новому наблюдению,
а зарегистрированная ошибка остаётся видимой до выхода из часового окна.

Проверка запросов выполняется `promtool` из `prom/prometheus:v3.2.1`.
Сначала внутри контейнера с Python выполнить
`python /infra/scripts/test_grafana_m6_promql.py /fixtures`, где `/infra` смонтирован
только для чтения, а `/fixtures` — отдельный временный каталог. Затем передать
его только для чтения контейнеру Prometheus и выполнить из `/fixtures`
`promtool test rules /fixtures/tests.json`. Генератор берёт фактические запросы
шаблонов; проверяет восстановление после смены процесса, новый отказ, отсутствие
измерений, начальный нулевой отсчёт счётчика и независимость сигнала мониторинга
от успешного отчёта. Эти проверки не заменяют приём метрик и письмо владельцу.

До активации проверить реальные ряды и доставку отказа/восстановления в существующий
канал. Локальные тесты проверяют границы владения, сохранение активности/доставки
и безопасное повторное применение; они не подтверждают доставку уведомления.
Используется [HTTP API настройки Grafana](https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/http-api-provisioning/),
совместимый с настройкой M1; формат API отличается от формата экспорта правил.
