# ZontAnalyzer: фактический статус

Обновлено: 2026-08-03 (Europe/Samara).

Это краткий checkpoint факта. Актуальный порядок работ находится в
[`roadmap.md`](./roadmap.md), архитектурные принципы — в [`architecture.md`](./architecture.md).

## Резюме

Рабочий read-only CLI-MVP реализован и проверен end-to-end на одной реальной установке BAXI
Connect+: discovery → возобновляемый sync → локальный анализ → сохранённый текст/JSON/HTML →
опциональная OpenAI-интерпретация.

Это ещё не законченный автономный продукт: пользовательский путь только теперь описан в README,
worker не прошёл многонедельный пилот, а аналитика ГВС ограничена циклами горелки.

Критический организационный риск: в `main` пока нет ни одного commit, все файлы рабочей версии
untracked. До параллельного развития функций этот baseline нужно сохранить в Git.

## Проверенный факт

- Локальная БД: 40,013,824 байта, integrity `ok`, revision `dd4272b6d030`.
- 1 устройство, 39 временных рядов, 462,636 канонических samples и 4 отчёта.
- Диапазон данных: `2026-05-04T20:52:00Z` — `2026-08-02T21:30:00Z`.
- 90-дневный backfill на реальном ZONT завершался и корректно возобновлялся после rate limit.
- Неполное окно не продвигает cursor; повторная запись идемпотентна.
- Реальный daily-отчёт разделил нулевую работу отопления и один шестиминутный цикл ГВС.
- Один явно разрешённый OpenAI-вызов прошёл strict Structured Output и evidence validation;
  в ledger записано 1,464 токена. AI по умолчанию выключен.
- Последний полный локальный checkpoint: 34 теста, Ruff и strict mypy прошли; Docker/wheel smoke
  и сохранение SQLite в named volume также проверялись.

## Что реализовано

- Узкий ZONT adapter с allowlist только `devices` и `load_data`, recursive redaction секретов и
  ограничением частоты запросов.
- SQLite/WAL, canonical UPSERT, discovery/config snapshots, отчёты, evidence, lifecycle
  рекомендаций, outbox, usage ledger, integrity check и online backup.
- Автоматический переход к packaged Alembic head с проверенным backup перед изменением revision.
- Качество данных, time-weighted температура относительно исторической уставки, наружная
  температура, циклы горелки и безопасная атрибуция отклонений.
- Контекст отопительных режимов/расписаний и отдельное фактическое автоматическое летнее
  состояние контура.
- Разделение OpenTherm `ch` и `dhw` для базовых burner-метрик.
- Initial/daily/weekly/monthly/seasonal команды, безопасные renderers text/JSON/standalone HTML,
  локальный lifecycle рекомендаций и простой worker.
- OpenAI Responses API через строгую схему, `store=False`, без tools/functions, с проверкой
  evidence ID, budget и graceful degradation.
- Непривилегированный Docker image и CI с lint/types/tests/wheel import/Docker build.

## ГВС: фундамент и пробел

В реальной БД уже есть отдельный контур «ГВС»: температура БКН `dt`, `mode_id`, `target_temp`,
`setpoint_temp`, `status`, `worktime`, температура подачи `bt` и OpenTherm-флаги `ch/dhw/fl`.
Системные режимы задают разные политики отопления и ГВС; автоматическое летнее состояние
отопления не означает отключение ГВС.

Сейчас анализ читает только `dhw + fl` и показывает старты, duty cycle и длительность циклов
ГВС. Он пока не:

- проверяет фактическую температуру БКН относительно исторической уставки;
- строит режим/доступность ГВС и события его переходов;
- измеряет время догрева, недогрев, перелёт, водоразбор или спокойное остывание;
- определяет паузу отопления, использование остаточного тепла и время возврата после ГВС;
- даёт отдельную оценку качества данных ГВС;
- сравнивает качество догрева при активном отоплении и в летнем состоянии.

Подробные ряды ГВС накоплены только с `2026-07-22`; зимнего набора пока нет. Текущие config
snapshots нельзя ретроспективно применять ко всей истории, поэтому анализ обязан использовать
исторические `mode_id/target_temp` и явно маркировать неизвестный старый контекст.

## Главные незавершённые части

В порядке продуктового приоритета:

1. Зафиксированный baseline в Git и проверенный путь README до ежедневного отчёта/worker.
2. Полноценный вертикальный срез ГВС ↔ отопление.
3. Автоматическое восстановление пропущенных отчётов, свежесть/ошибки worker и пилот 2–4 недели.
4. Baseline и настоящие нормализованные weekly/monthly/seasonal сравнения.
5. Внешний backup, production deploy/healthcheck, worker lease и AI eval-набор.
6. Telegram, новые миграции, storage benchmark и полировка CLI — после полезного пилота.

## Ограничения, которые нельзя скрывать

- Анализ сейчас выбирает один основной отопительный контур/комнатный датчик.
- Нет прямого ряда насоса, трёхходового клапана, расхода ГВС и подтверждённой обратки. Можно
  наблюдать задержку переключения, но не всегда доказать её гидравлическую причину.
- Команды длинных периодов уже существуют, но пока не выполняют обещанные сравнения периодов.
- Worker создаёт вчерашний daily-отчёт, но не догоняет все пропущенные сутки и не экспортирует
  стабильный `latest.html`.

## Safety invariants

1. Не добавлять ZONT mutation endpoint, generic request или model tool для оборудования.
2. Не хранить и не печатать raw credentials; discovery всегда проходит recursive redaction.
3. Числа рассчитывает детерминированный код; AI только интерпретирует переданные evidence ID.
4. При плохом качестве данных разрешено советовать только восстановление наблюдаемости.
5. `mark-applied` фиксирует ручное действие владельца и никогда не обращается к ZONT.
6. Сохранять idempotent UPSERT и стабильные report/evidence IDs.
