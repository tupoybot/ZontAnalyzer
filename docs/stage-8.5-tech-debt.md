# Ожидание публикации при сохранении комментария

Этап 8.5 устраняет основной дефект: каждый feedback PUT вызывал `publish_reports`,
который обходил весь архив, обновлял газовый контекст и рендерил все отчёты.
Теперь `publish_report` обновляет один отчёт, сохраняя сериализацию писателей.

Остающееся ограничение: HTTP-обработчик синхронно ждёт `.publication.lock`,
если worker или изменение газовых данных уже запустили полную публикацию.
Холодный кэш графиков выбранного отчёта тоже может потребовать чтения телеметрии.
Цикла повторного сохранения не найдено; это возможное ожидание другой работы,
а не повторная обработка комментария. Частота такого совпадения не измерена.

Если задержки сохранятся, следующий отдельный рефакторинг — очередь публикации
с объединением задач по отчёту и быстрым ответом после durable-записи feedback.
Нужны устойчивость к перезапуску, повторы после ошибки, защита новых версий отчётов,
показ статуса публикации и обработка reload до готовности HTML. Просто запускать
поток на каждый PUT недостаточно: можно потерять работу или вернуть старую страницу.

Критерии будущей проверки: PUT во время полной публикации быстро подтверждает
сохранение; после перезапуска заметка появляется в HTML; устаревшая задача не
перезаписывает более новую; ошибка публикации видна и повторяется безопасно.
