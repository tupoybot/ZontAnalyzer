# Карта документации

Сначала прочитайте короткий [статус](./status.md), затем выберите строку по задаче.
Указанные документы — варианты входа, а не список обязательного чтения.
Начните с одного-двух нужных разделов; переходите дальше только для ответа на
конкретный вопрос. Ссылки внутри документа сами по себе не требуют чтения.

## Как читать экономно

Найдите заголовки выбранного файла командой `rg -n '^#{1,3} ' <файл>`, затем
прочитайте диапазон нужного раздела через `sed -n '<начало>,<конец>p' <файл>`.
Ищите сначала внутри папки темы. Если тема неизвестна, ищите имена файлов или
заголовки в актуальной документации, например:

```sh
rg --files docs -g '*.md' -g '!archive/**' -g '!benchmarks/**'
rg -n '^#{1,3} .*публикац' docs -g '*.md' -g '!archive/**' -g '!benchmarks/**'
```

Не загружайте каталог целиком и не перечитывайте неизменившиеся разделы в ходе
одной задачи. Расширяйте чтение, если неясны зависимость, инвариант или проверка;
начальный бюджет не должен мешать корректному изменению.

## Где хранить сведения

- `status.md` — текущая готовность, развёрнутая версия, ограничения и следующий шаг.
  Подробности проверок — в документе темы или CI по ссылке.
- `cloud/`, `reports/`, `gas/`, `ai/`, `development/` — действующие контракты,
  причины решений, проверки и незавершённая работа по теме.
- Общие требования, архитектура и планы в корне задают цели и связи между темами.
  Реализованные возможности не теряют документацию о своём назначении.
- `archive/` — завершённая история и заменённые решения; это не текущий план.
  `benchmarks/` — данные измерений, которые не нужны для обычной разработки.

Не копируйте один контракт в несколько документов: оставьте его в документе темы,
а из карты, статуса и планов дайте ссылку. Отмечайте, что реализовано, что
запланировано и что ещё требует проверки.
