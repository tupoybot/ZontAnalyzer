# М5 — публикация отчётов и защищённый сайт

`#for-human`

Статус: в М5 добавлен независимый каталог Identity Hub и прямая выдача S3.
Повторная техническая проверка выполняется; полный браузерный вход требует
ручного прохождения CAPTCHA. Приёмка владельцем и слияние ожидаются.
Объём: [М5 в облачном плане](./cloud_first_milestone.md#m5--публикация-в-object-storage-и-сохранение-защищённого-webapi),

Старый production остаётся на `old-stable`; переключение относится к М8.

## Как публикуется отчёт

В YDB хранятся исходный результат анализа (канонический отчёт),
пользовательские данные и очередь обновлений.
Формирование HTML использует тот же шаблон, графики, сведения о стоимости газа
и происхождении AI, что и локальная публикация. Просмотр готового файла и его
переформирование не вызывают AI. Текст в переносимом HTML экранируется.

При заданном `CLOUD_PUBLICATION_BUCKET` приложение загружает HTML и JSON в закрытое
объектное хранилище Object Storage: каждый отчёт хранится отдельным файлом.
Адрес бакета и префикс задаются конфигурацией окружения.
Постоянный каталог публикации не нужен; база не монтируется из Object Storage.
Для локального экспорта сохраняется прежняя файловая публикация.

Порядок обновления:

1. Сохранить исходный результат и изменения пользователя в YDB.
2. Загрузить неизменяемые HTML и канонический JSON выбранных отчётов.
3. Загрузить новый `reports.json`, содержащий только готовые объекты.
4. Загрузить новую версию `latest.html`, если изменился последний дневной отчёт.
5. Одной транзакцией YDB переключить указатели на файлы и подтвердить обработанную
   часть очереди. Транзакция проверяет владельца задания, номер попытки и предыдущую
   отметку обработки.
6. Обновить `site-index.json` в S3 из уже подтверждённых указателей YDB.
   Условная запись проверяет прочитанный ETag — версию объекта. При конфликте
   сначала перечитываются объект и подтверждённые указатели.

Ключ объекта содержит контрольную сумму содержимого. Условная загрузка запрещает
перезапись существующего объекта; повтор с теми же байтами безопасен. Приложение
использует краткоживущий IAM-токен сервисной учётной записи, полученный через сервис
метаданных контейнера. Постоянный S3-ключ не требуется. Этот способ поддерживает
[API Object Storage](https://yandex.cloud/en/docs/storage/api-ref/authentication).

`reports.json` и `latest.html` — стабильные адреса сайта. Шлюз отдаёт
`reports.json` из `reports/site-index.json`, а пустая HTML-страница разрешает
нужный отчёт по этому списку и получает неизменяемый объект через шлюз.
Индекс обновляется после транзакции YDB; при сбое остаётся предыдущая готовая
версия, следующий проход публикации повторяет обновление даже при пустой очереди.

Один проход формирует не более восьми отчётов, начиная с последнего дневного.
Пустая очередь не вызывает полного чтения архива; проверяется ограниченная часть
индекса и существование объектов. При смене бакета или префикса список строится
заново, без ссылок на файлы прежнего назначения. Сезонные отчёты поддерживаются
публикацией; это не добавляет новый вид аналитического задания.

## Как работает сайт

Вход выполняет [Identity Hub с отдельным локальным каталогом](./identity_hub.md).
Публичная стартовая страница выполняет вход в браузере через публичный
OAuth-клиент и одноразовый код с PKCE. Токен хранится только в памяти страницы
и передаётся в заголовке Authorization. API Gateway проверяет JWT и читает
закрытый S3 напрямую. Cloud Function, контейнер приложения и YDB для входа
и чтения HTML/JSON не нужны. Формы обращаются к приложению при открытии
раздела или действии пользователя.

Контейнер повторно проверяет JWT пользовательского API. Basic Auth разрешён
только служебным `/ready`, `/diagnostics`, `/jobs/*`. Запись из браузера требует
явного `Origin`, совпадающего с `CLOUD_PUBLIC_ORIGIN`. Выход удаляет токен из
памяти и убирает отчёт; уже выданный токен остаётся действительным до `exp`.

Анонимное чтение отчётов и просмотр списка объектов бакета запрещены. Прямой вызов
контейнера требует прав IAM. Секреты, состояние Terraform и резервные копии
не входят в публикацию.

Сохраняются корень сайта, `latest.html`, датированные HTML/JSON и `reports.json`,
а также прежний префикс `/za/`. При открытии JSON по логической дате браузер находит
неизменяемый объект в индексе и скачивает его через защищённый S3-шлюз. Навигация по дням, неделям, месяцам и сезонам
использует опубликованный список. Просмотр содержимого каталога не предоставляется.

Общий HTTP-обработчик сохраняет операции профиля, показаний газа, тарифов,
обратной связи и экспериментов, настроек AI и перегенерации отчёта. Запись формы
сначала фиксируется в YDB; публикация догоняет её через очередь. Для записи
проверяется происхождение запроса. Предел времени приёма HTTP действует до
завершения чтения заголовков и ограниченного тела. Чтение YDB и Object Storage после этого
не прерывается таймером ввода. В облаке `CLOUD_PUBLIC_ORIGIN` задаёт точный
HTTPS-адрес сайта; произвольные заголовки пересылки не заменяют эту настройку.

Схема YDB проверяется при первом обращении процесса к базе; успешная проверка
не повторяется для каждого запроса API. После ошибки подготовка повторяется при следующем
обращении. Пользовательские данные продолжают читаться из YDB для каждого запроса.

В каждой зоне облачное приложение ограничено одним экземпляром с 512 МиБ памяти
и одним выполняющимся HTTP-запросом на экземпляр. Лимит восьми принятых запросов
на зону включает ожидание: запросы открытых форм проходят через очередь
в пределах этих ограничений. Готовые HTML и список отчётов эту очередь не используют. Пробный контейнер
сохраняет лимит одного принятого запроса на зону. Такое поведение очереди описано в
[правилах масштабирования Serverless Containers](https://yandex.cloud/en/docs/serverless-containers/concepts/container).

Перегенерация и проверка моделей регистрируются как долговечные задания перед
ответом HTTP 202. Статус хранится в YDB и доступен после перезапуска контейнера.
Отдельный таймер вызывает закрытый `/internal/maintenance`: этот путь отсутствует
в API Gateway и доступен через IAM только вызывающей сервисной учётной записи.
Обработчик забирает ограниченную часть очереди. Без явно поставленного задания
просмотры и проходы публикации не обращаются к OpenAI. Проверка моделей и принятие
предложения читают официальную документацию только через разрешённый прокси;
прямой сетевой обход запрещён.

Параметр Terraform `enable_maintenance_timer` включает доставку заданий форм
каждую минуту; по умолчанию он выключен. Перед включением нужны короткая проверка
контейнера и настроенная отправка метрик. Этот таймер не включает штатную генерацию
новых отчётов старого production. Для ручной проверки доступны защищённые
`POST /jobs/publication` и `POST /jobs/maintenance`.

## Проверка и восстановление

Перевод входа на публичную браузерную страницу реализован. Локально прошли
852 теста приложения, Ruff/mypy и сборка, 17 проверок Terraform, 28 проверок
инфраструктурных скриптов и 23 браузерных сценария входа. Дополнительно проверены
четыре архива и формы на одноразовой YDB. Тесты используют ответы OIDC с настоящей
RSA-подписью, но не подтверждают вход в живой сервис.
Публичный OAuth-клиент создан; прежний каталог и тестовый пользователь сохранены.
Развёрнут commit `524c9aa`: [CI](https://github.com/tupoybot/ZontAnalyzer/actions/runs/36329537077)
и [выпуск](https://github.com/tupoybot/ZontAnalyzer/actions/runs/36329534727) прошли.
Неизменяемый образ:
`ghcr.io/tupoybot/zontanalyzer@sha256:9a3a298ad8f076121298ab58da3ed1be0fd48ea35b558cf975b6fee2f47063a9`.
Его происхождение сверено с выпуском; этот же образ прошёл локальную проверку
запуска и развёрнут обычной сервисной учётной записью.

Облачная проверка подтвердила готовность нужной ревизии, повторные аналитические
запросы без внешних API, публичную стартовую страницу и сформированный в браузере
запрос PKCE. Проверен отказ при неверном callback. Отчёты, индекс и API отвечают
401 без токена, со старой cookie, Basic и поддельным Bearer; прямые адреса
контейнера и S3 отвечают 403. Настоящий положительный вход через провайдера
в новой схеме остаётся ручной проверкой.

Старая функция входа, её служебная учётная запись, два секрета, прежнее приложение
и конфиденциальный клиент удалены. Каталог и пользователь сохранены.

Владелец проверяет настоящий вход, четыре архива,
сохранение формы и выход. Автоматический браузер не обходит CAPTCHA провайдера.
Также нужно перенести подготовленные настройки в оба секрета GitHub Environment:
`M1_CONFIG_JSON` и `M1_SCOPE_JSON`. Идентификаторы, логин и пароль остаются
в приватных файлах.

Четыре синтетических демонстрационных отчёта сохраняются до ручной проверки;
они показывают интерфейс, а не реальную работу отопления. Предыдущие проверки
М5 подтвердили безопасные повторы публикации, восстановление пропавшего объекта,
атомарную смену указателей, защиту от запоздавшего процесса, долговечную очередь
и сравнение облачного экспорта с локальным. Новая доработка не меняет расчёты
отчётов. Для этой проверки внешние запросы к ZONT и OpenAI не выполнялись.

Для слияния [PR #49](https://github.com/tupoybot/ZontAnalyzer/pull/49) нужна явная
приёмка владельцем. До неё М6 не начинается; старый production не менялся.

При отказе Object Storage пользовательская запись остаётся в YDB, а старые
указатели публикации не меняются. Повтор прохода продолжает очередь. Если потеряны
объекты, их можно восстановить из канонических отчётов. При восстановлении YDB
и Object Storage нужно проверить, что все объекты активного списка существуют,
до открытия сайта пользователям. Старые объекты нельзя удалять только по возрасту:
они могут оставаться частью действующего архива.
