# ZontAnalyzer — целевая cloud-first / AI-first архитектура

Статус: целевая архитектура новой облачной версии; реализация М2–М8 впереди.<br>
Обновлено: 2026-09-17.

Контракты: [M0](./cloud_first_m0.md). Фактическая готовность: [текущий статус](../status.md).
Телеметрия получается при инициации отчёта,
без отдельного пятиминутного сборщика; proxy — выбранный маршрут приложения,
без требования сетевой изоляции произвольного кода контейнера.

Этот документ фиксирует архитектурное направление, сформулированное после работ по ГВС и надёжности. Старый VPS с SQLite замораживается на принятом неизменяемом релизе (образе с фиксированной контрольной суммой): до cutover в него попадают только критические исправления. Активная разработка ведётся для одного нового cloud-only приложения; отдельного второго потока функциональной разработки для VPS нет. Старый VPS сохраняется до доказанного cutover и служит источником резервной копии и планом возврата.

## 1. Принцип продукта

ZontAnalyzer остаётся read-only помощником для одного реального дома. Главная ценность продукта не в инфраструктуре самой по себе, а в способности со временем понимать поведение конкретной системы отопления и помогать владельцу выбирать безопасные ручные эксперименты.

Поэтому проект разделяется на два слоя.

### Доверенный слой данных — детерминированный код

Отвечает за то, что должно быть воспроизводимым и проверяемым:

- read-only discovery/config/history/events из ZONT;
- каноническое хранение телеметрии;
- идентификацию датчиков, семантические роли, provenance и confidence;
- выравнивание временных шкал и проверки качества данных;
- сегментацию состояний отопления, ГВС и надёжности;
- исключаемые окна для устаревших данных, отключений, летнего/off-состояния, приоритета ГВС и переходов управления;
- простые проверяемые расчёты: средние, диапазоны, ошибка относительно уставки, duty cycle, ΔT, длительности, coverage и т.п.;
- компактные временные evidence-окна для reasoning;
- evidence ID и safety guards.

Этот слой не должен превращаться в большую локальную экспертную систему отопления из фиксированных порогов и `if/else` для каждого возможного диагноза.

### Слой reasoning — OpenAI

Отвечает за задачи, где многомерный анализ полезнее ручных эвристик:

- поиск и объяснение закономерностей между погодой, состоянием управления, реакцией помещений, подачей/обраткой и ГВС;
- сравнение конкурирующих инженерных гипотез;
- ранжирование вероятных причин с сохранением неопределённости;
- counterfactual/predictive анализ небольших ручных изменений;
- выбор следующего наиболее информативного эксперимента;
- использование структурированной истории предыдущих интервенций владельца;
- построение специфичной для этого дома картины поведения на горизонте недель и сезонов.

Вывод AI обязан различать четыре эпистемических уровня:

1. **observed** — непосредственно прочитано или измерено;
2. **derived** — детерминированная математика по observed-данным;
3. **inferred** — вывод или гипотеза модели;
4. **predicted** — прогноз или counterfactual-оценка.

Inference и prediction не становятся измеренным фактом только потому, что сохранены в отчёте.

## 2. Почему cloud-first

Для этого pet project нагрузка импульсная, а не постоянная: периодическая синхронизация, периодический анализ, редкие обращения к OpenAI и публикация отчётов. Поэтому постоянно работающий VPS/container — не единственная естественная модель развёртывания.

Целевая облачная архитектура должна сохранить сильные стороны текущего application layer (`run --once`, идемпотентный sync/catch-up, read-only API, сохраняемые cursors/reports) и перенести их на managed/serverless сервисы, не переписывая приложение в набор микросервисов.

Cloud-first здесь означает:

- managed/serverless сервисы — предпочтительная production-цель;
- локальная разработка и интеграционные тесты нового приложения работают в Docker + YDB;
- инфраструктура описывается как код;
- приложение сохраняет переносимость: domain/analytics не знают о Yandex Cloud;
- облачная миграция выполняется постепенно и остаётся обратимой до cutover.

Это **не** означает разделение каждой операции на отдельную функцию или сервис.

## 3. Начальная целевая схема в Yandex Cloud

Предпочтительный базовый вариант:

```text
Timer Trigger
    |
    v
Serverless Container
report job: sync required window -> analyze -> publish
    |
    +--> разрешённый direct --> ZONT read-only API
    +--> YDB Serverless
    +--> локальный Xray-клиент --> управляемый egress --> OpenAI API
    +--> Object Storage (публикуемые HTML/JSON-артефакты)
    +--> Lockbox (runtime-секреты)
    +--> Monium (метрики/логи/алерты)
```

Опциональные сервисы подключаются только при появлении реальной задачи:

- API Gateway — кандидат для обязательного переноса существующих защищённых web/API операций; конкретный сервис необязателен, сохранение операций обязательно;
- Postbox — email-сводки и уведомления;
- Workflows/EventRouter — orchestration, если единый `run --once` перестанет быть достаточным;
- Message Queue — асинхронная развязка только если retries/concurrency действительно этого потребуют;
- Yandex Query + Object Storage — в будущем для аналитического архива/data lake;
- Cloud Functions — для действительно маленьких изолированных handlers, но не как runtime по умолчанию для уже существующего packaged application.

Первая облачная версия должна оставаться одним развёртываемым приложением, а не становиться распределённой микросервисной системой.

Размещение runtime/AI, доступность внешних сервисов и управляемый egress проверяются
до переноса состояния. [M0–M1 и реестр зависимостей](./cloud_first_milestone.md)
задают обязательные ранние проверки; Yandex Cloud остаётся кандидатом до их прохождения.

## 4. Модель вычислений

Предпочтительная единица выполнения — вызов Serverless Container с идемпотентным one-shot use case.

```text
timer -> invocation adapter -> one-shot use case -> invocation result
```

Существующий долгоживущий `run` worker остаётся замороженным старым runtime на VPS, но cloud production не должен зависеть от постоянно живущего процесса.

Основной cloud use case — **задание генерации отчёта**. Расписание (daily после
01:00 по времени дома, остальные периоды по календарным границам) или явный запрос
владельца сначала инициирует получение необходимых данных из ZONT API, затем
проверку полноты, анализ и публикацию. Загрузка охватывает период отчёта и
необходимый контекст сравнения; курсоры и сохранённая история исключают полный
повторный backfill. Daily job получает данные непосредственно перед построением
дневного отчёта. Weekly/monthly/quarterly/seasonal job переиспользует сохранённую историю
и запрашивает только недостающие диапазоны; полный период повторно не тянется.
Политика перечитывания поздних данных проверяется в M2/M3.
Отдельного периодического sync без потребности в отчёте нет.

Простой просмотр готового отчёта не вызывает ZONT или OpenAI. Изменение газа,
профиля, тарифа и feedback создаёт только нужную invalidation/publication job.
Retry выполняется для незавершённого задания с сохранённым checkpoint; старый
опубликованный отчёт остаётся доступен при отказе ZONT. Периодический recovery
проверяет только зависшие/недоставленные задания, не собирает телеметрию вхолостую.
История текущих настроек котла требует отдельной проверки: архив телеметрии
не доказывает восстановимость всех промежуточных config snapshots.

ZONT сохраняет данные только за последние 90 дней. Собственная каноническая
telemetry history хранится дольше этого срока, поэтому квартальные периоды могут
выходить за retention источника. Для каждого окна ingestion различает successful
empty range, фактический gap/error и unrecoverable gap старше доступной границы.
Невосстановимый диапазон явно отражается в coverage/evidence и не заменяется
нулевыми или синтетическими samples. Catch-up идёт от самого старого
восстановимого окна; поздние данные вызывают только bounded refresh overlap,
а не полный refetch.
Покрытие учитывается по устройству/серии/окну с проверкой pagination и truncation;
одного HTTP 200 или наличия samples недостаточно. Первый запуск забирает доступную
историю для будущих длинных отчётов возобновляемыми порциями, чтобы она не исчезла
к концу квартала. Квартальные 91–92 дня и старый контекст опираются на собственный
архив; риск истечения срока незагруженных окон виден в диагностике.

Из этого следуют важные требования:

- всё долговечное состояние хранится вне контейнера;
- локальная файловая система используется только как scratch space;
- параллельные/перекрывающиеся вызовы возможны и должны быть безопасны;
- claim/idempotency задач должны сохраняться транзакционно;
- retries не должны дублировать отчёты, interventions или OpenAI-вызовы.

`run --once` — legacy aggregate сценарий, которому ещё нужен адаптер облачного вызова
и проверка жизненного цикла; схема не утверждает, что запуск CLI уже совместим
с invocation-протоколом платформы. Catch-up ограничивается бюджетом выполнения
и продолжается по устойчивым курсорам. Фоновый пересмотр моделей также должен
завершаться в контролируемом задании с сохранённым состоянием, а не теряться при
выходе процесса. Неизвестный результат внешнего AI-вызова после таймаута нельзя
исправлять слепым повтором: журнал и политика восстановления должны различать
завершённый, ошибочный и неопределённый исход; lease сам по себе не гарантирует
строго однократный внешний вызов.

Адаптер обслуживает каждый вызов, включая повторный вызов прогретого экземпляра.
Для HTTP server mode обработчик слушает `PORT`; возврат результата use case
не требует завершения серверного процесса. Конкретный режим, его ограничения
и бюджет cold start фиксируются в M0 и проверяются минимальным контейнером в M1.

Не добавлять функцию, которая лишь вызывает контейнер. Scheduler должен обращаться к execution target напрямую.

## 5. Модель долговечного хранения

### YDB Serverless

Единственная БД нового приложения для локальной разработки и cloud production:

- devices/entities/config snapshots;
- telemetry series и samples;
- долговечное состояние coverage/gaps и ingestion cursors (без TTL источника);
- source/reliability events;
- sync cursors и job/idempotency state;
- reports и evidence metadata;
- recommendations/interventions/owner feedback;
- профиль владельца/оборудования, показания газа и калибровка;
- месячные тарифы/валюты и аудит исправлений;
- версии настроек AI, состояние пересмотра/предложения/решения владельца;
- OpenAI usage ledger, provenance успешных ответов и пригодные кэши.

Перенос сохраняет идентичности, связи, временную гранулярность и аудит без
автоматического сокращения истории. Точный состав задают текущие модели и миграции,
а не этот перечень. Текущие настройки не распространяются на прошлые периоды.

YDB нельзя считать «SQLite с другим URL». Нужен отдельный storage adapter/repository implementation. SQL-, transaction- и index-предположения должны быть проверены явно.

SQLite не является backend нового приложения. Старый VPS продолжает работать на
принятом релизе до cutover, а его SQLite переносится в YDB однократно из online backup.
Для сравнения используются изолированные копии и read-only проверки; обратная запись
в SQLite не является способом синхронизации.

Application/domain/analytics должны зависеть от устойчивых доменных контрактов, а не от
деталей YDB. Общие аналитические расчёты, тестовые сценарии и формат отчёта сохраняются.

Общий доменный контракт задаёт операции и типы для единственной реализации на YDB.
SQLite-адаптер, выбор backend в конфигурации и двойная запись не нужны. Разработка
универсальной ORM или общего backend-фреймворка не нужна. M0 определяет контракты,
M3 реализует рабочее хранение на YDB и проверяет его операции, M4 встраивает его в
новое приложение, выполняет импорт и удаляет старую SQLite-зависимость; contract tests
сохраняются.

Общая логика аналитики и тестовые контракты переносятся в новое приложение.
Готовность cloud не задерживает критические исправления legacy VPS, но такие исправления
не создают второй активной линии разработки и отдельно учитываются при cutover.
Использование YDB-specific возможностей разрешено при сохранении прикладных гарантий.

Локальная разработка YDB доступна через официальный Docker-образ
`ydbplatform/local-ydb`; локальная и managed YDB используют один adapter с разными
настройками подключения. Одна production writer-система действует и до, и после
cutover: сначала legacy VPS, затем cloud. После переключения все новые записи
сохраняются в YDB и учитываются при возможном возврате.
Порядок локальных проверок до облачного развёртывания и ограничения описаны
в [M0](./cloud_first_milestone.md#хранение-и-локальная-разработка).

### Object Storage

Используется для immutable/published артефактов, а не транзакционного состояния:

- `latest.html` только для последнего дневного отчёта;
- датированные HTML/JSON exports;
- архив дневных, недельных, месячных и сезонных отчётов и manifest `reports.json`;
- опциональные долгосрочные exports/Parquet в будущем;
- sanitized fixtures или migration exports, где это уместно.

Живую SQLite-базу нельзя запускать с Object Storage mount.

## 6. Конкурентность и расписание

Serverless execution делает инвариант «ровно один вечно работающий worker» неправильным. Вместо него используется атомарное владение задачей/idempotency.

Концептуально:

```text
job key = <тип задачи, период/ревизия входных данных, версия алгоритма>

атомарный claim
  -> уже завершено: no-op
  -> lease занят: no-op / retry позже
  -> claim получен: выполнить
```

Crash/timeout должен оставлять достаточно сохранённого состояния, чтобы следующий вызов мог безопасно продолжить работу.

Существующее поведение cursor/catch-up/idempotent-report нужно переиспользовать, а не заменять.

## 7. Секреты и IAM

Cloud runtime должен использовать service account/IAM permissions с минимально необходимыми правами для каждого ресурса.

Секреты — ZONT token/client identity, OpenAI API key и т.п. — в cloud execution должны переехать в managed secret store. Они никогда не должны попадать в image layers, Terraform state в открытом виде, report artifacts или logs.

Для developer mode сохраняется существующий путь через локальные secret-files/env.

### Исходящий трафик

Обязателен единый контракт маршрутизации по назначениям: proxy, явно разрешённый
direct или deny. OpenAI API/metadata и каталог моделей используют локальный
HTTP CONNECT интерфейс Xray-клиента рядом с приложением и аутентифицированный
внешний транспорт VLESS/XHTTP/REALITY. ZONT идёт напрямую по явному разрешению.
Обязательны allowlist, таймауты и лимиты соединений/байтов, проверка TLS целевого API.
Cloud APIs и служебная identity имеют отдельные разрешённые маршруты.
Локальный proxy не публикуется наружу. Совместный lifecycle, готовность и ресурсы
Xray требуют проверки в M1; это выбранный контракт, не реализованный cloud runtime.

При отказе обязательного proxy прямого fallback нет. Проверяется
маршрутизация всех прикладных клиентов, SDK и redirects;
изоляция произвольного кода контейнера на уровне сети не требуется.
Секреты proxy не попадают в логи; учитываются назначения, отказы и объём трафика.
Лимиты API-запросов/токенов обеспечивает приложение: CONNECT не видит HTTPS payload.
Детали и критерии — в [контракте M0](./cloud_first_milestone.md#контракт-проксирования-и-контроля-трафика).

Используется существующий управляемый egress. Его стоимость, доступность и
восстановление учитываются как внешняя зависимость; адреса и топология задаются
приватной конфигурацией. Постоянный VPS для самого приложения не требуется.
Региональную совместимость OpenAI проверяют отдельно до миграции.

## 8. Наблюдаемость

Cloud observability является частью архитектуры, а не последующей надстройкой.

Минимальный набор application metrics:

- время последнего успешного sync / sync lag;
- возраст последней telemetry;
- завершённые/ошибочные окна;
- длительность analysis;
- статус генерации отчёта;
- OpenAI calls/tokens/failures;
- уже вычисляемые приложением reliability-метрики ZONT/controller/boiler;
- ошибки/timeouts вызовов контейнера.

Здоровье инфраструктуры и факты уровня приложения должны оставаться разными понятиями. Успешный вызов контейнера не доказывает свежесть telemetry ZONT.

## 9. Публикация отчётов и feedback

Первая serverless-миграция должна сохранить текущую report-модель.

Рекомендуемое разделение:

- канонический report JSON/state — в YDB;
- отрендеренный standalone HTML/JSON export — в Object Storage;
- стабильный pointer/object для последнего отчёта.

До cutover обязателен защищённый web/API path для уже работающих комментариев,
исходов рекомендаций (включая различие `ignored/applied/rejected`), ручных
экспериментов, профиля, показаний газа, тарифов и настроек AI. API Gateway +
handler/container — возможная реализация; все записи меняют только данные
ZontAnalyzer. Сохраняются валидация, аудит и защита от конфликтующих изменений.

Общий периметр доступа защищает HTML, JSON, manifest и API; прямой доступ к bucket
не должен обходить авторизацию. Сначала сохраняются пользовательские данные,
затем обновляется представление. Просмотр и повторная публикация не запускают AI
и не меняют сохранённый ответ. HTML переносим, без обязательного CDN, пользовательский
и AI-текст экранируется. Файлы отчётов публикуются до manifest, latest — после
архива; читатель не получает ссылку на незавершённый артефакт. Межобъектная
атомарность не предполагается: порядок, версии и защита от устаревшего publisher
проверяются при сбоях и конкурентных вызовах.

## 10. AI packet в облачной архитектуре

Cloud migration не должна откатить AI-first направление продукта.

Пакет для OpenAI должен строиться из того же детерминированного evidence layer независимо от storage/runtime backend. Он должен содержать ограниченную по размеру временную структуру, а не слепо выгружать сырую минутную telemetry.

Желаемые входные данные для reasoning:

- активный управляющий комнатный датчик и target;
- дополнительные температуры помещений и влажность;
- наружная температура;
- расчётная и фактическая температура подачи;
- обратка и ΔT;
- heating activity/modulation/context;
- окна взаимодействия с ГВС;
- reliability/staleness context;
- предыдущие ручные interventions и их результаты;
- representative evidence windows, сохраняющие временную форму поведения.

Cloud backend — инфраструктурная деталь и не должен менять эпистемический контракт аналитика.

Сохраняются представительные окна ГВС до заполнения бюджета агрегатами, различие
запроса контура, пламени и фактической работы, а также неизвестность расхода.
Нулевая модуляция при активной горелке не равна выключению; номинальные кВт не
становятся измеренным м³/ч. Стоимость наследует качество исходного объёма,
месячные тарифы в зоне объекта и раздельные валюты; неизвестный тариф не равен нулю.

Дневной и обзорный профили AI получают согласованный снимок версионируемых
настроек. Смена параметров действует на новые анализы без пересчёта истории.
Сохраняются фактическая модель/параметры успешного ответа, prompt/schema, время,
версия настроек, связь с журналом и исходный отпечаток фактов. Историческая модель
без доказательств остаётся неизвестной. Ревизии ограничены данными периода;
служебная миграция или рендер не означают изменение фактов и устаревание AI.
Пересмотр каталога раз в 60 дней и ручная проверка сохраняют ограниченные повторы
и решения владельца; автоматической смены модели нет. Качество кандидата требует
сохранённой локальной оценки по действующему контракту 9.2.

## 11. Границы трека, GitHub Issues и приёмка через PR

До первого облачного изменения приложения в `main` точный commit работающего
старого production закрепляется в ветке `old-stable` и неизменяемом
теге. После приёмки М1 облачный каркас отдельным PR включается в `main`. Дальнейшие
этапы разрабатываются короткими ветками от `main`; постоянная параллельная облачная
ветка не поддерживается. В работу входят запуск, хранение YDB, публикация,
наблюдение, ограничения расходов и переключение production. Новые продуктовые
возможности требуют отдельного решения и не добавляются в миграцию автоматически.
Документационные изменения идут в `docs/<topic>`. Необходимые исправления старого
production разрабатываются короткими ветками от `old-stable` и возвращаются туда
отдельными PR. Применимое исправление отдельно переносится или адаптируется в `main`.

Legacy VPS/SQLite deployment не удаляется и не ломается во время cloud-разработки.
После переключения старое расписание выключено. До открытия пользовательских записей
можно вернуться на старую систему; после него восстановление выполняется в облаке.
После завершения наблюдения приложение и его
ресурсы на старом VPS останавливаются и удаляются; резервные копии и релизы
сохраняются отдельно, не затрагивая другие сервисы и внешний egress.

Общий прогресс отслеживается в [GitHub Issue #1](https://github.com/tupoybot/ZontAnalyzer/issues/1).
Начиная с М2, перед началом этапа создаётся его GitHub sub-issue этой вехи.
Итоговый комментарий кратко описывает результат, проверки и оставшиеся ограничения.
Промежуточные сообщения нужны только при существенном изменении ожиданий или
препятствии, требующем решения автора; [правила](./cloud_first_milestone.md#интеграция-и-приёмка-через-github-issuespr).
При изменении плана одновременно обновляются общий issue и затронутые sub-issues;
непринятые изменения отмечаются ссылкой на PR. Подробные критерии остаются в
документах. [Порядок ведения issues](./cloud_first_milestone.md#интеграция-и-приёмка-через-github-issuespr).

Каждая веха оформляется отдельным GitHub Pull Request со scope, проверками,
evidence, состоянием legacy deployment и rollback/cutover impact. По действующей
[процедуре](../development/release-process.md) до запроса приёмки выполняются реализация,
проверки, commit/push и применимое развёртывание проверенного immutable image
с bounded smoke. Только merge ожидает явной приёмки владельца; явное принятие
в чате допустимо, нажатие кнопки GitHub не является единственным способом.
Зелёный CI, deployment, smoke и молчание не означают приёмку. Для документации
достаточно проверок документов/ссылок/diff и commit/push, без сборки и деплоя.
Перед merge выполняется локальный `docker system prune -af`, никогда на production host.

После merge PR этап считается принятым, Issue обновляется ссылкой на PR и evidence, а следующий этап начинается от принятого состояния. Для небольшого функционального исправления, не относящегося к cloud-инфраструктуре, используется отдельный review/PR в `main`; такое исправление не считается приёмкой cloud-вехи.

### CI/CD и граница legacy/cloud

Legacy VPS остаётся на принятом образе с фиксированной контрольной суммой и
исходниками в `old-stable`. Новое cloud-only приложение
собирается и тестируется как отдельный артефакт; его runtime и зависимости не обязаны
совпадать с legacy image. Коммиты IaC, cloud runtime и environment wiring проверяются
вместе с cloud-приложением в одной активной линии разработки.

VPS и cloud не используют общий runtime и не работают как два активных production
потока. Legacy получает только критические исправления через `old-stable` до cutover;
cloud-приложение развивается в `main` и сразу ориентировано на YDB. `main` не
сливается в `old-stable`, а образ из `main` не развёртывается на старом VPS.

До M8 cloud проверяется на изолированных копиях состояния, publication namespace и
sinks. Разрешены read-only сравнения с legacy и mock/no-op side effects; повторная
production-аналитика и пользовательские записи не выполняются. Legacy VPS сохраняет
единственного production writer и scheduler до согласованного cutover. При cutover
старое расписание останавливается, импортируется финальная online backup-копия,
затем cloud становится единственным writer. До включения записи возврат возможен
на замороженный старый production. После появления новых записей основной путь
восстановления — совместимый cloud-релиз с сохранением данных YDB; возврат на старый
VPS допускается только после отдельной проверки импорта этих записей.

После принятия M8 приложение и ресурсы старого VPS останавливаются и удаляются после
наблюдения. Резервные копии и релизы сохраняются как аварийные материалы, не затрагивая
другие сервисы и внешний egress. Отдельной вехи отложенного удаления SQLite из нового
runtime нет: переход выполнен в М3–М4. Облачное приложение и его CI используют YDB.

## 12. Философия миграции

Предпочтительный порядок:

1. проверить облачный запуск и соединения с внешними API;
2. реализовать хранение YDB и проверить его на характерной нагрузке;
3. импортировать online backup SQLite в изолированную YDB и сравнить данные и отчёты;
4. проверить приложение на копиях без записи в production и повторной отправки уведомлений;
5. в М8 остановить старое расписание и записи, перенести последние изменения,
   проверить облако и разрешить запись только в одной системе;
6. после открытия записей восстанавливать работу в облаке с сохранением новых данных;
   возврат на старую систему требует отдельной проверки их переноса.

Цель — изучить платформу и упростить эксплуатацию, а не устроить big-bang rewrite.
