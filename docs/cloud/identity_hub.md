# Вход через Identity Hub

`#for-human`

В рамках [М5](./cloud_first_m5.md) сайт использует отдельный каталог локальных
пользователей Yandex Identity Hub. Пользователю не нужен Яндекс-аккаунт.
Тестовый пользователь явно назначается приложению отчётов; учётные записи
организации и группы автоматически доступа не получают. Пароли проверяет
Identity Hub.

## Вход и чтение отчёта

1. Публичная стартовая страница предлагает войти через Identity Hub. Самих
   отчётов и списка архива на ней нет.
2. Браузер создаёт запрос OpenID Connect (OIDC — протокол входа через внешний
   сервис). PKCE связывает одноразовый код с начавшим вход браузером; случайные
   `state` и `nonce` защищают возврат и полученный токен. Данные незавершённого
   входа хранятся в `sessionStorage` не дольше десяти минут и используются один раз.
3. После входа браузер сам обменивает код на токен. Публичный OAuth-клиент типа
   `user-agent` не имеет секрета. Страница проверяет подпись RS256, издателя,
   приложение, срок действия и `nonce`; код сразу убирается из адресной строки.
4. Токен хранится только в памяти страницы. Запросы списка, HTML/JSON и форм
   передают его в `Authorization: Bearer`. API Gateway проверяет подпись,
   издателя, приложение и срок действия и читает закрытый Object Storage напрямую.
   Cloud Function, контейнер приложения и YDB для входа и чтения не вызываются.
5. Формы обращаются к контейнеру при открытии раздела или действии пользователя.
   Контейнер повторно проверяет JWT — подписанное подтверждение входа. Изменения
   требуют точного `Origin` сайта; запрос без него отвергается.

Вход сохраняет выбранный адрес отчёта, включая прежний префикс `/za/`.
Переход на другую страницу или перезагрузка требуют нового обмена OIDC;
действующая сессия Identity Hub обычно позволяет обойтись без повторного пароля.
В хранилище вкладки остаются только временные параметры входа и признак
продолжения сессии, но не токен. Выгрузка JSON получает неизменяемый объект
через тот же защищённый шлюз.

Выход удаляет токен из памяти и убирает отчёт со страницы. Общая сессия Identity Hub
и ранее выданный JWT этим не отзываются: JWT действителен до `exp`.
JavaScript имеет доступ к токену, поэтому внедрение постороннего скрипта в сайт
может скомпрометировать сессию. Отчёты считаются доверенным кодом приложения;
пользовательские значения должны экранироваться при генерации HTML.
Постоянное хранение токена в `localStorage`, `sessionStorage` и cookie запрещено.

Basic Auth остаётся только у служебных `/ready`, `/diagnostics` и `/jobs/*`.
Пользовательский API не принимает старую cookie OIDC или Basic вместо токена.

## Развёртывание

[Отдельный модуль](../../infra/identity/main.tf) создаёт пул, локального пользователя,
публичный OAuth-клиент, OIDC-приложение и явное назначение пользователя.
Он выполняется администратором организации отдельно от обычного развёртывания.
Сервисной учётной записи приложения не выдаются права управления каталогом.
Функция входа, её сервисная учётная запись и секреты Lockbox не требуются.

В закрытой рабочей копии задаются `folder_id`, `organization_id`, `pool_subdomain`,
`public_origin` и начальный `test_password`. Состояние Terraform содержит этот
пароль и остаётся приватным вместе с входными значениями и планами.
После первой смены Terraform не сбрасывает пароль пользователя.

Основное окружение получает `identity = {mode = "spa", client_id = ..., issuer = ...}`.
Эти же значения задаются в `allowed_environment_identity` файла области
развёртывания. Публичная страница получает только идентификатор клиента и
официального издателя; секретов в ней нет. В GitHub Environment обе приватные
настройки обновляются вместе: `M1_CONFIG_JSON` и `M1_SCOPE_JSON`.

При переходе с прежнего клиента создаётся новый: тип OAuth-клиента у провайдера
неизменяемый. Каталог и пользователь сохраняются. После переключения шлюза
удаляются прежнее приложение, клиент и ресурсы функции. Для удаления уже
развёрнутой функции проверка плана требует её точный идентификатор в
`allowed_auth_function_retirement` для нужного окружения и включённый режим
`spa`. После удаления разрешение убирается. Устаревшая конфигурация окружения
не может молча отключить защиту сайта.

## Проверка

Браузерные проверки используют тестового OIDC-провайдера с настоящей RSA-подписью.
Проверяются PKCE, состояние входа, подпись и поля JWT, отсутствие токена в
постоянных хранилищах, заголовки защищённых запросов, навигация, ошибки и выход.
Проверки приложения подтверждают независимую проверку JWT и ограничения `Origin`.

Настоящий вход локального пользователя, чтение архивов, сохранение формы и выход
нужно также проверить в развёрнутом сайте. CAPTCHA Identity Hub выполняет человек;
автоматические тесты не подменяют эту проверку. Текущая готовность — в [М5](./cloud_first_m5.md).

Официальные контракты: [OIDC-приложения и типы клиентов](https://yandex.cloud/ru/docs/organization/operations/applications/oidc-create),
[проверка JWT шлюзом](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/jwt-authorizer),
[прямая выдача S3](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/object-storage).
