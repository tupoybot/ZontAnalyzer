# Вход через Identity Hub

`#for-human`

В рамках [М5](./cloud_first_m5.md) сайт использует отдельный каталог локальных
пользователей Yandex Identity Hub. Пользователю не нужен Яндекс-аккаунт.
Созданный Terraform тестовый пользователь назначается только приложению отчётов;
учётные записи организации и группы автоматически доступа не получают.
Пароли проверяет Identity Hub, а не приложение анализа.

## Вход и чтение отчёта

1. Пустая страница сайта запрашивает защищённый список отчётов. Если входа нет,
   браузер переходит в Identity Hub.
2. Небольшая Cloud Function создаёт запрос OpenID Connect (OIDC — протокол входа
   через внешний сервис). PKCE связывает одноразовый код с начатым запросом.
   Случайные `state` и `nonce` защищают возврат в браузер и полученный токен.
   Данные незавершённого входа зашифрованы отдельным ключом и живут десять минут.
3. После проверки пароля функция обменивает код на токен, проверяет подпись,
   издателя, приложение, срок действия и `nonce`. Токен записывается в
   `__Host-zont_oidc`: `Secure`, `HttpOnly`, `SameSite=Lax`, без `Domain`.
   JavaScript страницы не читает пароль или токен.
4. API Gateway самостоятельно проверяет JWT — подписанное подтверждение входа —
   и получает список и неизменяемые файлы напрямую из закрытого Object Storage.
   Контейнер приложения и YDB при чтении отчёта не вызываются. Формы загружают
   актуальные значения после открытия соответствующего раздела.
5. Действия в формах идут в контейнер: он повторно проверяет токен. Изменения
   требуют точного `Origin` сайта; запрос без него отвергается.

Функция входа не содержит аналитики и не подключается к YDB. Её запуск всё ещё
может иметь небольшую задержку после простоя; это отдельная функция на Node.js,
а не контейнер приложения. Проверка каждого HTML/JSON не вызывает эту функцию.
Basic Auth остаётся только у служебных `/ready`, `/diagnostics` и `/jobs/*`.
Для пользовательского API и отчётов он не является запасным способом входа.

Выход удаляет cookie сайта. Новая попытка входа требует повторной проверки
Identity Hub (`prompt=login`). Общая сессия Identity Hub этим не удаляется.
Уже выданный JWT проверяется до его `exp`; мгновенного отзыва токена при удалении
назначения или пользователя нет. Срок cookie не превышает срок JWT.

## Развёртывание и секреты

[Отдельный модуль](../../infra/identity/main.tf) создаёт пул, локального пользователя,
OIDC-приложение, назначение, сервисную учётную запись функции и два секрета Lockbox.
Он выполняется администратором выбранной организации отдельно от обычного
развёртывания приложения. Сервисной учётной записи приложения не выдаются права
управления каталогом пользователей. Функция получает только свои секреты. Учётная запись развёртывания может
назначать функции эту конкретную сервисную учётную запись; права управления
организацией ей не передаются.

В закрытой рабочей копии модуля задаются `folder_id`, `organization_id`,
`pool_subdomain`, `public_origin`, `deployment_service_account_id`, случайный `test_password` и отдельный
`transaction_key` — 32 случайных байта в base64url. Версия провайдера закреплена
файлом `.terraform.lock.hcl`. `terraform init`, `plan` и `apply` запускаются
в Docker-образе инструментов инфраструктуры. План сначала проверяется по списку
создаваемых ресурсов, затем применяется сохранённый файл плана.
Рабочая копия, входные значения, состояние и журналы остаются приватными:
состояние содержит начальный пароль и ключ незавершённых входов.

Результат `integration` переносится в приватную настройку `identity` основного
окружения. Её точные идентификаторы и версии секретов также входят в
`allowed_environment_identity` файла области развёртывания. `issuer` сверяется
с официальным OIDC discovery. `infra/deploy.sh` собирает воспроизводимый архив
функции, вычисляет `code_sha256` и сохраняет план приватно. В GitHub Environment
нужно обновлять оба секрета конфигурации и области развёртывания вместе.

Пароль после первой смены Terraform не сбрасывает. Для нового пользователя
создаются отдельная локальная запись и явное назначение этому приложению.
Пароли и список пользователей не публикуются в документации или CI.
Смена секрета клиента требует новой версии Lockbox и функции; смена
`transaction_key` отменяет только незавершённые входы. Уже выданные JWT проверяются
открытыми ключами Identity Hub.

## Проверка

Локально проверяются callback, подписи и сроки токенов, защита от подмены запроса,
запрет прежнего Basic для браузера, условное обновление индекса S3 и навигация.
Облачная проверка должна подтвердить настоящий вход локального пользователя,
смену начального пароля, чтение четырёх архивов, запись формы и выход.
CAPTCHA Identity Hub выполняет человек; её наличие не считается успешным входом.
Текущее состояние проверки указано в [М5](./cloud_first_m5.md).
