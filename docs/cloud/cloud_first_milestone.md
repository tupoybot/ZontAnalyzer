# ZontAnalyzer — веха Cloud-first

Статус: M0–M3 приняты; M4–M8 — план новой облачной версии<br>
Архитектура: [`cloud_first_architecture.md`](./cloud_first_architecture.md)

M0 принят; контракты сбора телеметрии от 2026-09-15:
[контракты, внешние решения и проверки следующих вех](./cloud_first_m0.md).
Получение телеметрии входит в задание генерации отчёта; отдельный частый polling
не переносится из VPS. Эти изменения плана ещё не означают реализации runtime.
Quarterly report остаётся планируемым контрактом cloud-first: текущая реализация
его не предоставляет, поэтому M3–M4 проверяют только будущую семантику данных и
явно не объявляют этот отчёт поддержанным до отдельной реализации.

Сверено 2026-09-08: [текущий статус](../status.md) подтверждает приёмку до 8.5
и 9.1/9.2. M0–M8 ниже — план отдельного инфраструктурного трека, не свидетельство
его реализации и не замена продолжающегося этапа 9. Действующие источники
и сохраняемые контракты перечислены в [cloud-архитектуре](./cloud_first_architecture.md#статус-и-связь-с-действующими-документами).

Основной product/analytics функционал уже реализован в `main`. M0–M8 описывают отдельный инфраструктурный трек: IaC, cloud runtime, managed storage, публикацию, observability и cutover. Старый VPS/SQLite production заморожен на принятом релизе до переключения. Новая версия развивается под облако и YDB без обязательной совместимости со старым runtime. Новые продуктовые функции в миграцию автоматически не включаются.

## Общие правила выполнения M0–M8

- Порядок зависимостей: M0 (контракты и внешняя реализуемость) → M1 (каркас,
  egress и минимальные лимиты) → M2 (облачный запуск и API) → M3 (реализация YDB)
  → M4 (перенос данных и полный цикл на YDB) → M5 → M6
  → M8 (переключение и завершение перехода).
  M7 необязателен и не блокирует cutover. Минимальные логи, ограничения расходов
  и выключение расписания нужны с M1; M6 завершает эксплуатационную наблюдаемость.
- Это порядок полной приёмки. Локальные части M3/M4 на YDB в Docker допускаются
  после контрактов M0 до M1/M2; облачная приёмка остаётся после их зависимостей.
- Сохранить поведение принятого production, включая стоимость газа и сопровождение AI.
  Этапы 10/11, доставка и накопленная экономия не включаются в миграцию автоматически.
- Сборки, Python-проверки и подготовка данных — локально в Docker по
  [процедуре выпуска](../development/release-process.md). Копия production создаётся штатным
  SQLite online backup, скачивается и проверяется на отдельной записываемой копии
  с изолированной публикацией. Живые SQLite/WAL не копируются напрямую.
- production host остаётся deployment-only: проверенный immutable image и короткий smoke,
  без сборок, тестовых наборов, backfill и тяжёлой приёмки. Cloud-spikes выполняются
  в изолированных ресурсах с ограниченным объёмом и бюджетом; production не тестовый стенд.
- По умолчанию использовать `--no-ai`/моки; не более одного реального OpenAI-запроса
  на пользовательскую итерацию суммарно для всех исполнителей, включая metadata smoke.
- Для каждой вехи фиксировать проверки и ограничения. Документация требует только
  проверок документов/ссылок/diff и commit/push; развёртывание для неё неприменимо.

## Облачная версия в main и old-stable для текущего production

До первого облачного изменения приложения в `main` проверяется точный commit и
digest образа, который работает на старом production. От этого commit создаются
ветка `old-stable` и неизменяемый тег. Сохраняются конфигурация,
резервные копии и инструкция восстановления этого выпуска.
Правила защиты ветки в GitHub не требуются для приёмки этапов; тег выпуска
не перемещается, а происхождение образа проверяется при развёртывании.

После приёмки М1 и отдельного согласованного включения облачного каркаса в `main`
дальнейшие этапы разрабатываются короткими ветками от `main`. Постоянная вторая
ветка облачной разработки не нужна. Ветка `old-stable` содержит только исходники
работающего старого production и необходимые для него исправления. Каждый этап
и каждое исправление проходят отдельный PR, проверки и явную приёмку. Это изменение
плана не разрешает автоматически слить М1 или обновить production.

Исправление старого production начинается короткой веткой от `old-stable` и
возвращается PR в `old-stable`. Проверенный образ собирается локально и
развёртывается на старом production вручную по digest. Если исправление применимо
к облачной версии, его отдельным коммитом переносят или адаптируют в ветке от
`main`. `main` не сливается в `old-stable`, новые возможности там не разрабатываются.

Новая версия предназначена для облака и YDB. Работоспособность нового образа на
старом VPS и поддержка SQLite в новом runtime не требуются. Сохраняются проверенная
аналитика, пользовательские функции и тесты их поведения. Слой работы с YDB
отделяется от расчётов настолько, насколько нужно для понятного кода и тестов;
универсальная система сменных backend и дублирующие реализации не создаются.

Локальная разработка и CI используют YDB в Docker; чистые расчёты тестируются без
БД. SQLite читается отдельным инструментом импорта из online backup старого
production. Код импорта не включается в рабочий контейнер. Новая версия и старый
зафиксированный выпуск сравниваются на одинаковых входных данных; совпадение
их image digest не требуется.

Образ проверенного коммита собирается один раз и развёртывается по неизменяемому
digest. Кандидат этапа может быть собран из его PR для изолированной облачной
проверки до приёмки. Образы из `main` и облачных веток запрещено развёртывать на
старом production. До первого облачного изменения приложения в `main` процедура
старого развёртывания должна проверять, что образ выпущен из `old-stable`.
Deployment выбирает проверенный артефакт, конфигурацию и ссылки на секреты,
не пересобирая приложение. При необходимости образ копируется в облачный registry
с сохранением digest. В М2 workflow выпуска дополняется сборкой кандидата из
доверенной ветки этапа; существующий workflow М1 пока выпускает только `main`.

До М8 облачные проверки используют отдельные данные, публикацию и получателей
уведомлений. Штатное расписание и пользовательские записи остаются на старом
production. При переключении сначала останавливаются старые записи и расписание,
затем переносится последняя разница данных и запускается облачная версия.
Возврат после новых записей в облаке требует их сохранения и проверенного переноса;
старой резервной копии для этого недостаточно.

## Обязательная очистка после каждого облачного этапа

Каждый этап М2–М8 завершается инвентаризацией ресурсов, созданных или изменённых
в Yandex Cloud во время этапа. До приёмки этапа удаляются проверочные стенды,
временные объекты и состояния, устаревшие образы, неиспользуемые версии секретов,
лишние учётные записи и права, а также заменённые ресурсы. Удаление проверяется
через API провайдера; отсутствия ресурса в состоянии Terraform недостаточно.

Сохранить можно только ресурс, который используется следующим принятым этапом или
нужен для проверенного восстановления. Для него в доказательствах этапа фиксируются
назначение, действующий потребитель и причина дальнейших расходов. Завершённый
эксперимент, возможная будущая потребность и удобство повторной проверки такой
причиной не считаются. Очистка не должна затрагивать ресурсы других проектов.
Без инвентаризации, подтверждения удаления и объяснения каждого сохранённого
платного ресурса этап не принимается и следующий этап не начинается.

## Внешние зависимости и условия продолжения

План не доказывает доступность конкретного аккаунта, региона или сетевого маршрута.
В M0 для каждой строки записать предварительное решение, ответственного и срок
проверки; фактические результаты добавить на указанной вехе. Неизвестное не считать
успешной проверкой. Внешний blocker закрывается доступной
альтернативой или останавливает зависимую работу, а не переносится к cutover.

| Зависимость | Когда закрыть | Проверка и выход при недоступности |
| --- | --- | --- |
| Cloud account, billing, IAM, квоты, IaC state и registry | M0; provisioning в M1 | Проверить доступ исполнителя и бюджет; определить bootstrap identity и защищённое хранилище IaC state вне удаляемого stack. При отсутствии доступа M1 не начинать. |
| OpenAI: поддерживаемая география, аккаунт и модели baseline | Выбор размещения в M0; сетевой/auth smoke в M2 | Проверить допустимость всей схемы по официальным условиям. Если несовместима, выбрать поддерживаемое размещение AI/runtime; при отсутствии приемлемого варианта остановить AI-миграцию, сохранить legacy. `--no-ai` пригоден для разработки, но не заменяет функциональную приёмку. |
| Управляемый исходящий proxy/egress | Контракт в M0; стенд и проверка в M1 | Зафиксировать провайдера/размещение, доступ, стоимость, владельца и восстановление. Внешний proxy должен учитываться как явная эксплуатационная зависимость; адреса не публикуются. Если выбранный runtime не позволяет нужный контроль, пересмотреть runtime/сетевую схему до M2. |
| ZONT API и облачные endpoints | Маршруты в M1; bounded read-only smoke в M2 | Проверить DNS/TLS, авторизацию и лимиты из выбранного runtime. Моки разрешают разработку, но не закрывают приёмку интеграции. |

## M0 — Зафиксировать архитектурные контракты без изменения product baseline

Принят владельцем 2026-09-15: [PR #4](https://github.com/tupoybot/ZontAnalyzer/pull/4)
слит в `architecture/cloud-first-serverless`, коммит `95f75d2`.
[Решения M0](./cloud_first_m0.md). [Реализация и проверки M1](./cloud_first_m1.md) завершены;
М1 принят владельцем 2026-09-22.

### Цель

Определить границы, на которые будет опираться полная cloud-инфраструктура, не меняя стабильный product baseline в `main`.

### Работа

- Основная единица — задание отчёта: получить из ZONT нужное окно и контекст,
  проверить полноту, проанализировать, опубликовать. Отдельного регулярного
  сбора телеметрии нет; legacy `run --once` декомпозируется на bounded use cases.
- Перечислить операции хранения и гарантии, которые нужны существующей аналитике.
- Выявить SQLite-specific предположения в migrations, UPSERT, transactions, locking и lifecycle отчётов.
- Разделить формирование отчёта и его публикацию в Object Storage.
- Определить загрузку конфигурации и секретов из локального окружения и Lockbox.
- Сохранить текущую read-only границу ZONT неизменной.
- Сбор перед daily, переиспользование истории для weekly/monthly/quarterly/seasonal
  и дозагрузка только missing ranges — обязательный контракт M0. Учесть 90 дней
  хранения ZONT, долговечный собственный архив и явные невосстановимые пропуски.
- Составить карту переноса всех сохраняемых данных и существующих web/API операций,
  включая профиль, газ/тарифы, эксперименты, AI-настройки/пересмотр и аудит.
- Зафиксировать границы application artifact, environment configuration и
  изолированные данные для последующих проверок облачного приложения.
- Закрыть предварительные решения из таблицы внешних зависимостей, включая
  размещение AI и механизм контроля исходящего трафика по контракту ниже.
- Выбрать invocation-протокол и записать бюджет cold start, работы, сетевых
  таймаутов и retries; большие задачи должны делиться на возобновляемые порции.

### Хранение и локальная разработка

YDB — единственная БД новой версии, локальной разработки и интеграционных тестов.
М3 реализует нужные операции хранения, М4 подключает их к приложению и проверяет
перенос данных. Старый production продолжает работать со своей SQLite на
зафиксированном релизе; поддержки двух БД в новом приложении нет.

Сохраняются предметные гарантии: чтение телеметрии за период, сохранение отчёта,
атомарный захват задания, обновление настроек и аудит. SQL/YQL, преобразования
типов, транзакции и индексы находятся в коде хранения под YDB. Общая ORM,
переключатель backend и отдельная система плагинов для БД не нужны.

У YDB есть официальный [Docker-образ](https://ydb.tech/docs/en/reference/docker/)
и [инструкция запуска](https://ydb.tech/docs/en/reference/docker/start). Версия
закрепляется, данные тестов изолируются. Локальная и управляемая YDB используют
один код хранения с разными параметрами подключения и аутентификации.
Локальные проверки не заменяют проверку IAM, сети, лимитов и расходов в облаке.

Сейчас приложение ещё использует SQLite. Перевод runtime, тестовых данных,
инструкций и CI выполняется в М3–М4. После этого SQLite читается только отдельным
инструментом импорта online backup; смена конфигурации сама по себе данные не
переносит. Сохраняются старый релиз и необходимые резервные копии. Перенос
production выполняется только при принятом переключении М8.

### Контракт проксирования и контроля трафика

- Ввести явную политику маршрутов по назначениям: ZONT, OpenAI generation/metadata,
  каталог моделей, cloud APIs и служебная identity. Для каждого маршрута выбрать
  `proxy`, разрешённый `direct` или `deny`; незаданные внешние назначения запрещены.
  Это будущий контракт конфигурации, а не уже существующие поля приложения.
- OpenAI generation/metadata и каталог моделей используют HTTP CONNECT на loopback
  Xray-клиента рядом с приложением; внешний транспорт — аутентифицированный
  VLESS/XHTTP/REALITY. ZONT использует явно разрешённый direct. Обязательны allowlist
  назначений/портов, лимиты соединений/байтов и таймауты. TLS к целевому API проверяет
  клиент; перехват/расшифровка TLS не требуется. Локальный proxy не публикуется наружу.
  Совместный lifecycle, готовность, cold start и ресурсы Xray проверяются в M1;
  при несовместимости runtime зависимая работа останавливается до нового решения.
- Все HTTP-клиенты должны применять одну политику, включая SDK OpenAI и каталог
  моделей. Не полагаться только на глобальный `HTTPS_PROXY`: проверить влияние
  `NO_PROXY`, redirects, DNS и переменных окружения на каждом адаптере. Служебный
  metadata/identity endpoint и cloud SDK используют отдельно разрешённые маршруты.
- При обязательном proxy его отказ блокирует соответствующий внешний вызов без
  автоматического direct fallback. Проверить маршрутизацию клиентов через
  выбранный внешний egress; блокировка прямого выхода
  произвольного кода на уровне сети не требуется. Проверить клиентов, SDK,
  redirects и влияние environment. Это не утверждение о сетевой изоляции VPC.
- CONNECT позволяет контролировать назначения и объём соединений, но не видеть
  HTTPS path, число API-запросов или токены. Лимиты запросов/токенов/расходов
  реализуются в приложении с общим долговечным учётом после M4.
- Proxy credentials хранить через secrets abstraction/Lockbox. В журналы писать
  назначение, разрешение/отказ, длительность и байты; не писать ключи, заголовки
  авторизации, тела запросов и телеметрию. Определить срок хранения журналов.
- Настроить воспроизводимое подключение к существующему управляемому proxy.
  Его доступность, стоимость и восстановление входят в эксплуатационный контракт;
  адреса и топология хранятся в приватной конфигурации окружения.
- Прокси контролирует трафик, но не подтверждает региональную совместимость OpenAI.
  Смена выходного IP сама по себе не закрывает проверку допустимости размещения.

### Критерии приёмки

- Cloud-код можно разрабатывать без импорта Yandex-specific SDK в domain/analytics modules.
- Не появляется требований, блокирующих текущий runtime и отдельную разработку функциональных исправлений в `main`.
- Существующий SQLite/local runtime остаётся рабочим и зелёным.
- Определены операции/типы storage contracts, временный выбор backend и критерии
  завершения rollback; различия локальной и managed YDB перечислены как проверки.
- Архитектурное изменение, описанное в `cloud_first_architecture.md`, просмотрено и считается целевым для этой ветки.
- Для зависимостей со сроком M0 есть решение и доказательства доступности;
  для проверок M1–M3 указаны критерий, ответственный и альтернатива при отказе.
  Размещение AI и способ контроля egress выбраны до создания основного stack.

## M1 — Terraform/IaC-скелет и пустой cloud runtime

### Цель

Создать облачный каркас проекта, пока не перенося application state.

### Работа

Создать через IaC отдельный **Yandex Cloud project folder** в выбранном
cloud. Все ресурсы проекта, поддерживающие folder scope, размещать в нём;
`folder_id` явно передавать в IaC и deploy workflows, не наследовать каталог
из активного профиля `yc` или developer environment. Если каталог уже существует,
проверить его принадлежность проекту и импортировать в IaC вместо дублирования.
Bootstrap-доступ для создания folder отделить от deployment service account;
права deployment ограничить этим folder и необходимыми ресурсами. Общие
cloud/billing ресурсы учитывать как внешние зависимости, не изменять попутно.

Развернуть через Terraform или выбранный в репозитории IaC-инструмент:

- service account(s) с least-privilege IAM;
- Yandex Container Registry как target для локально проверенного immutable image;
- environment-specific configuration и references на secrets отдельно от image;
- механизм выбора и копирования проверенного application image digest из `main`;
- Serverless Container;
- Timer Trigger, напрямую вызывающий контейнер; включить после ручного smoke;
- placeholders/references секретов Lockbox;
- изолированную YDB Serverless database для M3, ещё не production backend;
- Object Storage bucket/prefix для публикуемых отчётов;
- панель Grafana, экспорт health-метрик и оповещение владельцу;
- выбранный proxy/egress, необходимые сетевые ресурсы и secret references;
- минимальные логи/alerts, бюджет стенда, ограничения invocation/concurrency/retries
  и документированное выключение расписания. Billing alert не считать hard cap.

Развернуть минимальную revision контейнера, которая обрабатывает вызов выбранного
режима, подтверждает identity/config access, публикует тестовую health-метрику
и возвращает успешный результат. Для HTTP server mode нужен обработчик на `PORT`;
завершение CLI при старте само по себе не является обработкой timer invocation.

На синтетическом endpoint проверить разрешённый proxy-маршрут, запрет постороннего
назначения в прикладных клиентах, отсутствие direct fallback и отказ proxy.
Отдельным маленьким web-spike
проверить приватный объект и защищённый API через выбранный ingress: нельзя
предполагать, что Basic Auth/cookies проходят фильтрацию заголовков без изменений.

Не добавлять Cloud Functions только ради вызова контейнера.

### CI/CD и проверенный артефакт М1

М1 проверяет выпуск принятого приложения из `main`, копирование его digest в
облачный registry и отдельное развёртывание инфраструктурного probe. Production
не обновляется. Этот результат сохраняется при переходе к одной облачной версии;
он не доказывает готовность приложения к работе с YDB.

Критерии:

- Проверки, commit SHA и digest позволяют однозначно определить выбранный образ.
- Deployment не принимает плавающие теги и не пересобирает приложение.
- Повторное развёртывание с тем же digest сохраняет выбранный артефакт.
- Конфигурация, секреты, состояние и публикация разделены по окружениям.
- Проверочный контейнер не запускает production-анализ, AI-генерацию или
  пользовательские записи. Работа старого production не зависит от проверки.



### Критерии приёмки

- Чистый cloud/folder воспроизводимо разворачивается из IaC.
- Имя folder задаётся приватной конфигурацией; его ID доступен в защищённых outputs и deployment
  evidence. Plan и фактическое размещение подтверждают, что ресурсы создаются
  в нём, а ресурсы других folder не изменяются. Dev/pilot/prod внутри него имеют
  раздельные state/secrets/publication и явные имена окружений.
- Timer по расписанию вызывает Serverless Container.
- Container работает под service account с ограниченными правами.
- Для скелета не нужен постоянно работающий VM/VPS.
- Секреты подключаются ссылками и не вшиваются в image/IaC source.
- Удаление тестового stack не затрагивает существующий production/pilot deployment.
- Перед приёмкой удалены временные и ненужные ресурсы, тестовые образы и
  неиспользуемые версии секретов. Отсутствие остатков подтверждено API провайдера,
  а не только состоянием Terraform. У каждого сохранённого платного ресурса есть
  действующий потребитель либо явное назначение для восстановления; завершённый
  эксперимент не является основанием продолжать платить за его ресурсы.
- Proxy/egress проверки пройдены из реального runtime; доступ к identity, secrets
  и storage работает по явно разрешённым маршрутам. Постоянные сетевые расходы учтены.
- Выбран реализуемый web/API-периметр; лимиты и отключение timer проверены до M2.

## M2 — Облачный запуск и внешние API

### Цель

Подготовить запуск новой версии в Serverless Containers и проверить внешние
соединения. Полный отчёт с постоянным хранением проверяется после реализации YDB.

### Работа

- Создать простой HTTP-вход для ограниченного задания, готовности и диагностики.
  Повторный запрос к уже запущенному контейнеру должен обрабатываться. Xray
  запускается вместе с приложением по проверенной схеме М1.
- Убрать из облачного старта обязательную инициализацию SQLite и бесконечный цикл
  старого worker. Не создавать временный SQLite-backend для облачного отчёта.
- Отделить вызов проверенной аналитики от запуска сервиса и работы с файлами.
  Временный диск используется только для воспроизводимых промежуточных файлов.
- Добавить идентификатор задания в логи, явные ошибки и ограничение времени работы.
  Проверить повторные запросы и отказ proxy на небольших тестовых данных с моками.
- Проверить ZONT ограниченным read-only запросом, OpenAI — через выбранный egress.
  После проверки условий доступа выполнить не более одного authenticated metadata
  запроса OpenAI с ожидаемым 200; генерация для сетевой проверки не нужна.
- Настроить workflow cloud deployment для `main` и коротких веток этапов.
  В Environment `cloud-dev` использовать `No restriction`, чтобы новые ветки
  не требовали ручной настройки; приватные параметры хранить в Environment Secrets.
  Дополнить CI сборкой проверенного
  кандидата из доверенной ветки этапа и развёртыванием по digest в изолированное
  окружение. Публикация кандидата
  не обновляет старый production; секреты недоступны недоверенным PR.

### Критерии приёмки

- Облачный кандидат запускается, отвечает на первый и повторный запросы,
  ограничивает время задания и сообщает об ошибках в логах и метриках.
- Потеря временных файлов не подменяет постоянное хранение; до М3–М4
  проверяются только изолированные сценарии, без production-расписания и записей.
- Подтверждены маршруты ZONT/OpenAI и отказ без прямого обхода proxy.
- Проверки и digest однозначно связаны с коммитом кандидата; повторный deploy
  использует тот же образ. Запуск этого образа на старом VPS не требуется.

## M3 — Реализация хранения в YDB

### Цель

Реализовать необходимое хранение в выбранной YDB и проверить его на реальных
операциях. Это рабочая реализация для М4, а не отдельный выбрасываемый прототип.

### Обязательные операции

Реализовать операции хранения под YDB и проверить:

1. Сохранение телеметрии без дубликатов при повторной загрузке.
2. Чтение рядов за период с учётом покрытия, пустых успешных ответов,
   пропусков и 90-дневной границы источника.
3. Чтение обнаруженных устройств и рядов.
4. Сохранение и чтение исходных событий.
5. Сохранение и загрузка отчёта.
6. Обратная связь по рекомендациям и история ручных изменений.
7. Сохранение позиции, с которой нужно продолжить синхронизацию.
8. Атомарный захват задания одним исполнителем, срок владения и безопасный повтор.
9. Учёт использования LLM.
10. профиль, показания/калибровка газа, месячные тарифы/валюты и аудит;
11. версии AI-настроек, предложения/решения пересмотра, provenance и кэши;
12. периоды/ревизии и согласованное чтение данных для расчёта/публикации.

Тестировать на обезличенной выборке реальной установки и реалистичном объёме телеметрии.
Начать с YDB в локальном Docker по порядку из M0; затем проверить managed YDB
в project folder. Результаты локальных функциональных
проверок и облачных эксплуатационных измерений фиксировать отдельно.

### Критерии приёмки

- Все обязательные операции реализованы; незакрытый блокер не позволяет принять М3.
- Тесты доказывают атомарность захвата заданий и поведение конкурентных записей.
- Запросы и индексы проверены на объёмах дневных и недельных расчётов.
- Тесты доказывают загрузку пропусков без дубликатов, повторное использование
  истории для weekly/monthly и будущего quarterly, ограниченную дозагрузку поздних
  данных и сохранение покрытия дольше 90 дней источника.
- Оценки cost/storage записаны по реальным измерениям или platform calculators, а не придуманы.
- Неразрешённый blocker YDB останавливает перенос, сохраняя текущий production;
  изменение выбранной целевой БД требует отдельного решения владельца.

## M4 — Перенос данных и полный цикл отчёта на YDB

### Цель

Запустить новую версию с постоянным состоянием в YDB и проверить её на копии
реальных данных. Старое приложение остаётся неизменным источником сравнения.

### Работа

- Подключить реализованное в М3 хранение к сбору телеметрии, аналитике, отчётам
  и пользовательским операциям. Использовать прямую реализацию под YDB;
  слой совместимости со вторым backend не нужен.
- Создать отдельный инструмент переноса online backup SQLite в YDB. Повторный
  импорт не дублирует данные; поддерживается перенос последних изменений перед
  переключением. Зафиксировать состав данных и проверку полноты переноса.
- Перенести профиль, газ, тарифы/валюты, feedback, аудит, настройки AI, версии
  отчётов, кэши и происхождение ответов. Не запускать массовую AI-генерацию.
- Перенести тестовые данные, локальные инструкции и CI на YDB в Docker. Удалить
  SQLite, Alembic и выбор backend из нового runtime, когда соответствующие
  операции и проверки переведены. Старый релиз и его инструкции сохраняются.
- Подключить сбор перед daily; weekly/monthly используют архив и догружают только
  пропуски. Сохранить успешные пустые интервалы, различать ошибки и отсутствие
  данных, учитывать 90-дневную границу ZONT и хранить собственную историю дольше.
- Проверить полный цикл задания: первый и повторный вызов, потерю временного
  диска, прерывание и продолжение загрузки, конкурирующие вызовы и лимиты API.

### Критерии приёмки

- Новое приложение, локальная разработка и CI используют только YDB.
  Чистая аналитика тестируется без БД. SQLite нужен только старому production
  и отдельно запускаемому инструменту импорта.
- Инициализация схемы и импорт воспроизводимы; повторный импорт безопасен.
  Сохранены идентичности, связи, исходная детализация, UTC-время, календарные
  границы объекта и пользовательский аудит.
- На одинаковых данных детерминированные факты нового и старого выпусков совпадают
  в пределах объяснённых различий. Регрессии аналитики, газа и DHW не скрыты
  обновлением ожидаемых значений тестов.
- Один и тот же период не вызывает повторную полную загрузку или пересчёт только
  из-за переноса БД. Сохранены кэши, отпечатки фактов и неизвестные исторические модели.
- Интервалы старше 90 дней читаются из архива; отсутствующие и уже недоступные
  интервалы явно отмечены. Будущий quarterly не объявляется реализованным.
- Проверены конкурентные записи, захват задания, истечение срока владения и
  неизвестный результат внешнего AI-вызова; слепой повтор генерации не используется.
- Полный облачный цикл работает на изолированной YDB; пользовательские записи,
  публикация и уведомления не затрагивают старый production.
- До М5 выбран простой проверяемый способ восстановления: возврат на старую
  систему до разрешения новых записей либо восстановление совместимого облачного
  выпуска с сохранением данных. Требования к переключению уточнены в М8.

## M5 — Публикация в Object Storage и сохранение защищённого web/API

### Цель

Публиковать отчёты без зависимости от persistent local filesystem.

### Работа

- Отделить формирование файлов отчёта от загрузки в Object Storage;
  универсальная система сменных способов публикации не требуется.
- Реализовать Object Storage publisher для:
  - стабильного `latest.html` только для дневного отчёта;
  - датированного HTML;
  - архива дневных, недельных, месячных и сезонных отчётов и `reports.json`;
  - канонического/переносимого JSON export, где это полезно.
- Канонический report state хранить в БД; Object Storage остаётся presentation/export target.
- Сделать публикацию идемпотентной и безопасной при retries.
- Перенести существующие web/API операции: комментарии/feedback, эксперименты,
  профиль, показания, тарифы и AI-настройки. API Gateway — кандидат, выбор сервиса
  не меняет обязательность сохранения этих функций до cutover.
- Сохранить общий периметр HTML/JSON/manifest/API, закрыть обход через bucket.

### Критерии приёмки

- Завершённый analysis публикует валидный standalone HTML report в Object Storage.
- Повторный invocation не создаёт несогласованное состояние latest/archive.
- Output rendering соответствует semantics локального renderer.
- База данных не запускается с Object Storage mount.
- Файлы готовы до manifest, latest обновляется после архива; сбой и устаревший
  конкурентный publisher не создают ссылки на незавершённые объекты и не откатывают новую публикацию.
- Сохранение пользовательских данных предшествует публикации; просмотр/рендер
  не вызывают AI и не подменяют его ответ. Переносимый HTML экранирует текст.
- Браузерные проверки desktop/mobile подтверждают навигацию по типам/архиву,
  формы, стоимость и происхождение AI; неавторизованный доступ закрыт.

## M7 — Опциональные cloud UX services и визуализация

### Цель

Добавлять managed services только там, где они упрощают реальный use case, и при желании дать проекту удобный инженерный UI для исследования телеметрии.

Возможные дополнения:

- **Grafana Cloud Free** как опциональный visualization layer для красивых инженерных графиков из канонической telemetry: комнаты/уставки, улица, подача/обратка/ΔT, ГВС, горелка, reliability events и interventions. Это не source of truth и не обязательная часть ZontAnalyzer: штатные графики ZONT и standalone HTML остаются достаточными для обычного использования. Если Grafana подключается напрямую к YDB, использовать отдельные строго read-only credentials/service identity;
- дополнительные API endpoints сверх обязательного переноса существующих операций в M5;
- Postbox как кандидат для email после отдельного выбора задачи по [плану доставки](../delivery-plan.md);
- Workflows/EventRouter, если orchestration станет понятнее, чем единый `run --once`;
- Message Queue, если понадобятся asynchronous retries/backpressure;
- Yandex Query + Object Storage для долгосрочного аналитического архива.

Cloud Functions разрешены для изолированных маленьких handlers, если они действительно проще расширения основного контейнера. Это не runtime по умолчанию.

### Критерии приёмки

- У каждого добавленного сервиса есть конкретная продуктовая или эксплуатационная причина.
- Ни один сервис не добавляется только ради более «cloud-native» вида архитектуры.
- Если Grafana включена, она читает только канонические данные через read-only доступ и не становится обязательной зависимостью ingestion/analysis/report pipeline.
- Feedback endpoints могут менять только состояние, принадлежащее ZontAnalyzer, но не ZONT/boiler controls.
- Telegram/email остаются отложенными: доставка использует сохранённый отчёт,
  не запускает AI, не обходит авторизацию и не блокирует ingestion/analysis/publication.
  При выборе канала отдельно проверяются повторы, неизвестный исход и отключение.

  выключенными. До их открытия возможен возврат к старому production без потери
  новых пользовательских данных; облачная генерация и расписание при возврате
  останавливаются. Проверить актуальность телеметрии после возобновления.
- После разрешения записей основное восстановление выполняется в облаке:
  совместимый проверенный образ и восстановление YDB с учётом новых данных.
  Если нужен возврат на старую систему, сначала отдельно проверить перенос всех
  новых пользовательских записей. Непроверенный обратный импорт не обещается.
- После согласованного периода наблюдения удалить остановленные ресурсы старого
  приложения и временные инструменты/данные, которые больше не нужны. Не затрагивать
  соседние сервисы и используемый egress. Сохранить необходимые backup и старый релиз.

### Критерии приёмки

- Перенесены исходные измерения, связи, пользовательские данные, аудит, тарифы,
  настройки и AI provenance; нет необъяснимых потерь или массовой регенерации AI.
- Работают защищённые страницы, архив и формы М5; штатное расписание и записи
  выполняет только одна система.
- Проверены возврат до открытия записей и восстановление облачной системы после
  их открытия. Условия и длительность окна переключения согласованы с владельцем.
- Облачная версия прошла согласованный период наблюдения; расходы и отказы видны.
- SQLite отсутствует в новом runtime и CI уже с М4. Отдельный поздний этап удаления
  второго backend не требуется. Архив старого релиза не считается его активной поддержкой.
- Временные и ненужные платные ресурсы удалены, необходимые данные сохранены.
  Переключение и завершение периода наблюдения явно приняты владельцем.

## Интеграция и приёмка через GitHub Issues/PR

[Issue #1](https://github.com/tupoybot/ZontAnalyzer/issues/1) остаётся общим указателем
на этапы и PR. Начиная с М2, перед началом каждого этапа создаётся один дочерний
issue (GitHub sub-issue) этой вехи. М7 создаётся только при решении выполнять его.
В описании достаточно цели, границ работы, ссылки на критерии в плане и связанного
PR. Подробные контракты остаются в документах; дополнительный трекер не нужен.

При передаче результата оставляется один короткий итоговый комментарий: что
изменилось для автора задачи, итог проверок, ссылка на PR и оставшиеся ограничения.
Промежуточные сообщения нужны только при препятствии, требующем решения автора,
существенном изменении объёма/сроков или выводе, меняющем ожидаемый результат.
Запуски CI, отдельные коммиты и обычные промежуточные проверки не комментируются.
Подробные доказательства доступны по ссылке на CI, PR или документ этапа.
После приёмки владельцем и merge issue закрывается со ссылкой на результат,
без повторного подробного отчёта. В Issue #1 обновляются состояние и ссылки
на этапы; итоги дочерних issues там не дублируются.

При изменении плана в той же задаче обновляются Issue #1 и затронутые дочерние
issues: объём, зависимости, критерии и статус. Если изменение ещё ожидает приёмки,
это явно отмечается со ссылкой на PR плана. Обновление плана считается завершённым
только после синхронизации issues. Завершённый М1 заново не оформляется и не проверяется.

М1 принят владельцем 2026-09-22. Перед первым облачным изменением приложения в `main`
точное работающее состояние старого production закрепляется в ветке
`old-stable` и неизменяемом теге. После приёмки М1 облачный каркас и обновлённые
документы отдельным PR включаются в `main`, без обновления старого production.
Затем М2–М8 выполняются короткими ветками `stageM<N>/<topic>` от актуального
`main`; документация — `docs/<topic>`. Не ждать М8 для интеграции облачного кода.

До запроса приёмки выполнить реализацию, необходимые проверки, commit/push,
применимое развёртывание и ограниченный smoke. Каждый этап сливается только после
явного принятия владельцем по [процедуре](../development/release-process.md). Следующий этап
начинается от принятого состояния. Перед merge выполнить локальный
`docker system prune -af`; на production host эта очистка не запускается.

PR описывает результат, проверки, миграцию данных и необходимые действия при
восстановлении. Совместимость нового образа со старым VPS не является критерием.
Необходимое исправление старого production идёт короткой веткой и PR в
`old-stable`; при необходимости оно отдельно переносится в `main`. Поддерживать
новые облачные функции в `old-stable` не требуется.

## Definition of milestone complete

Полный cloud-first трек завершается после обязательных M0–M6 и M8: scheduled
Serverless Container без постоянного VPS для приложения, каноническое состояние в YDB с пройденной
приёмкой, защищённые отчёты в Object Storage и существующий web/API, observability,
сохранение продуктовых контрактов и принятое переключение М8. Новый runtime,
локальная разработка и CI используют YDB; старый production выведен из эксплуатации
после периода наблюдения, необходимые данные и резервные копии сохранены.
Ветка `old-stable` после этого не используется для разработки и остаётся вместе с
тегом как источник аварийного выпуска.
M7 выполняется только по отдельной потребности. Каждая выбранная веха требует
технических доказательств, явной приёмки владельца и последующего merge её PR.
