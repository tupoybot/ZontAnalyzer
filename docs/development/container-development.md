# Локальная проверка в Docker

Используйте `deploy/check-local.sh` из корня репозитория. Скрипт собирает
тестовый Docker-образ, запускает Ruff и mypy, выполняет **весь** pytest через
`deploy/check-tests.sh` и собирает wheel/sdist. Чистая логика проверяется без
сети; запросы, транзакции и хранение — на настоящей одноразовой YDB. Доступ
к ZONT и OpenAI не нужен. Это техническая проверка кандидата, а не развёртывание.

```sh
deploy/check-local.sh
```

Доступны отдельные операции:

```sh
deploy/check-local.sh build
deploy/check-local.sh check
deploy/check-local.sh check-prebuilt
deploy/check-local.sh export --out-dir /absolute/path/to/artifacts
deploy/check-local.sh all --out-dir /absolute/path/to/artifacts
```

`check` тоже собирает актуальный test-образ перед проверками. `check-prebuilt`
использует уже подготовленный образ; этот режим нужен для сравнения локального
прогона с Actions на одном и том же образе. `export` сохраняет
пакеты только в явно заданный абсолютный каталог вне репозитория. Без `--out-dir`
сборка пакета остаётся во временном каталоге контейнера.

`check-tests.sh` сначала выполняет тесты без маркера `ydb` с `--network none`,
затем передаёт группу `pytest.mark.ydb` в `check-ydb.sh`. Тот создаёт отдельную
Docker-сеть и временный контейнер YDB, дожидается доступности сервиса, проверяет
фактический режим дисков в памяти и передаёт тестам `YDB_TEST_ENDPOINT`.
После тестов установленный CLI выполняет `init` на чистой схеме.
При завершении скрипт удаляет созданный стенд. Исходный репозиторий монтируется
только для чтения; временные файлы лежат в контейнерном `tmpfs`. Внешние API
не вызываются. Отсутствие YDB в Docker-проверке является ошибкой; явные пропуски
сохраняются только для ограниченной среды Codex Cloud.

Тесту, использующему общую фабрику базы, нужен маркер `@pytest.mark.ydb`.
Он задаётся у конкретной функции, чтобы чистые тесты смешанного модуля оставались
независимыми от базы. Между тестами очищаются все таблицы и создаются новые
клиенты YDB; процессы не делят пространства таблиц. Для тестов изменения схемы
используйте `make_database(..., fresh_schema=True)`. Ошибка очистки или
незавершённое фоновое задание приводит к ошибке теста и запрещает повторное
использование пространства.

Группа YDB запускается в двух процессах. Для последовательной диагностики
задайте `ZONT_TEST_WORKERS=1`; число процессов не выбирается автоматически
по мощности локального компьютера. Один контейнер YDB имеет пределы 2 CPU
и 5 GiB, тестовый контейнер — 2 CPU и 1 GiB. Дополнительный swap для них
запрещён. Обоснование этих значений приведено в результатах измерений.

Для замеров задайте пустой каталог вне репозитория:

```sh
ZONT_METRICS_DIR=/absolute/path/to/empty-metrics deploy/check-local.sh check-prebuilt
```

Нужен Node.js для измеряющей оболочки; Python по-прежнему работает только
в Docker. Каталог содержит фазы запуска, время setup/call/teardown каждого
теста, параметры образов, ограничения и потребление ресурсов, сводку
`summary.json` и таблицу `test-durations.csv`. В Actions они сохраняются как
`ci-metrics-N`, где N — номер попытки запуска. У PR с меткой `ci-benchmark`
также сохраняется архив тестового образа `ci-test-image-N`. Его нужно загрузить
локально через `docker load` и использовать тот же проверенный commit из `run.json`.

Метод сравнения и результаты приведены в [оптимизации CI](./ci-optimization.md).

Python и pip на хосте для этого процесса не нужны. Не устанавливайте зависимости
в host Python или локальную `.venv`. Для задачи Codex Cloud без Docker используйте
`deploy/check-codex-cloud.sh`; его проверки с фикстурами не заменяют Docker/CI,
проверку неизменяемого образа и отдельную приёмку на данных.

Кандидат М4 хранит рабочие данные в YDB. Локальные каталоги данных и публикации
нужны для временных файлов, HTML/JSON и статуса фонового процесса; они не являются
копией базы. Работающий прежний выпуск остаётся на ветке `old-stable` до этапа М8.
Его SQLite-команды и порядок эксплуатации приведены в
[README прежнего выпуска](https://github.com/tupoybot/ZontAnalyzer/blob/old-stable/README.md).
