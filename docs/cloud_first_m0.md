# M0 — как приложение будет работать в облаке

Дата: 2026-09-15. **M0 принят владельцем: PR #4 слит в
`architecture/cloud-first-serverless` (коммит `95f75d2`). Облачная версия
пока не реализована и не развёрнута.** Работа M0 выполнена в ветке `docs/cloud-first-m0`.
Код приложения соответствует принятой версии `main`, коммит `82a7a82`.

M0 определяет, что нужно сохранить при переносе, какие решения уже выбраны
и что предстоит проверить. Реализация распределена по следующим этапам
[плана M0–M8](./cloud_first_milestone.md). Приёмка этого документа разрешает
переход к M1, но не означает приёмку ещё не написанной облачной версии.

## Что выбрано и что работает сейчас

Сейчас приложение работает на сервере, хранит данные в SQLite и публикует
отчёты в локальные файлы. В облаке планируется следующая схема:

1. Перед дневным отчётом приложение получает нужную историю из ZONT и проверяет,
   что данные загружены полностью. Отдельного пятиминутного сборщика не будет.
2. Собственная история хранится в YDB. Недельные, месячные, сезонные и планируемые
   квартальные отчёты используют её и догружают только недостающие интервалы.
   Ограничение ZONT в 90 дней не становится сроком удаления нашей истории.
3. Готовые HTML и JSON загружаются в закрытое хранилище Yandex Object Storage
   через S3 API. Пользователь получает их через сайт с проверкой доступа.
   Формы сайта продолжают работать через API приложения.
4. Запросы к OpenAI идут через Xray-клиент рядом с приложением и выбранный внешний
   прокси. ZONT доступен напрямую. При отказе прокси приложение не обращается
   к OpenAI в обход него.
5. Ресурсы приложения размещаются в отдельном каталоге Yandex Cloud.
   Конкретные адреса, имена и идентификаторы задаются приватными настройками.

Доступ на чтение к облаку, активный платёжный аккаунт и основные свободные квоты
проверены. Расчёт стоимости подготовлен. Ресурсы проекта в M0 не создавались;
права на их создание и работа выбранной схемы проверяются в M1 и далее.
Старый VPS остаётся доступным на принятом immutable-релизе до cutover; его SQLite
используется для online backup, одностороннего импорта и изолированных сравнений.

## Где будут лежать HTML и как пользователь их получит

**Выбрано S3-совместимое хранилище Yandex Object Storage. Загрузка отчётов туда
будет реализована в M5.** Сейчас [публикация](../src/zont_analyzer/application/publication.py)
создаёт HTML и JSON в каталоге на диске сервера.

В облаке приложение после расчёта сохранит результат в YDB, сформирует файлы
и загрузит их в отдельный закрытый бакет — контейнер для объектов в S3.
В нём будут датированные отчёты, архив по видам отчётов, список `reports.json`
и доступ к последнему дневному отчёту по адресу `latest.html`.
Исходные данные и история изменений остаются в YDB; HTML и JSON — их публикация.

Предлагаемая схема выдачи:

```text
Расчёт отчёта → результат в YDB → готовые HTML/JSON в закрытом S3-бакете

Браузер → сайт с проверкой доступа
             ├─ просмотр отчёта → готовый файл из S3
             └─ сохранение формы → API приложения → YDB → обновление публикации
```

Для входа на сайт в M1 проверяется API Gateway: он должен проверять доступ
пользователя, отдавать готовые файлы и направлять запросы форм в приложение.
У шлюза есть [интеграция с Object Storage](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/object-storage).
Конкретная настройка авторизации и маршрутов ещё не проверена на стенде.
Бакет не должен позволять обойти вход на сайт по прямой ссылке.

Просмотр страницы не запускает анализ или AI. Формирование отчётов остаётся
отдельной работой по расписанию или явному запросу. Комментарии, показания газа,
тарифы, профиль и настройки AI сохраняются через API; обновления HTML можно
дождаться после ответа формы. Секреты, резервные копии и состояние Terraform
не размещаются в бакете публикаций.

### Как избежать битых ссылок и потери публикации

Сначала загружается полный набор файлов новой версии отчёта. Затем обновляется
список опубликованных отчётов, и только после этого — ссылка на последний дневной
отчёт. Файлы уже опубликованной версии не изменяются на месте. Если загрузка
прервётся, старый отчёт останется доступным, а незавершённая версия не попадёт
в навигацию. Неиспользуемые файлы после сбоя допустимы; ссылки на отсутствующие
файлы — нет.

Для реализации предлагаются две операции: загрузить файлы версии
(`ArtifactPublisher.stage`) и заменить список опубликованных версий
(`commit_manifest`). Это проектные названия методов, а не уже существующий API.
Замена списка должна проверять, что за это время его не обновил другой процесс.
В M5 нужно доказать работу условной записи по версии либо выполнять публикации
через один координирующий процесс. Обычная загрузка файла после проверки права
на выполнение не защищает от запоздавшего процесса.

YDB и S3 не участвуют в одной общей транзакции. Поэтому задание публикации
сохраняется в БД и после сбоя может безопасно продолжиться. Отметка о завершении
меняется только после подтверждённой публикации. Процесс, потерявший право
выполнять задание, не может отметить его завершённым или вернуть старую версию.

Сейчас надёжную запись файлов обеспечивают блокировка `flock`, сброс на диск
`fsync` и замена `os.replace`. Локальная `.publication-cache.sqlite3` хранит
восстановимый индекс и очередь, а не исходные данные. При переносе её не нужно
импортировать как отдельную рабочую БД. Облачные индекс, очередь и отметки
о прогрессе хранятся в YDB и восстанавливаются по отчётам и списку публикаций.

Сохраняются ограничения [инкрементальной публикации](./incremental-publication.md):
не более восьми отчётов за проход, приоритет последнего дневного отчёта,
отсутствие полного чтения архива при пустой очереди.

## Как будет запускаться и настраиваться приложение

Старый сервер остаётся на принятом образе с фиксированной контрольной суммой
`digest`. Новое cloud-only приложение собирается и тестируется как отдельный
артефакт, сразу рассчитанный на YDB. Общего образа для VPS и cloud не требуется;
legacy получает только критические исправления до cutover.

В M1 допустим отдельный небольшой тестовый образ для проверки инфраструктуры.
Он должен быть явно обозначен как проверочный, не запускать аналитику и не
считаться доказательством, что рабочий образ уже совместим с облаком.

Cloud-приложение получает настройки публикации, заданий, секретов и внешних маршрутов.
Оно работает только с YDB. Бизнес-аналитика, формат отчёта и проверочные тесты
сохраняются при переносе, но SQLite-runtime adapter и переключатель backend не нужны.

Сейчас [код запуска](../src/zont_analyzer/runtime.py) сразу подключает базу,
обновляет её структуру и статусы рекомендаций. В M2 эти действия нужно отделить
от проверки настроек и прав доступа. Проверка должна завершаться без изменения
БД и рекомендаций.

Настройки загружаются с проверкой значений. Секреты передаются из приватного
окружения, в облаке — через ссылки Lockbox, и остаются в памяти процесса.
Для этого достаточно простых функций загрузки и проверки; отдельная система
сменных поставщиков конфигурации не требуется.

На сервере остаются файлы и переменные окружения; для секретных файлов проверяется
режим доступа `0600`. В облаке используются ссылки на конкретные версии секретов
в Lockbox. Значения секретов не входят в образ, Git, состояние Terraform или логи.
Неизвестный тип БД, отсутствующий обязательный секрет или неполные правила сети
останавливают соответствующий запуск. Облако не подхватывает случайный локальный
файл, если нужной настройки нет.

Проверочный стенд использует отдельные БД, бакет или префикс объектов, секреты
и записи заданий и расходов. Рабочее расписание, генерация AI, отправка сообщений
и запись в основное окружение там явно отключены. Сам по себе `run --once`
означает один запуск, а не безопасный режим без изменений.

## Когда и какие данные забирать из ZONT

Перед дневным отчётом приложение загружает историю за нужный период, проверяет
её полноту и только затем выполняет анализ. Недельный, месячный, сезонный
и планируемый квартальный отчёт сначала проверяют собственный архив.
Из ZONT запрашивается только то, чего в нём недостаёт.

Для каждого устройства, ряда измерений и интервала сохраняется один из результатов:

- данные успешно получены полностью;
- источник успешно проверен, но измерений в этом интервале нет;
- данные получены не полностью либо запрос завершился ошибкой;
- интервал уже недоступен в ZONT и ранее не был сохранён.

Успешный HTTP-ответ и несколько найденных измерений ещё не доказывают полноту.
Нужно проверить все страницы ответа, возможное обрезание и частичные ошибки.
Проверенный пустой интервал не запрашивается снова только из-за отсутствия
измерений. Ответ, обрезанный границей хранения ZONT, нельзя считать проверенным
пустым интервалом.

План загрузки получается вычитанием уже проверенных и сохранённых интервалов
из нужного периода. При дозагрузке первыми обрабатываются самые старые данные,
которые ещё можно получить. Для запаздывающих измерений допускается ограниченное
повторное чтение соседнего интервала; его размер должен быть согласован.
Новые данные меняют версию истории и позволяют обновить зависимые отчёты.

### Что означает ограничение ZONT в 90 дней

Рабочее ограничение, указанное владельцем: ZONT хранит историю только 90 дней.
В нашей БД и резервных копиях история должна сохраняться дольше. Квартал может
длиться 91–92 дня, поэтому его начало нужно загрузить заранее, а не в день
формирования квартального отчёта.

При первом запуске приложение постепенно загружает доступную историю для будущих
длинных отчётов. Загрузка должна продолжаться после прерывания с сохранённого
места. После простоя сначала восполняются доступные пропуски. Если старейшие
незагруженные данные скоро выйдут за пределы 90 дней, приложение сообщает
о риске потери. Отдельный пятиминутный сборщик для этого не вводится.

Если старые измерения уже исчезли из ZONT и у нас не сохранены, восстановить их
через этот API нельзя. Отчёт явно показывает неполный период и делает выводы
только по имеющимся данным. Пропуски не заменяются нулями, не выдумываются
и не запрашиваются бесконечно.

Сейчас история читается порциями до 24 часов с сохранённой позиции и небольшим
перекрытием. Редкая загрузка истории сама по себе не уменьшает частоту исходных
измерений. Однако настройки оборудования фиксируются в момент опроса:
при ежедневном запуске промежуточная смена настроек может остаться незамеченной.
В M2 нужно отдельно проверить получение запаздывающей истории и сведений
о смене настроек. До проверки нельзя обещать, что ежедневная фиксация настроек
равнозначна пятиминутной. Это ограничение источника, а не решение вернуть
частый опрос без отдельной потребности продукта.

## Какие действия запускают работу

Облачная версия должна выполнять конкретную задачу, а не полный текущий цикл
`PilotService.run_cycle` при каждом обращении.

| Событие | Что выполняется | Ограничение |
| --- | --- | --- |
| Завершился местный день, наступило 01:00 | Загрузка нужной истории, проверка полноты, дневной анализ и публикация | Изменение только служебных полей не вызывает повторный AI |
| Завершилась неделя, месяц или сезон; в будущем — квартал | Дозагрузка недостающей истории и контекста, расчёт соответствующего отчёта | Полностью сохранённый период не загружается заново |
| Изменены газ, профиль, тариф или отзыв | Данные и необходимость публикации сохраняются вместе | HTTP-ответ не ждёт полного анализа и обновления HTML |
| Пользователь задал вопрос или запросил пересоздание отчёта | В БД регистрируется задание; перед анализом загружаются нужные данные | Обычный просмотр страницы не запускает ZONT или AI |
| Наступил срок проверки моделей AI | Выполняется отдельное задание либо проверка срока при дневном запуске | Каждый HTTP-запрос не создаёт новый фоновый поток |

Расписание учитывает часовой пояс дома, переходы времени и пропущенные периоды.
Внутренняя загрузка истории является частью задания отчёта; отдельного таймера
синхронизации не будет. При отказе источника предыдущая публикация остаётся доступна.

Задания и необходимость их отправки сохраняются в БД вместе с изменением данных.
После записи отправляется сигнал обработчику. Повторный сигнал относится к тому
же заданию и не создаёт дубликат. Редкая проверка восстановления находит задания,
для которых сигнал потерялся. Выбор между асинхронным вызовом платформы и очередью
будет сделан по надёжности доставки и стоимости; отдельные микросервисы пока
не требуются. Локального потока недостаточно: после ответа платформа может
приостановить процесс.

### Ограничения времени и повторных попыток

Предлагается HTTP-сервер на порту из `PORT`. Таймер платформы вызывает его напрямую.
Один запрос выполняет ограниченную порцию работы и возвращает ответ; живой процесс
может обслужить следующий запрос. Постоянно работающий процесс с внутренним
ожиданием между циклами в облаке не используется. Заранее запущенных экземпляров — 0.

Начальная настройка: одна одновременно выполняемая операция и небольшой лимит
экземпляров. Этого недостаточно для защиты от повторной доставки: право на
выполнение задания всё равно должно захватываться в БД.

Предложенный предел запроса — 300 секунд: 30 на запуск и настройки, до 240 на работу,
30 на сохранение результата и ответ. Это плановые значения для проверки в M1–M2,
а не результаты измерений. Проверки M1 выполняются вручную, не дольше 60 секунд,
без рабочего расписания и обращений к ZONT или AI.

| Операция | Предлагаемое ограничение |
| --- | --- |
| ZONT | Подключение до 5 секунд, запрос до 30; повторы и паузы только в пределах оставшегося времени задания |
| Генерация AI | Подключение до 5 секунд, весь вызов до 120; автоматических повторов нет |
| Каталог моделей | До 15 секунд на запрос |
| БД и облачные сервисы | До 10 секунд на попытку, не более двух повторов и только в пределах общего времени |

Новая порция работы не начинается, если на неё и сохранение результата уже
не хватит времени. Дозагрузка делится по устройствам, рядам и интервалам.
Длинные отчёты и проверка моделей продолжаются из сохранённого состояния.
Числа уточняются измерениями M2–M3.

Сейчас клиент ZONT делает до трёх попыток с ожиданием `Retry-After` до 60 секунд
между ними, без общего предела времени. OpenAI уже использует 120 секунд
и `max_retries=0`. Проверка моделей и пересоздание отчёта запускают локальные
потоки. Эти отличия нужно устранить до подтверждения в M4 работоспособности
нового cloud-only приложения на YDB.

## Какие данные нужно перенести без потерь

Ниже перечислены существующие таблицы, включая объявленные вне SQLite-модуля.
При переносе сохраняются идентификаторы, связи, история изменений и аудит.
Расчёты должны получать обычные объекты приложения и ограниченные порции данных
с устойчивой позицией продолжения. Запросы SQL, сессии SQLAlchemy и детали YDB
должны оставаться внутри кода работы с конкретной БД.

Названия интерфейсов в скобках — ориентиры для реализации M4.

| Данные и будущий интерфейс | Текущие таблицы | Что обязательно сохранить |
| --- | --- | --- |
| Оборудование и настройки (`CatalogRepository`) | `devices`, `entities`, `config_snapshots`, `telemetry_series` | Поиск и обновление устройств, снимки настроек, роли и происхождение значений; ключи устройств и источников не меняются |
| Измерения (`TelemetryRepository`) | `telemetry_samples`, `ingestion_cursors`, `data_gaps`, `source_events` | Пакетную запись и удаление без дубликатов при повторе; числовые и текстовые значения и качество; позицию загрузки только после записи; версии поздних данных и различение пустых, неполных и невосстановимых интервалов |
| Отчёты (`ReportRepository`) | `analysis_periods`, `metric_values`, `detected_events`, `reports` | Совместное сохранение всех частей отчёта, поиск последнего и предыдущего завершённого, обновление служебных отметок с проверкой версии; историю AI и исходные поля |
| Рекомендации и обратная связь (`FeedbackRepository`) | `recommendations`, `interventions`, `intervention_experiments` | Статусы, отзывы, историю действий и ручные эксперименты; согласованную запись статуса, действия и снимка |
| Профиль и газ (`OwnerRepository`) | `owner_profile_revisions`, `gas_readings`, `gas_meter_boundaries`, `gas_reading_audit` | Историю профиля и происхождение ручных/автоматических значений, дату показания и её перенос, периоды разных счётчиков; проверку и аудит вместе с записью, запрет перезаписи занятой даты |
| Тарифы (`TariffRepository`) | `gas_tariffs`, `gas_tariff_audit` | Историю по области действия и месяцу начала, цену и валюту; запись с аудитом без подмены исторических настроек |

| Проверка моделей (`ModelReviewRepository`) | `model_review_state`, `model_review_runs`, `model_review_proposals` | Сроки, захват задания, результаты, предложения и решения; применение предложения вместе с новой версией настроек AI |
| Задания и расходы (`JobRepository`, `UsageRepository`) | `jobs`, `llm_calls`, `notification_outbox` | Учёт вызовов и очередь уведомлений; добавить защиту от повторов, право выполнения задания и состояние неизвестного результата внешнего вызова — сейчас `jobs` для захвата не используется |
| Версии и публикации (`RevisionRepository`, `PublicationRepository`) | `app_meta`, `publication_changes` | Признаки изменения периода, служебные данные, объединение повторных изменений в журнале, чтение порциями и отметку прогресса публикации без потерь при одновременной работе |

### Форматы данных и проверка точности

Физические типы YDB проверяются в M3: после записи и обратного чтения значения
должны совпасть с исходными.

| Значение | Сейчас в SQLite | Требование к YDB |
| --- | --- | --- |
| Строковый идентификатор, ключ или вариант значения | `String` / `TEXT` | `Utf8`, без изменения регистра, префиксов и существующих идентификаторов |
| Время измерения в секундах UTC | `Integer` | `Int64`; единица остаётся секундой; чтение интервала включает начало, но не конец: `[start,end)` |
| Точное время записи или действия | SQLAlchemy `DateTime`, приведённое к UTC | `Timestamp` либо целое число микросекунд; выбрать после проверки обратного чтения без потери точности |
| Местный день или месяц | Строка ISO | `Utf8` с прежними проверками; часовой пояс дома хранится отдельно, местная полночь не заменяется полуночью UTC |
| Объём газа и денежная цена | Точное десятичное число `Decimal` в строке | `Utf8` с прежними точностью и округлением; не приближённый `Double` |
| Измерение | Число или текст, возможно отсутствие значения | Необязательные `Double` / `Utf8`; отсутствие значения, пустая строка и ноль остаются разными; качество сохраняется |
| JSON | Сериализованный `TEXT` | `Utf8` с прежним представлением; контрольные суммы считает приложение, преобразование JSON средствами БД их не меняет |
| Логическое значение | SQLAlchemy `Boolean` | `Bool`, без неявного преобразования в строку |
| Порядковый идентификатор или версия | Автоматически возрастающий `Integer` | Сохранить старые числа; новые `Int64` выдавать согласованно внутри транзакции, версии должны возрастать |

Контрольная сумма периода, в коде `fingerprint`, зависит от порядка строк.
Он задаётся явно: сначала `series_id`, затем `timestamp`. Сохраняются версии
алгоритма, обозначение пустого периода и правила для старых служебных отметок.
Версия настроек указывает, с какими настройками получен результат; версия
публикации отмечает, до какого изменения обработан журнал.

Поэтому нельзя просто заменить числовые идентификаторы случайными UUID.
Выдача новых номеров и запись журнала могут создавать конкуренцию за одни данные;
нагрузку и повтор транзакций нужно проверить в M3.

### Какие изменения должны сохраняться вместе

- Сохранение отчёта (`save_report`) включает период, метрики, события, рекомендации,
  уведомления и отметку о необходимости публикации. Всё сохраняется либо целиком,
  либо никак. Сейчас журнал обновляют триггеры SQLite; код YDB должен делать это явно.
- Изменение газа, профиля, тарифа или решения по AI включает чтение текущего
  значения, проверку, запись и аудит. Между ними другой запрос не должен незаметно
  подменить данные. Нужна транзакция с последовательным результатом либо запись
  с проверкой, что прочитанная версия ещё актуальна.
- Право выполнять задание выдаётся вместе с уникальным ключом задания, владельцем,
  сроком действия и номером попытки. Завершение и отметку прогресса может записать
  только текущий владелец. Это защищает БД, но само по себе не гарантирует
  единственный внешний вызов AI.
- Автоматический повтор транзакции БД не должен повторять HTTP-запрос или публикацию.
  Внешний вызов отдельно проходит состояния «подготовлен», «отправлен»,
  «успешен», «ошибка» или «результат неизвестен». При неизвестном результате
  требуется сверка или решение, а не новая генерация из-за таймаута.
  Этот порядок предстоит реализовать в M4; текущего `llm_calls` недостаточно.
- Настройки SQLite (`BEGIN IMMEDIATE`, WAL, PRAGMA), её синтаксис записи,
  автоинкремент, внешние ключи, каскадное удаление и триггеры не переносятся буквально.
  YDB должна обеспечить те же гарантии. Где нет равнозначного ограничения БД,
  уникальность и целостность проверяются в транзакции. Приёмка проверяет отсутствие
  записей, потерявших связанные данные.

Сейчас прямые SQLAlchemy-запросы есть и в коде профиля, тарифов, настроек AI
и проверки моделей. `incremental_publication.py` тоже читает таблицы напрямую.
В M4 эти обращения нужно перенести за общие интерфейсы. Замены одного класса
`Database` недостаточно.

При чтении конец интервала исключается: `[start,end)`. При загрузке ZONT сейчас
принимается также точка `timestamp == end`, а повторная запись этой точки
не создаёт дубликат. На стыках окон нужно сохранить полноту и проверить границы
отдельно; нельзя механически обрезать ответ источника правилом чтения из БД.

Пути ниже дополняют настраиваемый префикс API, сейчас `/api`.

Сохраняются коды HTTP, проверки входных данных и правила обращения форм к тому же
сайту. Приложение принимает сведения о вошедшем пользователе только от доверенного
входного сервиса, а не из произвольного заголовка браузера.

Сейчас вход по логину и паролю обеспечивает внешний веб-прокси. При прямом вызове

поэтому текущую схему nginx нельзя считать готовой к переносу без проверки.

в закрытый контейнер и отсутствие обхода через служебный адрес контейнера
или бакета. Выбор сервиса не отменяет обязательность всех функций сайта.

## Как приложение обращается во внешнюю сеть

Требование относится к HTTP-клиентам приложения: они должны соблюдать выбранные
маршруты и список разрешённых адресов. Защита от произвольного сетевого кода
в скомпрометированном контейнере в эту задачу не входит. Подключение к VPC само
по себе [не отключает интернет](https://yandex.cloud/en/docs/serverless-containers/concepts/networking).
Это уточняет [сетевые требования общего плана](./cloud_first_milestone.md#контракт-проксирования-и-контроля-трафика).

| Назначение | Маршрут |
| --- | --- |
| ZONT, `my.zont.online:443` | Напрямую |
| Генерация и метаданные OpenAI, `api.openai.com:443` | Через выбранный прокси |
| Каталог моделей, `developers.openai.com:443` | Через выбранный прокси |
| YDB, Object Storage, Lockbox, мониторинг и получение служебных прав доступа | Напрямую, только к явно разрешённым адресам окружения |
| Остальные адреса | Запрещены |

Перенаправление на другой адрес проверяется заново. Переменные окружения,
включая `NO_PROXY`, не должны незаметно менять эти правила. Если обязательный
прокси недоступен, запрос завершается ошибкой без прямого подключения.

Приложение подключается к локальному Xray через HTTP CONNECT — запрос на создание
туннеля к нужному API. Xray использует выбранное соединение VLESS/XHTTP/REALITY
с внешним сервисом. Проверка TLS-сертификата целевого API остаётся в HTTP-клиенте
приложения. Локальный порт доступен только внутри окружения приложения.
Параметры подключения приходят из приватных настроек и Lockbox; содержимое
секретов не записывается в Terraform.

Существующая конфигурация проверена без изменений: параметры нужного транспорта
и HTTP/SOCKS-входы найдены. Совместная работа приложения и Xray в облаке ещё
не проверена. В M1 нужно проверить их запуск, готовность порта, остановку,
восстановление, потребление памяти и влияние на время запуска и стоимость.
На тестовых адресах проверяются запреты, перенаправления и отказ туннеля.
Если совместная работа или ограничения не подтверждаются, зависимые проверки
останавливаются до согласования исправления.

### Обслуживание и восстановление соединения

Владелец сопровождает существующий внешний сервис; исполнитель настраивает клиент,
проводит короткую проверку и диагностирует приложение. Новый сервер для этого
не создаётся. Стоимость существующего сервиса учитывается отдельно от Yandex Cloud.

При отказе туннеля задание AI сохраняется как завершившееся ошибкой либо как задание
с неизвестным результатом — по фактическому исходу. Старый отчёт остаётся доступен,
ZONT продолжает использовать прямой маршрут. После восстановления автоматически
повторяются только безопасные задания с известным исходом; неизвестный исход
требует сверки.

Для восстановления нужны приватная копия конфигурации, ссылки на секреты,
проверенный образ клиента и короткая повторная проверка. Начальные ограничения M1:
не более четырёх CONNECT-соединений на экземпляр, до 5 секунд на подключение,
общий срок задания и настраиваемый предел переданных байтов на соединение и задание.
Предел байтов выбирается на искусственных данных до включения реального API.
Его превышение завершает вызов ошибкой без обхода прокси.

В журнале на семь дней сохраняются только адрес назначения, разрешение или запрет,
длительность, число байтов и результат. Тела запросов и секреты не записываются.
Отсутствие нужного ограничения или возможности восстановления блокирует дальнейшие
проверки зависимого API.

### Что подтверждено по доступу к OpenAI

Владелец 2026-09-14 сообщил, что имеет подтверждение OpenAI для выбранной схемы
доступа. Предварительное условие M0 закрыто на основании этого сообщения;
исходный ответ провайдера исполнителю не предоставлялся и независимо не проверялся.
При изменении схемы условия нужно проверить повторно, в том числе по
[официальному списку поддерживаемых стран](https://developers.openai.com/api/docs/supported-countries).

Это не проверка реального соединения или авторизации. В M2 сначала проверяются
DNS, TLS и маршрут без ключей, затем выполняется не более одного запроса
с авторизацией за пользовательскую итерацию. В M0 запросы к OpenAI не выполнялись.

| [Исходящий трафик](https://yandex.cloud/ru/docs/vpc/pricing) | 1,42 руб./GiB; из Object Storage — 1,67994 руб./GiB в первом платном диапазоне | Отдельно выдача сайта, скачивание копий и внешние запросы контейнера |

[Certificate Manager](https://yandex.cloud/ru/docs/certificate-manager/pricing)
в использованном расчёте не добавляет платы. DNS остаётся у внешнего провайдера;
новая облачная зона не требуется. Дополнительные виртуальные машины, NAT-шлюз,
балансировщик и CDN в выбранную схему не входят. Их включение, рост числа версий
секретов и образов или объёма данных требуют предварительного пересчёта.

Удвоенный сценарий не является верхней границей счёта. Реальные операции YDB
и размер индексов измеряются в M3, память и время работы приложения с Xray —
в M1–M2. До создания ресурсов задаются лимиты экземпляров и параллельных запросов,
нагрузки и объёма YDB, хранения логов и уведомления о расходах из приватных настроек.
Уведомления и квоты не гарантируют остановку всех списаний: хранение, версии
секретов и ключей и проверки оповещений оплачиваются и в простое.

## Как подготовить инфраструктуру и сохранить приватность

Terraform описывает облачные ресурсы в коде. Его файл состояния хранит сведения
о созданных ресурсах, поэтому он приватный. Первичная подготовка создаёт хранилище
этого состояния и права доступа до развёртывания самого приложения.
Все требования ниже относятся к будущей реализации M1.

### Что можно хранить в публичном репозитории

| Место | Содержимое |
| --- | --- |
| Git: файлы `.tf`, сценарии CI, примеры | Описание ресурсов, имена и типы параметров, проверки и безопасные заглушки; без личных значений по умолчанию |
| GitHub Environment Variables | Разрешённые к раскрытию настройки: регион, лимиты ресурсов и контрольная сумма публичного образа |
| GitHub Environment Secrets | Приватные идентификаторы и имена облака и каталога, адреса прокси, имя бакета состояния и необходимые учётные данные |
| Приватное хранилище состояния Terraform | Реальные идентификаторы, адреса и связи ресурсов; шифрование, ограниченный доступ, версии и блокировка записи |
| Lockbox | Секреты приложения; Terraform создаёт места хранения и ссылки, но не читает значения секретов в своё состояние |

CI передаёт приватные настройки через переменные окружения `TF_VAR_*`, а не
вставляет их в команды оболочки, аргументы или отслеживаемые `.tfvars`.
Соответствующие входы и выходы помечаются `sensitive = true`. Созданные облаком
идентификаторы берутся из ссылок Terraform и его состояния. Если они нужны
другому развёртыванию, передаются защищённым способом.

Настройка хранилища состояния передаётся при `terraform init` из приватного
временного файла; блок `backend` не умеет читать обычные переменные Terraform.
Доступ задаётся поддерживаемыми средствами окружения или служебной учётной записи.
Каталог `.terraform/`, реальные `.tfvars`, настройки хранилища, состояние
и сохранённые планы не включаются в Git. Файл `.terraform.lock.hcl` с версиями
и контрольными суммами провайдеров, напротив, отслеживается.

Метка `sensitive` скрывает обычный вывод, **но не удаляет секретные значения
из состояния или плана**. Маскирование GitHub Secrets тоже не скрывает надёжно
все производные значения. Полный вывод `plan/apply/show/output`, JSON состояния
и плана и диагностические трассы остаются в приватном файле или хранилище.
В открытые логи, комментарии PR и файлы CI попадает только проверенная сводка
без приватных адресов и идентификаторов.

Реальные секреты, планы и состояние доступны только доверенному процессу
развёртывания. Проверки чужого кода из PR не получают их. Настройка GitHub
Environments, ограничения запуска и доступ к приватным результатам проверяются
до первого настоящего плана M1; сейчас они этим документом не считаются настроенными.

Источники: [секретные данные Terraform](https://developer.hashicorp.com/terraform/language/manage-sensitive-data),
[настройка хранилища состояния](https://developer.hashicorp.com/terraform/language/backend),
[секреты GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

### Хранение состояния и разделение прав

Для состояния Terraform выбран отдельный закрытый S3-бакет с историей версий
и шифрованием ключом KMS (`SSE-KMS`). Этот бакет, ключ шифрования и состояние
первичной подготовки не удаляются при удалении ресурсов приложения.

Первичная подготовка выполняется локально в Docker с приватной учётной записью:
каталог проекта, бакет состояния, ключ шифрования и служебные учётные записи
создаются или, если уже существуют, принимаются под управление. Начальное локальное
состояние с правами `0600` переносится в отдельный объект подготовленного
хранилища; защищённая копия сохраняется. Права первичной подготовки не передаются
обычному процессу развёртывания приложения.

От одновременной записи защищает `use_lockfile = true` в S3-настройках Terraform.
Ограничение параллельных запусков GitHub дополняет, но не заменяет эту блокировку.
Выбор основан на [блокировке S3 в Terraform](https://developer.hashicorp.com/terraform/language/backend/s3)
и [условной загрузке объекта в Object Storage](https://yandex.cloud/ru/docs/storage/s3/api-ref/object/upload).
Совместимость ещё нужно доказать в M1 на закреплённой версии Terraform:
запустить два конкурирующих клиента, проверить освобождение после сбоя
и восстановление предыдущей версии состояния. При провале создание ресурсов
останавливается; блокировку нельзя отключить ради продолжения.

Обычное развёртывание использует краткоживущий IAM-токен через
[федерацию служебных удостоверений](https://yandex.cloud/en/docs/iam/concepts/workload-identity):
облако выдаёт права строго определённому окружению GitHub. У этой учётной записи
права ограничены каталогом проекта. Доступ к S3-состоянию проверяется отдельно:
выбранный способ авторизации должен поддерживаться Terraform и давать доступ
только к нужным объектам состояния, блокировки и ключу KMS. Если потребуется
постоянный S3-ключ, он создаётся вне состояния Terraform, передаётся приватно
и регулярно заменяется.

Учётная запись работающего приложения не читает состояние Terraform и секреты
развёртывания. Фактическое разделение прав проверяется в M1. Образы хранятся
в Yandex Container Registry: туда копируется уже проверенный образ без пересборки,
после чего сверяется его контрольная сумма. Значения секретов загружаются отдельно
от Terraform.

### Домен и HTTPS

Для стенда выбран отдельный поддомен; его значение хранится приватно.
DNS остаётся у текущего провайдера. Для API Gateway нужны CNAME на служебное
имя шлюза и выданный сертификат Certificate Manager со статусом `Issued`.
Перенос всей DNS-зоны не требуется.

В M1 исполнитель подготавливает фактические записи для маршрутизации
и подтверждения владения доменом. Владелец вносит их в панели DNS-провайдера;
конкретные значения передаются приватно. Terraform управляет облачными ресурсами
и привязкой домена. После выпуска сертификата проверяются DNS, HTTPS, вход на сайт
и невозможность обойти его через прямые служебные адреса или бакет.

Инструкции: [домен API Gateway](https://yandex.cloud/ru/docs/api-gateway/operations/api-gw-domains),
[подтверждение домена для сертификата](https://yandex.cloud/ru/docs/certificate-manager/operations/managed/cert-validate).

### Как будет устроен возможный откат

Для M8 предлагается не менее 14 последовательных дней нормальной работы
с проверкой дневного, недельного и представительного длинного отчёта, сохранности
пользовательских данных и AI, резервного копирования и восстановления. До cutover
записывает только старый VPS, после cutover — только cloud.

До включения записи возврат возможен на замороженный старый production. Если в cloud
уже появились новые записи, основной путь восстановления — совместимый cloud-релиз
с сохранением данных YDB. Возврат на старый VPS допускается только после отдельной
проверки импорта этих записей; нельзя потерять записи после переключения. Старые
копии и образы сохраняются отдельно, а приложение и ресурсы VPS после наблюдения
останавливаются и удаляются без затрагивания других сервисов и внешнего egress.
В новом приложении SQLite не используется, поэтому отдельной поздней вехи для его
удаления нет.
