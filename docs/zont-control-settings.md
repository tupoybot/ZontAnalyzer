# Время дневного отчёта и настройки регулирования

Статус: кандидат в `stage9/report-delay-control-settings`, локальные проверки и CI пройдены;
выпуск HK остановлен из-за тайм-аутов healthcheck, возвращён прежний образ;
worker прежней версии восстановился, Docker healthcheck остаётся `unhealthy`.
Решение владельца: 2026-09-13.

## Дневной отчёт после поступления запоздавших данных

Первый автоматический отчёт за вчера формируется в первом успешном цикле worker
после **01:00 по часовому поясу дома**. Параметр
`pilot.daily_report_delay_minutes` задаёт задержку от местной полуночи; по умолчанию
60 минут, допустимо 0–1439. Полночь по UTC не задаёт границу суток объекта.

До границы времени синхронизация продолжается; доступен предыдущий опубликованный
отчёт. Если отчётов ещё нет, ожидание считается штатным состоянием worker.
Недельный/месячный/сезонный планировщик также ждёт эту границу в цикле worker,
чтобы не использовать незавершённый сбор последнего дня раньше дневного отчёта.
Ручной запуск анализа не ограничен этим расписанием. Перезапуск worker и повторный
цикл не создают повторный AI-вызов для уже сохранённого дневного отчёта.

В проверенном отчёте за 12 сентября AI был готов в 00:06:38, поздние точки за
23:51 поступили в 00:12:44, пересчёт завершился в 00:13:48. На изолированной копии
восстановлен исходный fingerprint AI: различались только семь счётчиков точек.
Владелец выбрал часовую задержку вместо расширения механизма сравнения.
`facts-v2`, сохранение прежнего AI и предупреждение при последующих изменениях
сохраняются. Задержка не гарантирует отсутствие данных, пришедших через час или позже.
Существующее предупреждение и исходный текст AI не удаляются задним числом.

## Подтверждённый контракт ZONT

Приложение читает `devices.z3k_config`. Раньше оно передавало коэффициенты и сырую
кривую, но безусловно объявляло способ регулирования и кодировку неизвестными.
Контракт `zont-controls-v1` расшифровывает эти поля по публичному клиенту производителя.

Первичные источники, проверены 2026-09-13:

- [Публичный демонстрационный интерфейс ZONT](https://my.zont.online/demo).
- [Код клиента, модуль HeatingCircuit NJx5](https://my.zont.online/webpack-beta/zont/vendor-796890.js):
  тип контура, маска способа регулирования, флаги выключения и применения ПЗА.
  SHA256: `38a09fc017a5a1e44963cfc451fa862681b5ddfaab79f43e270eb170940445b9`.
- [Source map клиента](https://my.zont.online/webpack-beta/zont/app-d5f256.js.map):
  `settings/pza-pane/index.tsx` использует `dk2g/g2dk` для координат;
  `circuits/additional-params/pid-koef.tsx` показывает P/I напрямую,
  стандартные значения 10/1, без второй конвертации.
- [Source map утилит производителя](https://my.zont.online/webpack-beta/zont/vendor-796890.js.map):
  `@microline/utils/dist/temperature.js`, перевод координат в °C: `(raw - 2730) / 10`.
- [ПЗА: документация производителя](https://support.microline.ru/index.php/ПЗА):
  при регулировании по воздуху с ПИД кривая ограничивает расчётную температуру.

| Поле | Интерпретация |
| --- | --- |
| `heating_circuits.type == 3` | Отопительный контур; код типа сам по себе не означает PID |
| `setting_register & 3` | 0 — по воздуху, 1 — по воздуху с ПИД, 2 — по теплоносителю; 3 не расшифровываем |
| `setting_register & 64` | Контур отключён в настройках |
| `setting_register & 128` | Для режима по теплоносителю: ПЗА только для запроса тепла |
| `pza` | Ссылка на кривую; 0, 255 и null означают отсутствие назначенной ПЗА |
| `pzas[].x/y` | Координаты наружной температуры/теплоносителя в кодировке производителя |
| `pid_prop_koef`, `pid_integral_koef` | Числа, показанные в настройках ZONT; физические единицы и безопасное направление изменения не выводятся из названия |

Декодируются только конечные числовые данные; неизвестные режимы, некорректные
регистры, дублирующиеся кривые, неподходящие диапазоны и немонотонная наружная ось
остаются явно нерасшифрованными. Сырые координаты и источники сохраняются.

Для проверенного контура `20496`: `type=3`, `setting_register=2561` означают
**«По воздуху с ПИД»**, контур включён в настройках. Кривая `8259` используется
как ограничитель расчётной температуры PID. P=10, I=1. Все семь точек совпали
с предоставленным владельцем интерфейсом ZONT:
20→30; 10→34,2; 0→38,4; −10→45,1; −20→50,4; −30→54,2; −40→56,4 °C.
Это подтверждённая конфигурация снимка, не доказательство работы горелки.

## Отчёт и AI

- `control_settings.regulation` содержит расшифрованный способ регулирования,
  включение в настройках и роль ПЗА; `pza_curve.points_c` — координаты в °C.
- Промпт `analyst-v8.4` использует известные значения, учитывает совместную работу
  PID и ПЗА и не запрашивает повторное подтверждение уже переданных параметров.
- Текущий снимок не доказывает неизменность настроек за весь исторический период.
  Наличие запроса тепла и доступность отопления оцениваются отдельно по телеметрии.
- Право/уместность изменения сервисного параметра отделены от знания его значения.
  Приложение не выполняет запись в ZONT и не выдумывает настройку «наклон/смещение»
  для табличной кривой. Направление настройки PID требует отдельного обоснования.
- HTML и текст показывают известные настройки. Время снимка и интервалы AI
  отображаются в часовом поясе отчёта; мгновенная ссылка только на настройки
  обозначается временем снимка, а не нулевым интервалом. Для новых AI-ответов
  мгновенные ссылки на настройки одного контура получают точное время из
  переданного снимка: модель не вычисляет часовой сдвиг этого факта.
- Старые AI-ответы сохраняются. Новые поля и промпт применяются при следующем
  анализе; выпуск сам не запускает массовый исторический пересчёт.

Локально: финальный полный прогон **646 тестов**, Ruff, mypy, wheel/sdist прошёл,
включая регрессию привязки времени снимка. Браузерный архив, Basic Auth и обе

Новый блок проверен в Chromium при ширине 1280 и 390 px; семь строк кривой,
горизонтальной прокрутки на мобильной ширине нет.

Online-копия: `/tmp/zont-diagnostic-20260913/snapshot.sqlite3`; отдельная рабочая
копия `working.sqlite3`. Новый анализ сохранил метрики, события и качество;
155 отчётов и 39 AI-записей остались неизменны. В пакет целиком вошли 5570 байт
настроек с `air_pid`, `upper_limit` и семью точками.

Один реальный локальный вызов `analyst-v8.4` успешен: модель правильно назвала
PID с ограничивающей ПЗА, коэффициенты/кривую не объявила недоступными.
На сохранённом ответе без второго запроса проверена привязка времени снимка:
04:24:50 UTC → 08:24:50 по Самаре. В пробном ответе обнаружено также ошибочное
присвоение местного смещения обычным AI-интервалам и неоднозначное название дат
в summary; инструкция сохранения исходных UTC-меток уточнена, но устойчивость
этого поведения требует следующих штатных ответов. Эти интервалы не исправляются
