# Дата снятия показания газа

Статус: в работе, расширение незакрытой ветки `stage9/gas-save-background`.
Выбор даты дополняет [быстрое сохранение](./gas-save-background.md); прежний релиз
не считается принятым и ветка не сливается в `main` без приёмки владельца.

## Контракт

- В форме дневного отчёта задаются накопленное показание и календарная дата снятия.
  На выбранную дату может не существовать отчёта. Поле времени не добавляется —
  это явно исключено владельцем 10 сентября 2026.
- Для нового показания обычный отчёт подставляет свою дату; последний доступный
  завершённый дневной отчёт определяется API и подставляет текущую локальную дату
  браузера. Это работает и для `latest.html`, и для прямого адреса отчёта. При
  недоступности API и в offline HTML безопасная исходная дата — дата отчёта.
- Редактирование всегда использует сохранённую дату. «Новое показание» создаёт
  независимую запись; история позволяет выбрать старую. Изменение даты редактора
  переносит выбранную запись при сохранении, сохраняя её id и исходное время ввода.
  Аудит хранит обе даты. Конфликт с другой записью не перезаписывает её.
- Сохраняется ограничение одного показания на день. Перенос самой границы замены/
  сброса счётчика отклоняется: без отдельного редактирования границ нельзя незаметно
  изменить принадлежность остальных показаний участкам учёта. Удаление показания
  сохраняет существующую границу, как и раньше.
- Ошибки сохраняют введённые дату и значение; загрузка не перезаписывает ввод во
  время запроса. Удаление относится к выбранной сохранённой записи, даже если дата
  в редакторе изменена и ещё не сохранена.

## API и расчёт

`GET /reports/{id}/gas?day=YYYY-MM-DD` выбирает календарный день; без параметра
используется дата отчёта. Ответ содержит `report_day`, `selected_day`,
`is_latest_report`, текущую запись, список показаний установки и аудит выбранного дня.
`PUT` принимает `day`, `reading_id`, значение либо удаление. `reading_id: null`
означает создание без перезаписи; строковый id — исправление/перенос существующей
записи. Старые клиенты без этих полей сохраняют прежний контракт по дате отчёта.

Схема БД не меняется: используется существующий `reading_day`. Существующие записи
не переименовываются автоматически. Владелец отдельно разрешил исправить 1929 м³
с 9 на 10 сентября; это будет одна обычная аудируемая коррекция после deployment.

Модель расхода уже использует `reading_day`. Проверка должна доказать, что две
записи из одного отчёта образуют интервал между выбранными датами, а перенос даты
меняет калибровочный интервал и версию модели, сохраняя сам объём разности. Точное
время не выдумывается: условный полдень и неопределённость внутри суток сохраняются.

## Проверки и выпуск

Будут зафиксированы после интеграции: Docker, браузер, онлайн-копия БД, immutable
образ, bounded HK smoke и разрешённый перенос показания 1929 м³ на 10 сентября.
