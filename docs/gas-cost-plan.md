# Стоимость газа — план доработки 9.1

Статус: реализован и развёрнут из ветки `stage9/gas-cost`, ожидает принятия владельцем. Требования владельца от 2026-09-07,
включая уточнения о календарных месяцах и отображении стоимости без подписи «оценка».
Стоимость — детерминированное умножение существующего объёма на действующий тариф.
Модель расхода, её источники, калибровка и надёжность сохраняются.

## Настройки и история

- Рядом с показанием газа показывать цену за м³ и кнопку изменения цены/валюты;
  не убирать тариф в настройки. Валюта по умолчанию — RUB (рубли).
  Тестовое значение **8,01 RUB/м³**, не молчаливый тариф для реальных пользователей.
- Хранить в SQLite историю тарифов по объекту/счётчику: цена, код валюты, начало
  действия, время записи и аудит исправлений. Точная схема определяется при реализации
  по существующему контракту показаний; это отдельные данные от накопленного объёма.
- Изменение тарифа создаёт новую временную версию, не заменяет старую. Настройки
  рядом с показанием показывать месяц начала действия; историческую цену можно внести явно, выбрав месяц.
  Новая цена не распространяется назад автоматически. Исправление старой ошибки —
  отдельное явное действие с аудитом и пересчётом только затронутых периодов.
- Интервал тарификации — календарный месяц в часовом поясе объекта. Обычное
  изменение цены в середине месяца действует со следующего месяца. Тариф сохраняется
  до следующей месячной версии; произвольные даты и интервалы не поддерживаются.
- При нескольких изменениях в течение месяца действует последнее сохранённое значение
  для следующего месяца. Предыдущие значения остаются в аудите; одинаковое повторное
  сохранение не создаёт лишних изменений.
- Цена и валюта действуют вместе во времени: смена валюты не переименовывает старые
  суммы и не является конвертацией. Не складывать разные валюты в одно число;
  показывать их раздельно, без неявного обменного курса.
- Денежные вычисления — decimal либо фиксированная точность, без накопления ошибок
  float; округлять итог для отображения до двух знаков. Принимать запятую в `8,01`,
  запрещать отрицательные/нечисловые цены; нулевой тариф допустим.

## Расчёт и отчёты

Для периода P: `стоимость(P) = Σ объём(P ∩ интервал_тарифа) × цена_интервала`.
Разрезать период только по месячным границам действия тарифов в часовом поясе объекта.
Никаких выдуманных промежуточных показаний: для разрезания использовать существующую
временную оценку расхода с её признаками качества. Если точного распределения нет,
сохранить происхождение расчёта в данных; если распределение недоступно, показать неполноту суммы.
До первого известного тарифа стоимость неизвестна, а не нулевая. Не выдавать
известную часть за полную стоимость периода.

- Основной дашборд: стоимость рядом с общим расходом, например `1,08 м³ · 8,65 руб.`
  (иллюстрация по округлённому объёму; расчёт использует исходную точность).
- Стоимость показывается без подписи «оценка»: приложение не рассчитывает платёж
  по квитанции. Отдельные пояснения нужны только при неполноте или отсутствии данных.
- «Подробные метрики» → «Газ»: деньги через разделитель `·` рядом с общим объёмом.
  Распределение по отоплению, ГВС и неопределённому назначению — только объёмы и доли,
  без денег, включая легенду дашборда.
- «Экономия газа»: `1,00 м³ · 8,01 руб.`; денежная оценка наследует достаточность
  данных, направление эффекта и оговорки существующей оценки экономии.
- Дневные, недельные, месячные и сезонные HTML/JSON и текстовые отчёты используют
  один расчёт и согласованное форматирование валюты; desktop/mobile без переполнения.

Сравнивать расход и стоимость с прошлыми аналогичными периодами средствами уже
существующей аналитики сопоставимости: погода/градусо-часы, отопление отдельно от
ГВС, режим, комфорт и покрытие. Погода не корректирует фактически потраченные деньги.
Показывать реальные исторические суммы по их тарифам, а погодонормализованный эффект —
отдельно. Денежный эквивалент разницы объёмов считать в тарифах оцениваемого периода,
указывая это основание. Изменение цены не называть экономией газа. Для смешанных
тарифов применять соответствующие интервальные веса; при недостатке данных или
несопоставимых валютах не показывать необоснованный денежный итог сравнения.

## Приёмка 9.1

1. При тарифе 8,01 RUB/м³: 1 м³ = 8,01 руб., 10 м³ = 80,10 руб.; нулевая цена работает.
2. Смена на 9 RUB/м³ сохраняет прежний итог; период из 1 м³ до смены и 2 м³ после
   стоит 26,01 руб. Граница месяца, изменение цены в середине месяца,
   повторное сохранение, перезапуск и повторная
   публикация не меняют историю тарифа.
3. Покрыть отсутствие тарифа, частичное покрытие, смену валюты, явное исправление,
   миграцию существующей БД без потери показаний и пользовательских данных.
4. Проверить аналогичные периоды с одинаковой/разной погодой и изменением цены:
   рост тарифа не становится ухудшением эффективности; нет данных — нет выдуманного сравнения.
5. Проверить все места отображения, типы отчётов и desktop/mobile; существующие
   газовые объёмы и надёжность не меняются. Выполнить обычную процедуру релиза.

Связанное уточнение владельца: числовые поля профиля и показания принимают точку
и запятую, проверяются до отправки и на сервере. Некорректный ввод не очищает
сохранённое значение. Сообщение о паспортном максимуме учитывает текущий профиль;
для сравнения старых показаний сохраняется проверка даты применимости параметра.

## Экономия благодаря приложению (отложено)

Отдельная необязательная доработка низкого приоритета, не часть 9.1.
Разность расходов до/после установки сама по себе не доказывает пользу приложения.
Предлагаемый расчёт требует отдельного согласования и проверки на реальных данных:

- Сохранить в БД постоянный `benefit_tracking_started_at` для объекта при явном
  включении учёта эффекта. Он переживает рестарты, релизы и восстановление backup;
  не равен uptime, первой загруженной дате или дате самой старой телеметрии.
  Загруженные 90 дней до старта могут служить базой, но не накопленной экономией.
- Учитывать только подтверждённые владельцем выполненные рекомендации приложения
  после старта. Для каждой хранить связь с экспериментом, дату вмешательства,
  зафиксированную базу и версию метода. Самостоятельные изменения не приписывать приложению.
- Прогнозировать контрфактический расход без вмешательства для фактической погоды,
  режима, использования дома и сопоставимого комфорта. ГВС оценивать отдельно.
  Эффект = прогноз без вмешательства − фактический расход, переведённый в деньги
  по тарифам периода эффекта. Ухудшение комфорта не засчитывать как пользу.
- До реализации определить и проверить пороги покрытия, длительности базы/наблюдения,
  погодной сопоставимости и неопределённости. Пока достаточность не подтверждена,
  в интерфейсе **0** с пояснением «Недостаточно данных», без обещания доказанной экономии.
- Не суммировать перекрывающиеся эффекты экспериментов. При смешанных изменениях
  или неразличимой причинности исключать окно из оценки и показывать ограничение.
  Использовать консервативную оценку эффекта с учётом неопределённости.
- Хранить знаковый накопленный результат, включая убытки. После проверки
  достаточности интерфейс показывает `max(0, суммарный_эффект)`, а не сумму
  положительных дней. Негативные периоды уменьшают общий итог. Разные валюты не смешивать.
- Приёмка обязана покрыть рестарт, backfill, восстановление точки старта, недостаток
  данных, отрицательный итог, перекрытия, изменение тарифа и независимые вмешательства.
  До появления надёжного метода показатель остаётся нулевым и не рекламируется как доказанный.
