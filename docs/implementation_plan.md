# ZontAnalyzer — план реализации

Обновлено: 2026-08-24

Это краткосрочный план работ на следующий цикл разработки ZontAnalyzer. Работы вести в ветке `fix/dhw-analysis-feedback`.

`feature/sensor-aware-pza-analysis` не содержит уникальных изменений и не должен использоваться как база.

## Базовая функциональность, которую необходимо сохранить

Текущая ветка уже содержит работающую функциональность, являющуюся частью базовой версии, а не предметом повторной реализации:

- анализ взаимодействия ГВС и отопления: исторический режим/задание по каждому контуру, эпизоды ГВС, пауза/возобновление отопления, неоднозначные одновременные флаги OT, остаточное тепло и проверки качества;
- доступный только для чтения импорт `raw_events`, сохранение нормализованных `SourceEvent` и анализ надёжности;
- классификация надёжности, отделяющая внутреннюю потерю связи котла/адаптера от потери основного питания и перезапуска ZONT; uptime/MTBF/MTBR и актуальность телеметрии уже доступны отчётам и OpenAI;
- существующая обратная связь по рекомендациям: `applied` / `rejected` и примечание владельца;
- шаблон адаптера OpenAI: строгая схема ответа API отделена от валидации предметной области приложения. Сохранять это разделение при расширении AI-контракта;
- ZONT навсегда остаётся доступным только для чтения. Никогда не добавлять управляющие конечные точки API, инструменты или автоматическое изменение оборудования.

## Архитектурное правило этого цикла: рассуждение прежде всего через AI

До реализации функций обновить раздел 2.1 в `architecture.md`, чтобы он отражал целевой дизайн:

- детерминированный код — надёжный слой данных: обнаружение, нормализация, происхождение данных, проверки качества, временное выравнивание, исключения и простая воспроизводимая математика;
- OpenAI — основной слой рассуждений для многофакторной диагностики, конкурирующих гипотез, прогнозного/контрфактуального анализа и выбора следующего безопасного эксперимента;
- не создавать большую локальную экспертную систему порогов отопления/PZA/гидравлики;
- не отправлять в OpenAI неконтролируемую сырую телеметрию: отправлять ограниченные временные свидетельства, сохраняющие форму релевантной динамики;
- явно сохранять эпистемические уровни: observed → derived → inferred → predicted;
- каждый вывод AI должен ссылаться на переданные свидетельства; прогноз никогда не должен отображаться как измеренный факт.

Это архитектурное обновление документирует уже согласованный дизайн, а не является отдельным этапом реализации.

## Предварительная проверка — подтвердить реальный текущий контракт ZONT

Это короткая обязательная проверка, а не фаза проекта и не основание переделывать существующее приложение.

### Работы

1. Убедиться, что ветка проходит обычные локальные проверки.
2. Выполнить один реальный доступный только для чтения `discover` и небольшую синхронизацию с текущей установкой.
3. Сохранить только обезличенные фрагменты, необходимые для определения:
   - связи контур отопления → датчик контрольной температуры;
   - источника истории радиотермогигрометра и фактических ключей метрик;
   - единицы/формы влажности;
   - идентичности внешнего датчика обратки;
   - полей батареи/RSSI/качества, только если они действительно существуют.
4. Превратить эти фрагменты в тестовые фикстуры.

### Критерии приёмки

- Существующие тесты/линтер/проверки типов/сборка проходят.
- Реальная связь управляющего комнатного датчика с контуром известна из конфигурации, а не угадана по именам или порядку.
- Реальная форма истории радиодатчика известна.
- Ряд внешней температуры обратки идентифицирован.
- Обезличенные фикстуры воспроизводят обнаружение/нормализацию без доступа к работающему ZONT.

Если эти факты уже есть в существующих обезличенных фикстурах, пропустить живое обнаружение и продолжить.

## Этап 1 — Семантика датчиков и импорт нескольких датчиков

### Цель

Научить ZontAnalyzer правильно понимать новые датчики до добавления нового интеллекта.

### Работы

1. Заменить неоднозначное предположение об одной комнате явными семантическими ролями:
   - `control_indoor_temperature` — датчик, фактически связанный с контуром отопления;
   - `room_temperature` — другие жилые комнаты;
   - `technical_temperature` — котельная/нежилые датчики, если это известно;
   - существующие роли наружной температуры/подачи/обратки/ГВС.
2. Усилить существующую логику связи датчика с контуром отопления; связь из конфигурации важнее эвристик по отображаемому имени.
3. Добавить фактический тип истории радиодатчика, обнаруженный на предварительной проверке.
4. Добавить влажность и, только если это полезно и действительно присутствует, качество батареи/сигнала.
5. Сохранять внешнюю температуру обратки отдельно от сообщаемой котлом `rwt`; сохранять источник/происхождение, если присутствуют оба значения.
6. Показывать в контексте отчёта компактные сведения об идентичности/происхождении датчиков.

### Критерии приёмки

- Текущая установка определяет связанный датчик жилой комнаты как контрольный; `Котельная` не используется для анализа комфорта/PZA, если только она явно не связана.
- Беспроводная влажность импортируется с правильной единицей и идентичностью датчика.
- `Обратка` классифицируется как температура обратки с указанием происхождения.
- Неизвестная связь остаётся неразрешённой или отмеченной как имеющая низкую уверенность, а не угадывается.
- Тесты покрывают независимость от порядка датчиков, нормализацию радиоисточника, влажность, датчик обратки и разделение технических/комнатных датчиков.
- Существующие регрессионные тесты ГВС и надёжности остаются зелёными.

## Этап 1.5 — Обратная связь без CLI для P2

### Цель

Закрыть обязательный продуктовый пробел P2: позволить владельцу подтверждать или отклонять рекомендации непосредственно из HTML-отчёта без использования CLI.

Использовать уже существующий жизненный цикл рекомендаций `applied` / `rejected`, примечания владельца и передачу обратной связи в последующие AI-пакеты. Не создавать параллельную модель хранения feedback и не менять read-only границу интеграции с ZONT.

### Работы

1. Добавить в HTML-карточку каждой рекомендации:

   * стабильный идентификатор рекомендации;
   * видимый текущий статус;
   * действие «Выполнено»;
   * действие «Отклонить»;
   * поле комментария владельца;
   * понятное отображение уже сохранённого комментария.

2. Добавить минимальный HTTP API для обратной связи:

   * принять идентификатор рекомендации;
   * принять состояние `applied` или `rejected`;
   * принять необязательный комментарий;
   * использовать существующие операции хранения жизненного цикла рекомендаций;
   * сделать повторный одинаковый запрос безопасным и идемпотентным;
   * возвращать актуальный сохранённый статус рекомендации.

3. Защитить endpoint от посторонней записи:

   * не публиковать незащищённый write API в интернет;
   * использовать минимальный механизм аутентификации, подходящий текущему локальному/Docker-развёртыванию;
   * не добавлять универсальных API-вызовов, shell-доступа, инструментов модели или каких-либо управляющих операций ZONT.

4. Связать HTML с API:

   * отправлять feedback без перезагрузки страницы либо через простую штатную форму;
   * после успешной записи сразу показывать сохранённый статус и комментарий;
   * при ошибке не изображать успешное сохранение и показывать понятное сообщение.

5. При генерации нового отчёта подмешивать сохранённое состояние рекомендаций из БД, чтобы статус не существовал только в состоянии браузера.

6. Сохранить текущий контракт последующего AI-анализа:

   * `applied` / `rejected` и комментарий владельца продолжают попадать в следующий AI-пакет;
   * отклонённая рекомендация не должна повторяться без существенно новых противоположных свидетельств;
   * этот этап не требует реализации расширенного structured experiment context из более поздних этапов.

7. Добавить сквозной Docker-тест сценария:

   `открыть отчёт → отметить рекомендацию → сохранить комментарий → получить подтверждение → повторно открыть/обновить отчёт → увидеть сохранённый статус → сформировать следующий AI-контекст → убедиться, что feedback в него вошёл`.

8. Обновить документацию рекомендуемого пользовательского сценария так, чтобы для обычной обратной связи CLI больше не требовался. CLI-команды жизненного цикла рекомендаций можно сохранить как административный/диагностический интерфейс.

### Критерии приёмки

* Для каждой рекомендации в HTML доступны «Выполнено», «Отклонить» и комментарий владельца.
* Сохранённый статус и комментарий видны после повторного открытия отчёта и не зависят от состояния браузера.
* Повторная отправка одинакового feedback не создаёт дубликатов или противоречивых записей.
* Некорректный или неизвестный идентификатор рекомендации корректно отклоняется.
* Неавторизованный клиент не может изменить feedback.
* Существующие CLI-команды `mark-applied` / `reject` продолжают работать и используют то же состояние.
* Последующий AI-пакет содержит сохранённую обратную связь владельца.
* Docker E2E покрывает полный пользовательский путь обратной связи.
* Существующие регрессионные тесты ГВС, надёжности и recommendation lifecycle остаются зелёными.
* Проходят `pytest`, `ruff check .`, `mypy src/zont_analyzer`, `python -m build`, сборка образа и проверка Compose.
* На изолированной копии реальной БД сценарий feedback проверен вручную перед обновлением рабочего экземпляра.
* После рабочего развёртывания обычная обратная связь владельца больше не требует CLI.

### Граница этапа

Этот этап закрывает именно минимальную обратную связь, необходимую для P2.

Он **не зависит** от реализации:

* расширенного AI-контракта гипотез/прогнозов;
* анализа PZA и контрфактуальных прогнозов;
* многокомнатного анализа и гидравлической балансировки;
* структурированного описания ручного эксперимента;
* автоматического сравнения окон до/после вмешательства;
* обучения на недельном/месячном поведении дома.

Эти возможности могут использовать тот же feedback lifecycle позднее, но не должны блокировать начало и завершение P2-пилота.


## Этап 2 — Слой свидетельств отопления для OpenAI

### Цель

Создать ограниченный надёжный пакет временных свидетельств, достаточно содержательный для рассуждений AI, но не превращающий Python в экспертную систему отопления.

### Работы

1. Выравнивать и суммировать доступные сигналы:
   - температура контрольной комнаты + историческое задание;
   - температуры дополнительных комнат;
   - наружная температура;
   - расчётное задание температуры подачи (`cs`);
   - фактическая температура подачи;
   - внешняя температура обратки и ΔT;
   - активность/модуляция горелки;
   - запрос/доступность/контекст отопления;
   - окна приоритета/влияния ГВС;
   - интервалы надёжности и устаревшей телеметрии.
2. Повторно использовать существующие исключения:
   - автоматическое лето/выключение;
   - переходы режима/задания;
   - окна приоритета ГВС;
   - известные пробелы телеметрии/надёжности.
3. Формировать ограниченные временные свидетельства: например, часовые интервалы и выбранные репрезентативные эпизоды отопления. Сохранять форму данных, не сводить всё к одному коэффициенту корреляции.
4. Присваивать окнам свидетельств стабильные идентификаторы и происхождение.
5. Детерминированно рассчитывать только воспроизводимые факты: средние значения и диапазоны, ошибку относительно задания, ΔT, задержки, покрытие, диапазон погоды и аналогичные базовые показатели.
6. Отслеживать качество отдельно для контрольной комнаты, погоды, подачи/обратки и дополнительных комнат.

### Критерии приёмки

- AI видит, как ошибка комнаты меняется вместе с погодой/поведением отопления, а не только агрегированные коэффициенты.
- Каждое число, видимое AI, имеет происхождение observed/derived.
- Загрязнённые окна явно помечаются/исключаются.
- Размер пакета ограничен для дневного/недельного/месячного анализа и соответствует ограничениям бюджета токенов.
- На этом этапе локальный код не объявляет наклон/смещение PZA или гидравлический дисбаланс.
- Тесты покрывают временное выравнивание, исключения, ΔT, области качества и стабильные идентификаторы свидетельств.

## Этап 3 — Контракт рассуждений AI: гипотезы, прогнозы и эксперименты

### Цель

Перевести OpenAI из роли комментатора локальных метрик в основной слой рассуждений.

### Работы

1. Расширить структурированный вывод за пределы `summary + recommendations` необязательными полями:
   - `observed_patterns`;
   - `hypotheses`;
   - `predictions`;
   - `unknowns`;
   - `recommended_experiment`.
2. Гипотезы должны поддерживать уверенность, свидетельства за/против и конкурирующие объяснения.
3. Прогнозы должны содержать сценарий, ожидаемое направление/эффект, уверенность, допущения, свидетельства и план проверки.
4. Сохранить существующий шаблон «строгая схема API → валидация домена».
5. Обновить `SYSTEM_PROMPT`, чтобы он:
   - рассуждал по временным свидетельствам, а не фиксированным порогам;
   - сравнивал конкурирующие объяснения;
   - различал observed / derived / inferred / predicted;
   - сохранял уже реализованные семантики ГВС и надёжности;
   - считал обратную связь владельца авторитетным ручным контекстом;
   - при неоднозначных свидетельствах предпочитал один минимально инвазивный следующий эксперимент;
   - никогда не выдумывал положения расходомеров, соответствие комнат/контуров или измеренный гидравлический расход.
6. Расширить проверку ссылок на свидетельства временными идентификаторами свидетельств.
7. Сохранить `store=False`, бюджет токенов и отсутствие доступа к инструментам или записи.

### Критерии приёмки

- Структурированный вывод может представить несколько конкурирующих гипотез, не вынуждая давать рекомендацию.
- `unknown` / недостаток свидетельств является успешным результатом.
- Прогнозы однозначно распознаются как прогнозы и никогда не являются измеренными фактами.
- Инциденты надёжности из-за питания/перезапуска не могут быть описаны как внутренние отказы котла.
- Недействительные ссылки на свидетельства приводят к ошибке валидации.
- Тесты с заглушками покрывают схему и валидацию; для этапа достаточно не более одного реального проверочного запроса к OpenAI.

## Этап 4 — Анализ PZA и контрфактуальный прогноз

### Цель

Отвечать на полезные вопросы о текущем поведении погодозависимой автоматики, не зашивая локальную экспертную систему PZA.

### Работы

1. Обнаруживать текущие доступные для чтения параметры PZA из конфигурации ZONT, если они доступны; никогда не угадывать имена полей.
2. Передавать сопоставимые окна отопления при разных погодных условиях, чтобы AI мог ранжировать гипотезы, например:
   - несоответствие общей кривой/смещения;
   - несоответствие наклона;
   - инерционность PID/тёплого пола;
   - солнечные/внутренние теплопритоки;
   - локальный дисбаланс вместо общей ошибки PZA;
   - недостаток данных/диапазона погоды.
3. Поддержать контрфактуальные вопросы вроде «что, вероятно, произойдёт после небольшого изменения PZA?». Допустимы качественные оценки; числовые оценки должны явно обозначаться как прогнозы.
4. `recommended_experiment` может предложить только одно безопасное ручное изменение PZA: одну переменную, небольшой шаг, период наблюдения, критерии успеха и условия отката/остановки.
5. Если свидетельств/диапазона погоды недостаточно, запрашивать дополнительные наблюдения, а не выдумывать точность.

### Критерии приёмки

- Постоянная ошибка комнаты при разной погоде автоматически не превращается в диагноз наклона.
- Зависимая от погоды ошибка может поднять гипотезу неверного наклона, сохраняя альтернативы.
- Перегрев днём без активности отопления может поднять внешние/солнечные теплопритоки выше гипотезы перегрева из-за PZA.
- Узкий диапазон погоды возвращает недостаток свидетельств.
- Отчёт может ответить на контрфактуальный вопрос о небольшом изменении с указанием допущений/уверенности.
- Пути автоматического изменения ZONT по-прежнему нет.

## Этап 5 — Многокомнатное рассуждение и гидравлическая балансировка

### Цель

После появления датчика в жилой комнате второго этажа и накопления достаточных реальных данных отопления отличать ошибки общего управления от локального дисбаланса комнаты/этажа.

### Работы

1. Сравнивать контрольную комнату и дополнительные жилые комнаты на сопоставимых окнах отопления.
2. Передавать AI ошибку относительно задания, поведение прогрева/остывания, погоду, подачу/обратку/ΔT и активность отопления.
3. Позволить AI ранжировать конкурирующие объяснения: распределение гидравлики, различия теплопотерь, солнечные/внутренние теплопритоки, смещение/расположение датчика и недостаток данных.
4. Предлагать эксперимент с расходомером/балансировкой только если комнату/этаж можно сопоставить с известной гидравлической ветвью/петлёй или владелец предоставил такое соответствие.
5. Неизвестное соответствие должно давать `needs_manual_context`.
6. Никогда не менять PZA и гидравлику в одном эксперименте.

### Критерии приёмки

- Нет второго датчика жилой комнаты → нет рекомендации по расходомеру.
- Локальный устойчивый дисбаланс можно отличить от общедомового дефицита.
- «Вероятный гидравлический дисбаланс» не означает, что фактический расход был измерен.
- Эксперимент балансировки изменяет на небольшой шаг одну известную ветвь/группу и ждёт тепловой реакции тёплого пола перед оценкой.
- Неизвестное соответствие петли никогда не превращается в угаданную инструкцию.

## Этап 6 — Обучение на вмешательствах и выпуск

### Цель

Использовать существующий цикл обратной связи, чтобы сделать последующее рассуждение специфичным для этого дома, и выпускать изменения только после регрессионных и оценочных тестов.

### Работы

1. Расширить применённую обратную связь необязательным структурированным контекстом эксперимента: категория/параметр, значение до/после, временная отметка и примечание владельца.
2. Формировать окна свидетельств до/после, насколько практически возможно нормализованные по погоде, режиму, влиянию ГВС и качеству данных.
3. Передавать последующему анализу AI предыдущий прогноз + наблюдаемый результат.
4. Позволить AI оценивать, подтверждает ли результат исходную гипотезу, противоречит ей или не позволяет её различить.
5. Добавить недельный/месячный контекст дома: тепловую инерцию, типичную реакцию на погоду, обычный ΔT и поведение комнат относительно друг друга.
6. Добавить сценарии оценки AI для:
   - постоянного смещения и зависящей от погоды ошибки;
   - дисбаланса одного этажа и общедомового дефицита;
   - солнечного притока/отсутствия активности отопления;
   - недостатка данных;
   - прерывания ГВС;
   - внутренней потери OT и потери питания/перезапуска;
   - успешных и неуспешных ручных экспериментов.
7. Сохранять отчёт компактным: текущий контекст датчиков, сводка ГВС/надёжности, важные паттерны AI, ранжированные гипотезы, полезный прогноз и один предпочтительный следующий эксперимент или «ничего не делать».

### Критерии приёмки

- Применённые эксперименты можно представить структурированно, а не только разобрать из свободного текста.
- Последующий AI явно сравнивает до/после и называет смешивающие факторы.
- Отклонённые рекомендации не повторяются без существенно новых противоположных свидетельств.
- Недельный/месячный вывод отражает устойчивое поведение этого дома, а не просто растягивает дневные метрики на больший период.
- Существующие регрессионные тесты ГВС и надёжности остаются зелёными.
- Ни один вывод/прогноз AI не отображается как измеренный факт.
- Проходят `pytest`, `ruff check .`, `mypy src/zont_analyzer`, `python -m build`, CI зелёный.
- Реальный `run --once` выполняется успешно, новый контекст датчиков корректно отображается.
- Перед слиянием в `main` хотя бы один реальный отчёт вручную признан более полезным, чем текущая базовая версия.

## Общий критерий закрытия функционального этапа

Зелёных локальных тестов недостаточно, чтобы закрыть этап. Для каждого этапа 1–6 требуется
следующая последовательность:

1. **Локальная и Docker-проверка.** Выполнить критерии приёмки этапа, синтетические и
   регрессионные тесты, `pytest`, `ruff check .`, `mypy src/zont_analyzer`, `python -m build`,
   сборку образа и проверку конфигурации Compose.
2. **Изолированная приёмка на рабочем сервере.** Создать штатной командой `db backup`
   проверенную онлайн-копию рабочей SQLite. Нельзя копировать живые SQLite/WAL-файлы напрямую.
   Статическую резервную копию разместить в уникальном непубличном временном каталоге с правами
   только для владельца процесса и предоставить контейнеру-кандидату как отдельную записываемую
   БД. Использовать отдельный проект Compose или одноразовый контейнер, рабочую конфигурацию и
   секреты только для чтения и отдельный временный каталог публикации. Не монтировать в кандидат
   рабочий `/opt/zont-analyzer/data` или `/var/www/html/za`.
3. **Проверка на реальных данных без воздействия на рабочий экземпляр.** Если этап зависит от
   текущего контракта ZONT, на временной БД разрешены `doctor --live`, `discover` и небольшая синхронизация:
   доступ к ZONT остаётся только для чтения. AI по умолчанию отключается через `--no-ai`; для
   этапа, явно проверяющего AI-контракт, допускается не более одного заранее контролируемого
   вызова. На временной БД сформировать как минимум подходящий `initial` или `daily` отчёт,
   экспортировать HTML и JSON во временный каталог и вручную проверить адекватность фактов,
   происхождения данных, формулировок, рекомендаций и отсутствие регрессий.
4. **Развёртывание в рабочую среду.** Перед обновлением ещё раз создать проверенную резервную
   копию рабочей БД и развернуть прошедший приёмку образ обычной процедурой. После обновления не
   записывать синтетические данные в рабочую БД и не подменять `latest.html` тестовым отчётом:
   достаточно проверить `healthcheck`, `status`, свежесть штатного `latest.html`, логи фонового
   процесса и неизменность соседних сервисов.
5. **Зафиксировать доказательства.** Записать commit/tag образа, результат проверок, путь к
   временному отчёту или сохранённый артефакт, итог ручного просмотра и результат рабочих
   проверок состояния в `status.md` либо в отдельную заметку выпуска.

Функциональный этап считается закрытым только после прохождения всей последовательности и всех
собственных критериев приёмки. Для предварительной проверки и изменений, не затрагивающих
работающую часть приложения, развёртывание можно отметить как неприменимое, но причину нужно
зафиксировать явно.

Синтетические сценарии не требуется повторять на живой рабочей БД. Их задача — проверять
детерминированную логику локально и в Docker; рабочий сервер нужен для проверки образа,
окружения и отчёта на изолированной копии реальных данных.

## Правила выполнения

- Предварительная проверка — только проверка контракта; не считать её повторной реализацией P0.
- Выполнять этапы по порядку, если только критерий приёмки явно не отменён с документированной причиной.
- Предпочитать небольшие коммиты, соответствующие этапам/подэтапам; избегать несвязанных рефакторингов.
- Детерминированный код подготавливает надёжные свидетельства и базовую математику. OpenAI выполняет многофакторное рассуждение, ранжирование гипотез и прогнозирование.
- Не заменять рассуждение AI большой коллекцией локальных экспертных порогов.
- Не отправлять в OpenAI длинную сырую телеметрию вслепую; сохранять динамику в ограниченных окнах свидетельств.
- Сохранять все уже реализованные семантики ГВС и надёжности в `fix/dhw-analysis-feedback`.
- Один ручной эксперимент меняет одну переменную. ZontAnalyzer сам изменение не выполняет.
