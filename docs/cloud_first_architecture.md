# ZontAnalyzer — целевая cloud-first / AI-first архитектура

Статус: архитектурный proposal и backlog ограниченных cloud-first работ<br>
Ветка: `architecture/cloud-first-serverless`<br>
База: `main`

Этот документ фиксирует архитектурное направление, сформулированное после работ по ГВС и надёжности. Основной product/analytics baseline уже находится в `main`; эта ветка не является вторым потоком разработки функциональности. Она используется для небольших совместимых исправлений, архитектурных экспериментов и подготовки возможной cloud-миграции.

## 1. Принцип продукта

ZontAnalyzer остаётся read-only помощником для одного реального дома. Главная ценность продукта не в инфраструктуре самой по себе, а в способности со временем понимать поведение конкретной системы отопления и помогать владельцу выбирать безопасные ручные эксперименты.

Поэтому проект разделяется на два слоя.

### Доверенный слой данных — детерминированный код

Отвечает за то, что должно быть воспроизводимым и проверяемым:

- read-only discovery/config/history/events из ZONT;
- каноническое хранение телеметрии;
- идентификацию датчиков, семантические роли, provenance и confidence;
- выравнивание временных шкал и проверки качества данных;
- сегментацию состояний отопления, ГВС и надёжности;
- исключаемые окна для устаревших данных, отключений, летнего/off-состояния, приоритета ГВС и переходов управления;
- простые проверяемые расчёты: средние, диапазоны, ошибка относительно уставки, duty cycle, ΔT, длительности, coverage и т.п.;
- компактные временные evidence-окна для reasoning;
- evidence ID и safety guards.

Этот слой не должен превращаться в большую локальную экспертную систему отопления из фиксированных порогов и `if/else` для каждого возможного диагноза.

### Слой reasoning — OpenAI

Отвечает за задачи, где многомерный анализ полезнее ручных эвристик:

- поиск и объяснение закономерностей между погодой, состоянием управления, реакцией помещений, подачей/обраткой и ГВС;
- сравнение конкурирующих инженерных гипотез;
- ранжирование вероятных причин с сохранением неопределённости;
- counterfactual/predictive анализ небольших ручных изменений;
- выбор следующего наиболее информативного эксперимента;
- использование структурированной истории предыдущих интервенций владельца;
- построение специфичной для этого дома картины поведения на горизонте недель и сезонов.

Вывод AI обязан различать четыре эпистемических уровня:

1. **observed** — непосредственно прочитано или измерено;
2. **derived** — детерминированная математика по observed-данным;
3. **inferred** — вывод или гипотеза модели;
4. **predicted** — прогноз или counterfactual-оценка.

Inference и prediction не становятся измеренным фактом только потому, что сохранены в отчёте.

## 2. Почему cloud-first

Для этого pet project нагрузка импульсная, а не постоянная: периодическая синхронизация, периодический анализ, редкие обращения к OpenAI и публикация отчётов. Поэтому постоянно работающий VPS/container — не единственная естественная модель развёртывания.

Целевая облачная архитектура должна сохранить сильные стороны текущего application layer (`run --once`, идемпотентный sync/catch-up, read-only API, сохраняемые cursors/reports) и перенести их на managed/serverless сервисы, не переписывая приложение в набор микросервисов.

Cloud-first здесь означает:

- managed/serverless сервисы — предпочтительная production-цель;
- локальный Docker + SQLite остаются полноценными режимами разработки и тестирования, где это удобно;
- инфраструктура описывается как код;
- приложение сохраняет переносимость: domain/analytics не знают о Yandex Cloud;
- облачная миграция выполняется постепенно и остаётся обратимой до cutover.

Это **не** означает разделение каждой операции на отдельную функцию или сервис.

## 3. Начальная целевая схема в Yandex Cloud

Предпочтительный базовый вариант:

```text
Timer Trigger
    |
    v
Serverless Container
`zont-analyzer run --once`
    |
    +--> ZONT read-only API
    +--> YDB Serverless
    +--> OpenAI API
    +--> Object Storage (публикуемые HTML/JSON-артефакты)
    +--> Lockbox (runtime-секреты)
    +--> Monium (метрики/логи/алерты)
```

Опциональные сервисы подключаются только при появлении реальной задачи:

- API Gateway — feedback/status/read endpoints;
- Postbox — email-сводки и уведомления;
- Workflows/EventRouter — orchestration, если единый `run --once` перестанет быть достаточным;
- Message Queue — асинхронная развязка только если retries/concurrency действительно этого потребуют;
- Yandex Query + Object Storage — в будущем для аналитического архива/data lake;
- Cloud Functions — для действительно маленьких изолированных handlers, но не как runtime по умолчанию для уже существующего packaged application.

Первая облачная версия должна оставаться одним развёртываемым приложением, а не становиться распределённой микросервисной системой.

## 4. Модель вычислений

Предпочтительная единица выполнения — вызов Serverless Container с идемпотентным one-shot use case.

```text
timer -> container -> run --once -> exit
```

Существующий долгоживущий `run` worker остаётся допустимым для локального/VPS-развёртывания, но cloud production не должен зависеть от постоянно живущего процесса.

Из этого следуют важные требования:

- всё долговечное состояние хранится вне контейнера;
- локальная файловая система используется только как scratch space;
- параллельные/перекрывающиеся вызовы возможны и должны быть безопасны;
- claim/idempotency задач должны сохраняться транзакционно;
- retries не должны дублировать отчёты, interventions или OpenAI-вызовы.

Не добавлять функцию, которая лишь вызывает контейнер. Scheduler должен обращаться к execution target напрямую.

## 5. Модель долговечного хранения

### YDB Serverless

Кандидат на основной cloud-state store для:

- devices/entities/config snapshots;
- telemetry series и samples;
- source/reliability events;
- sync cursors и job/idempotency state;
- reports и evidence metadata;
- recommendations/interventions/owner feedback;
- OpenAI usage ledger и call metadata.

YDB нельзя считать «SQLite с другим URL». Нужен отдельный storage adapter/repository implementation. SQL-, transaction- и index-предположения должны быть проверены явно.

SQLite сохраняется для:

- локальной разработки;
- быстрых unit/integration tests;
- offline single-machine режима;
- эталонного backend во время миграции.

Application/domain/analytics должны зависеть от repository contracts, а не от деталей YDB или SQLite.

### Object Storage

Используется для immutable/published артефактов, а не транзакционного состояния:

- целевой объект `latest.html`;
- датированные HTML/JSON exports;
- опциональные долгосрочные exports/Parquet в будущем;
- sanitized fixtures или migration exports, где это уместно.

Живую SQLite-базу нельзя запускать с Object Storage mount.

## 6. Конкурентность и расписание

Serverless execution делает инвариант «ровно один вечно работающий worker» неправильным. Вместо него используется атомарное владение задачей/idempotency.

Концептуально:

```text
job key = <тип задачи, период/ревизия входных данных, версия алгоритма>

атомарный claim
  -> уже завершено: no-op
  -> lease занят: no-op / retry позже
  -> claim получен: выполнить
```

Crash/timeout должен оставлять достаточно сохранённого состояния, чтобы следующий вызов мог безопасно продолжить работу.

Существующее поведение cursor/catch-up/idempotent-report нужно переиспользовать, а не заменять.

## 7. Секреты и IAM

Cloud runtime должен использовать service account/IAM permissions с минимально необходимыми правами для каждого ресурса.

Секреты — ZONT token/client identity, OpenAI API key и т.п. — в cloud execution должны переехать в managed secret store. Они никогда не должны попадать в image layers, Terraform state в открытом виде, report artifacts или logs.

Для developer mode сохраняется существующий путь через локальные secret-files/env.

## 8. Наблюдаемость

Cloud observability является частью архитектуры, а не последующей надстройкой.

Минимальный набор application metrics:

- время последнего успешного sync / sync lag;
- возраст последней telemetry;
- завершённые/ошибочные окна;
- длительность analysis;
- статус генерации отчёта;
- OpenAI calls/tokens/failures;
- уже вычисляемые приложением reliability-метрики ZONT/controller/boiler;
- ошибки/timeouts вызовов контейнера.

Здоровье инфраструктуры и факты уровня приложения должны оставаться разными понятиями. Успешный вызов контейнера не доказывает свежесть telemetry ZONT.

## 9. Публикация отчётов и feedback

Первая serverless-миграция должна сохранить текущую report-модель.

Рекомендуемое разделение:

- канонический report JSON/state — в YDB;
- отрендеренный standalone HTML/JSON export — в Object Storage;
- стабильный pointer/object для последнего отчёта.

Позже интерактивный feedback можно открыть через небольшой API Gateway + handler/container path, который меняет только состояние, принадлежащее ZontAnalyzer (`applied`, `rejected`, owner notes). Он никогда не должен превращаться в control plane для ZONT или котла.

## 10. AI packet в облачной архитектуре

Cloud migration не должна откатить AI-first направление продукта.

Пакет для OpenAI должен строиться из того же детерминированного evidence layer независимо от storage/runtime backend. Он должен содержать ограниченную по размеру временную структуру, а не слепо выгружать сырую минутную telemetry.

Желаемые входные данные для reasoning:

- активный управляющий комнатный датчик и target;
- дополнительные температуры помещений и влажность;
- наружная температура;
- расчётная и фактическая температура подачи;
- обратка и ΔT;
- heating activity/modulation/context;
- окна взаимодействия с ГВС;
- reliability/staleness context;
- предыдущие ручные interventions и их результаты;
- representative evidence windows, сохраняющие временную форму поведения.

Cloud backend — инфраструктурная деталь и не должен менять эпистемический контракт аналитика.

## 11. Правило работы ветки и GitHub Issues

Основная product/analytics разработка уже завершена в текущем baseline `main`. Cloud-ветка не должна заново открывать параллельный трек для датчиков, ПЗА или AI.

В этой ветке допустимы:

- небольшие cloud/runtime/storage/publisher/observability fixes;
- архитектурные spikes и проверка контрактов;
- обновление cloud-first документации;
- изолированные изменения, которые после проверки можно вернуть в `main`.

Текущий статус и рабочий прогресс cloud-first отслеживаются в [GitHub Issue #1](https://github.com/tupoybot/ZontAnalyzer/issues/1). Issue используется как живой tracker: там фиксируются активная веха, блокеры, ссылки на коммиты/PR и результаты проверок. Архитектурные решения и критерии приёмки остаются в versioned-документах этой ветки; их не следует дублировать в Issue целиком. Отдельные дочерние Issues создаются только для реально начатых вех.

После завершения ограниченной работы предпочтителен обычный PR/merge этой ветки в `main`. Если изменение изолировано и нужно перенести только его, допустим `git cherry-pick`. Регулярный rebase нужен только для обновления устаревшей базы, а не для поддержания двух постоянно развивающихся product-треков.

## 12. Философия миграции

Предпочтительный порядок:

1. доказать работоспособность cloud skeleton на текущем поведении приложения;
2. проверить YDB storage adapter на representative реальной нагрузке;
3. при необходимости временно сравнивать локальный/VPS и cloud пути;
4. сравнивать сохранённое состояние и отчёты;
5. выполнять cutover только после отдельного решения и понимания корректности, стоимости и эксплуатационных свойств;
6. сохранять возможность rollback, пока cloud path не переживёт обычную эксплуатацию и ошибки.

Цель — изучить платформу и упростить эксплуатацию, а не устроить big-bang rewrite.
