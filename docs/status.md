## Резюме

Рабочее приложение, использующее ZONT только для чтения, проверено по полному сценарию на одной
реальной установке BAXI Connect+: первичное обнаружение → возобновляемая синхронизация → локальный
анализ отопления и ГВС → атомарный ежедневный HTML/JSON → необязательная OpenAI-интерпретация.
Базовая версия до P1 сохранена отдельным Git-коммитом.

**Текущий продуктовый этап — P2, ближе к его завершению; P3 ещё не начат.** P0, вертикальный
срез P1 и обязательная обратная связь этапа 1.5 реализованы. Инженерная часть P2 работает на
реальной установке: фоновый процесс догоняет пропущенные дни, обновляет `latest.html`, пишет
контрольный сигнал, не повторяет AI-вызов при каждом опросе и принимает защищённый feedback
непосредственно из карточек HTML. Весь внешний `/za/` закрыт единым nginx Basic Auth; разрывы
наблюдаемости больше не считаются отказами без подтверждающих свидетельств.

Минимальная временная граница пилота достигнута: с 2026-08-03 по 2026-08-25 опубликованы
ежедневные отчёты без пропущенных дат, worker на 2026-08-26 healthy и продолжает публикацию.
Однако одного календарного срока недостаточно для формального закрытия P2: ещё требуется явная
оценка владельца, что несколько найденных эпизодов действительно полезны, и фиксация оставшихся
ложных тревог/непонятных формулировок. Поэтому честный статус — **активный P2 на выходе**, а не P3.

## Что реализовано

- Узкий адаптер ZONT со списком разрешённых методов только `devices` и `load_data`, рекурсивным удалением секретов и
  ограничением частоты запросов.
- SQLite/WAL, канонический UPSERT, снимки первичного обнаружения и конфигурации, отчёты,
  свидетельства, жизненный цикл рекомендаций, очередь исходящих сообщений, учёт использования,
  проверка целостности и онлайн-резервное копирование.
- Автоматический переход к поставляемой актуальной ревизии Alembic с проверенной резервной копией
  перед изменением ревизии БД.
- Качество данных, взвешенная по времени температура относительно исторической уставки, наружная
  температура, циклы горелки и безопасная атрибуция отклонений.
- Контекст отопительных режимов/расписаний и отдельное фактическое автоматическое летнее
  состояние контура.
- Взаимоисключающие OpenTherm-состояния `heating / dhw / concurrent-or-ambiguous / idle` без
  двойного засчёта одновременных флагов.
- Детерминированные эпизоды ГВС: историческая цель/режим, восстановление и перелёт, запрос и
  пауза отопления, возврат `ch`/`worktime` без пламени, горячий хвост и проверки качества.
- Команды начального, ежедневного, недельного, месячного и сезонного отчётов, безопасные средства
  вывода текста, JSON и автономного HTML,
  локальный жизненный цикл рекомендаций с обратной связью владельца в следующих AI-пакетах и автономный фоновый процесс
  с догоном/контрольным сигналом/атомарной публикацией.
- OpenAI Responses API через строгую схему, `store=False`, без инструментов и функций, с проверкой
  идентификаторов свидетельств, лимита и штатного ухудшения режима.
- Непривилегированный образ Docker и CI с проверками стиля, типов, тестов, импорта wheel-пакета
  и сборки Docker.

## ГВС: реализованный вертикальный срез

В реальной БД уже есть отдельный контур «ГВС»: температура БКН `dt`, `mode_id`, `target_temp`,
`setpoint_temp`, `status`, `worktime`, температура подачи `bt` и OpenTherm-флаги `ch/dhw/fl`.
Системные режимы задают разные политики отопления и ГВС; автоматическое летнее состояние
отопления не означает отключение ГВС.

Анализ использует эти ряды совместно: исторические режим и цель, температура, `status`/`worktime`,
взаимоисключающие состояния `ch/dhw`, температура подачи и комнатный дефицит. Для каждого
эпизода он показывает наблюдавшиеся факты, выводы из нескольких сигналов и недоказанную
гидравлическую гипотезу; отсутствие подтверждённого запроса отопления не становится тревогой.

Подробные ряды ГВС накоплены только с `2026-07-22`; зимнего набора пока нет. Текущие снимки
конфигурации нельзя ретроспективно применять ко всей истории, поэтому анализ обязан использовать
исторические `mode_id/target_temp` и явно маркировать неизвестный старый контекст.

## Главные незавершённые части

В порядке продуктового приоритета:

1. Подвести итог уже идущего P2-пилота: собрать явные оценки владельца
   «верно/ложно/непонятно» и подтвердить пользу нескольких конкретных эпизодов.
2. Исправить оставшиеся обнаруженные на пилоте пропуски данных, ложные тревоги и непонятные
   формулировки; после этого явно закрыть P2.
3. Исходная линия и настоящие нормализованные недельные/месячные/сезонные сравнения (P3).
4. Внешнее резервное копирование, межпроцессная аренда и набор оценки AI после подтверждения пользы.
5. Telegram, новые миграции и тест производительности хранилища — только по подтверждённой необходимости.

## Ограничения, которые нельзя скрывать

- Анализ сейчас выбирает один основной отопительный контур/комнатный датчик.
- Нет прямого ряда насоса, трёхходового клапана, расхода ГВС и подтверждённой обратки. Можно
  наблюдать задержку переключения, но не всегда доказать её гидравлическую причину.
- Команды длинных периодов уже существуют, но пока не выполняют обещанные сравнения периодов.
- Межпроцессной аренды пока нет; запускать следует ровно один контейнер фонового процесса.

## Инварианты безопасности

1. Не добавлять для оборудования изменяющие конечные точки ZONT, универсальные запросы или инструменты модели.
2. Не хранить и не печатать исходные учётные данные; первичное обнаружение всегда рекурсивно удаляет секреты.
3. Числа рассчитывает детерминированный код; AI только интерпретирует переданные идентификаторы свидетельств.
4. При плохом качестве данных разрешено советовать только восстановление наблюдаемости.
5. `mark-applied` фиксирует ручное действие владельца и никогда не обращается к ZONT.
6. Сохранять идемпотентный UPSERT и стабильные идентификаторы отчётов и свидетельств.
