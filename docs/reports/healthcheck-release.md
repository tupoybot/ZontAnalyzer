# Лёгкий healthcheck — 2026-09-13

`#for-human`

Docker раз в минуту вызывает `curl` к `/za/api/worker-health` внутри контейнера.
Работающий HTTP-сервер читает JSON heartbeat и возвращает 200 для свежего
допустимого состояния, 503 для ошибки/отсутствия/устаревания. Порог берётся
из текущей конфигурации: `max(sync_every_minutes * 180, 300)`, на HK 900 секунд.
Путь статуса также берётся из конфигурации. Инициализации приложения, импорта
аналитики, обращений к БД и обслуживания рекомендаций при опросе нет.

Проверка сохраняет обнаружение зависшего worker. Обычный `/health` по-прежнему
означает только доступность HTTP. Таймаут curl — 3 секунды, Docker — 5 секунд;
интервал 60 секунд, три неудачи, стартовый льготный период 45 секунд.
При другом порте/API-префиксе используется `ZONT_HEALTH_URL` в deployment `.env`.

## Проверки

- Тест endpoint с отключённым доступом к БД: свежий/устаревший/ошибочный статус,
  отсутствие и повреждение JSON, нестандартные путь и период синхронизации.
- До финального переключения на curl проверена изолированная копия исходной
  БД: 149 отчётов, 0 пересчётов, очередь пуста. Семантика публикации не меняется.
- AI-запросов: 0. Миграций и изменений расчётов нет.
- Для деплоя переиспользуется сегодняшний application-created online backup
  `/opt/zont-analyzer/data/backups/zont-analyzer-20260913T133453006828Z.sqlite3`,
  скачанный и проверенный локально при выпуске инкрементальной публикации.
  Повторных тяжёлых backup/integrity/analysis на HK нет.
- Отдельный Python-probe был проверен на HK и заменён HTTP-вариантом:
  даже без приложения запуск Python стоил 2,158 CPU-секунды на этом хосте.
  Это причина использования curl и уже запущенного HTTP-сервера.
