# Файлы отчётов в Object Storage

`#for-human`

Изменение относится к [задаче #63](https://github.com/tupoybot/ZontAnalyzer/issues/63).
Реализация подготовлена; перенос существующего облачного архива, изменение
настроек бакета и проверка развёрнутого приложения ещё не подтверждены.
Общий договор сайта описан в [М5](../cloud/cloud_first_m5.md).

## Адреса и чтение

В закрытом бакете, под настроенным префиксом публикации, используются ключи
`daily/YYYY-MM-DD.html`, `weekly/YYYY-MM-DD.html`, `monthly/YYYY-MM-DD.html`
и `seasonal/YYYY-MM-DD.html`; рядом с каждым HTML находится JSON с тем же именем.
Дата — начало периода в часовом поясе отчёта. `reports.json` содержит список
опубликованных отчётов, `latest.html` — последний дневной отчёт. Результат
первичного анализа `initial` сейчас не входит в календарный архив; задача
не добавляет его публикацию.

Небольшой `site-index.json` содержит подтверждённый список и указатель на последний
отчёт для браузера. API Gateway проверяет токен и читает этот индекс и файлы
из Object Storage напрямую. Контейнер приложения, YDB и AI при просмотре
готовых отчётов не вызываются. Внешний адрес `/reports.json` по-прежнему
возвращает браузерный индекс. Датированные ссылки, `latest.html` и префикс `/za/`
сохраняются. Старые ключи с контрольной суммой поддерживаются на время перехода.

## Запись и защита от запоздавшего обработчика

Канонический отчёт, пользовательские данные и очередь изменений остаются в YDB.
Один проход публикации выбирает не более восьми отчётов. Для каждого выбранного
файла приложение:

1. Читает текущие байты и ETag — идентификатор содержимого объекта.
2. Продлевает аренду задания в YDB, проверяя владельца, номер попытки и срок действия.
3. Условно записывает файл: `If-Match` проверяет прочитанный ETag, а
   `If-None-Match: *` разрешает создание только отсутствующего объекта.

Конфликт завершает проход с ошибкой. Подготовленный старый файл не записывается
повторно после чтения нового ETag: следующий проход заново получает исходные данные.
После файлов одной транзакцией YDB сохраняются их ETag, список и отметка
обработки очереди; транзакция снова проверяет аренду и предыдущую отметку.

Каждая выбранная запись получает новый случайный UUID, даже если текст отчёта
не изменился. В HTML это служебный комментарий; в JSON —
`context['_publication']['generation']`, добавленный только к сериализованной копии.
Канонический отчёт в YDB, его контекст и результат AI остаются прежними.
Маркер меняет байты и ETag: возврат к прежнему тексту не позволяет запоздавшему
обработчику принять его за ранее прочитанную версию.

`reports.json` также получает новую `generation`; его ETag сохраняется как
`manifest_etag`. Браузерный индекс обновляется после подтверждения в YDB:
сначала читается ETag индекса, затем подтверждённые сведения и список отчётов.
ETag списка должен совпасть с `manifest_etag`. Его `generation` переносится
в индекс, который записывается условно. При конфликте перечитываются и индекс,
и подтверждённые сведения. Пустая очередь также позволяет восстановить индекс.
При проверке готовности приложение сравнивает сохранённые ETag списка и
последнего отчёта с хранилищем, а не только проверяет наличие файлов.

Каждая отдельная запись атомарна: читатель получает целый файл. Общей транзакции
для HTML, JSON и индекса нет. На время обновления они могут относиться к разным
попыткам публикации. До подтверждения YDB браузерный индекс остаётся прежним,
хотя файлы по стабильным адресам уже могут обновиться. Календарные ссылки
сохраняют адреса, файлы не удаляются для замены; следующий успешный проход
устраняет частичное обновление. Это не гарантия единого снимка всех файлов.

## Перенос и очистка

Обычная публикация блокирует обновление старого архива с ключами-контрольными
суммами в том же бакете и префиксе: сначала нужен отдельный перенос. Инструмент
[`migrate_publication_storage.py`](../../tools/migrate_publication_storage.py)
копирует точные опубликованные байты HTML и JSON, обновляет ссылки в списке
и подтверждает новые указатели с проверкой аренды. Он не обращается к ZONT,
не вызывает AI и не переформировывает отчёты. Идентичные результаты прерванного
копирования используются при повторе; отличающиеся файлы вызывают отказ.

До очистки `--rollback --apply` восстанавливает исходные указатели и записи
публикации из приватного журнала. Откат разрешён только пока состояние точно
совпадает с результатом переноса и прежние объекты доступны с теми же байтами.
После нового обновления архива он откажется затирать более свежий результат.

Инструмент [`cleanup_publication_storage.py`](../../tools/cleanup_publication_storage.py)
готовит точный план удаления по полному перечню объектов, версий и отметок
удаления. Он сохраняет текущие стабильные файлы, в том числе старые календарные
пары вне текущего списка. Удалению подлежат только проверенные устаревшие объекты
прежнего формата и допустимые нетекущие версии или отметки удаления.
Перед применением повторно проверяются состояние публикации, перечень версий
и, при сохранении удаляемых байтов, резервные копии; изменившийся план отклоняется.
Версии стабильных файлов с идентификатором `null` сохраняются: при
приостановленном версионировании этот идентификатор может использоваться повторно.
Старый выпуск приложения должен закончить все запросы до начала очистки.
Удаления выполняются порциями с проверкой блокировки и журнала; после прерывания
нужен новый план по фактически оставшимся версиям.

По умолчанию подготовка сохраняет приватные копии всех удаляемых файлов и версий,
а применение повторно проверяет их байты. Если владелец принимает восстановление
текущего архива из канонических отчётов в YDB, план можно подготовить с
`--no-deleted-object-backup`. В этом режиме подготовка и применение не скачивают
тела удаляемых объектов и не сохраняют их прежние версии. Исторические байты после
удаления восстановить нельзя; файлы текущих отчётов при необходимости публикуются
заново из YDB. Проверка текущих HTML/JSON, полного перечня версий, точного плана,
аренды задания и допустимых ключей остаётся обязательной. Политика записывается
в план; при `--apply --plan` она не переопределяется отдельным флагом.
Приватные план и журнал точных удалений сохраняются в обоих режимах.

Обычная публикация может изменить файлы между подготовкой и применением плана;
тогда применение правильно откажется от устаревшего состояния. Для непрерывной
эксплуатационной процедуры вызывающая программа может удерживать одну обычную
аренду задания публикации на оба шага: передать её продление как `fence` в
`prepare_cleanup`, а саму тройку `(owner, attempt, fence)` — как `lease` в
`apply_cleanup`. Аренду получает, продлевает и освобождает вызывающая программа.
План по-прежнему сохраняется отдельно и проверяется перед применением; все
проверки состояния, версий и допустимых удалений остаются обязательными.
Отдельные команды CLI по-прежнему используют прежний порядок работы.

Оба инструмента по умолчанию только готовят проверку и приватные материалы;
изменения требуют явного `--apply`. Очистка дополнительно требует `--plan`.
Каталог `--artifacts` должен находиться вне репозитория: там находятся закрытый
перечень объектов, выбранные резервные байты и журнал для восстановления или повторного
запуска. Инструменты запускаются отдельно от приложения в Docker с приватной
конфигурацией нужного окружения. Перечни, планы и журналы не публикуются в Git.
Для локального Docker доступен `--iam-token-file` — файл краткоживущего IAM-токена,
смонтированный только для чтения и доступный только владельцу. Сам токен не
передаётся аргументом команды.

Для прекращения накопления версий задаётся приватный вход Terraform
`publication_versioning_enabled=false`. У существующего версионируемого бакета
это перевод в `Suspended`, а не удаление прежних версий; их очистка выполняется
отдельным проверенным планом. Перед применением нужен свежий Terraform plan
с правильным хранилищем состояния; действующие ограничения приложения и настройки журналов
сохраняются. Проверка кода и локальные тесты не подтверждают применение политики
или очистку живого хранилища.

Временное отключение журналирования задаёт приватный параметр
`cloud_logging_enabled=false`: он действует на приложение, диагностический
контейнер и шлюз, сохраняя группу и прежние журналы. Чтение самой группы
Terraform всё ещё зависит от доступности Cloud Logging. Ошибка этого API
не означает, что готовый сайт или Object Storage недоступны.

## Проверки

Локальные проверки покрывают устаревшую аренду, конфликт ETag, возврат к прежним
байтам, частичные записи и восстановление индекса. На изолированной копии
скачанного архива с настоящей локальной YDB проверены прерывание переноса,
продолжение, побайтовое сравнение, откат, повторный перенос и отдельная очистка.
Контрольные суммы локальных исходных записей сохранились. Во время этой проверки
обращений к рабочей базе, ZONT или AI не было.

Условия записи описаны в [API загрузки объекта](https://yandex.cloud/ru/docs/storage/s3/api-ref/object/upload).
[API копирования](https://yandex.cloud/ru/docs/storage/s3/api-ref/object/copy)
проверяет условия источника, поэтому инструмент читает байты и выполняет условную
загрузку назначения. Поведение приостановки описано в
[правилах версионирования](https://yandex.cloud/ru/docs/storage/concepts/versioning).
