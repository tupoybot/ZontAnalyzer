# M1: облачный каркас

Статус: реализация и техническая проверка продолжаются. Этап ещё не принят.
Критерии: [дорожная карта M1](./cloud_first_milestone.md#m1--terraformiac-скелет-и-пустой-cloud-runtime).

## Что работает

В отдельном каталоге разрешённого облака созданы хранилище состояния Terraform,
служебные учётные записи, registry, Lockbox, изолированная YDB и приватный bucket
публикации. Инфраструктурный контейнер запускает небольшой HTTP-сервис вместе
с Xray. Он проверяет исходящий HTTPS через proxy, получение служебного токена,
чтение тестового объекта и запись метрики. Приложение и его данные пока не перенесены.

API Gateway передаёт заголовок авторизации контейнеру. Тестовый API и объект
требуют Basic Auth; прямой анонимный доступ к контейнеру и bucket закрыт.
Сертификат выпущен и подключён к gateway. На собственном тестовом домене
проверен HTTPS: API и приватный объект отвечают 401 без пароля и 200 с ним.

Исходный код и образы не содержат конфигурацию Xray и пароль веб-доступа.
Контейнер получает их из конкретной версии Lockbox по ключам `xray_config`
и `web_credentials`; OTLP-доступ — по ключу `grafana_otlp_config`.
Локальные секреты, состояния, планы и журналы находятся
в приватном каталоге, исключённом из Git и контекста сборки приложения.

## Разделение приложения и инфраструктуры

Принятый образ приложения выбирается по digest — неизменяемой контрольной сумме.
Он копируется из GHCR в облачный registry с сохранением digest. М1 запускает
отдельный проверочный образ; совпадение digest приложения при копировании
не доказывает работоспособность самого приложения в облаке.

Ошибки инфраструктуры исправляются в инфраструктурной ветке. Изменения кода
совместимости проходят отдельный PR приложения в `main`. После принятия выпускается
новый образ, который выбирает облачный deployment. Merge, выпуск образа и обновление
production — разные операции. Успех облачного теста не обновляет текущий production
автоматически. До переключения M8 действующий production остаётся единственным
исполнителем расписания и записи пользовательских данных.

## Код и приватные входные данные

- [Первичная инфраструктура](../infra/bootstrap/) создаёт каталог, защищённый
  backend состояния, IAM и федерацию GitHub OIDC. Bootstrap выполняется отдельной
  учётной записью; дальнейшее развёртывание использует ограниченную deployment identity.
- [Облачные ресурсы](../infra/cloud/) используют явные `cloud_id`, `folder_id`
  и окружение `dev` либо `pilot`. Принадлежность каталога облаку проверяется Terraform.
- [Сценарий развёртывания](../infra/deploy.sh) принимает `plan|apply`,
  а для первого запуска — `plan-foundation|apply-foundation`, и путь
  к приватному каталогу. Перед доступом к backend проверяются разрешённые облако,
  каталог, служебные учётные записи, bucket состояния и пространство имён окружения.
  Перед apply повторно проверяются переменные сохранённого плана.
  Порядок первоначальной установки описан в [инструкции](../infra/README.md).
- Приватный каталог содержит `scope.json`, `cloud.tfbackend.json`, `state.env`,
  `deploy-token` и `cloud-work/inputs.tfvars.json`. Эти файлы не являются
  публичными примерами конфигурации. Полные планы, outputs и логи остаются там же.
- [Пример backend](../infra/backend.example.hcl) использует S3 lockfile.
  Шифрование SSE-KMS задаётся политикой bucket; версия объекта позволяет восстановить
  предыдущий снимок. Принудительное снятие блокировки допустимо только после
  подтверждения остановки её владельца.

## Расписание и ограничения

`enable_timer=false` является безопасным исходным состоянием. Таймер включается
только после успешного ручного вызова `/smoke`. Обычное расписание — раз в час;
минутный вариант `timer_schedule` предназначен для короткой проверки и затем
отключается. При ошибке разрешён один повтор через 10 секунд.

Чтобы остановить новые запуски, задать `enable_timer=false` в приватной конфигурации,
выполнить plan, проверить удаление только тестового таймера и применить план.
Уже начатый вызов может закончиться после отключения.

У контейнера 256 МБ памяти, один запрос одновременно на экземпляр и timeout 30 секунд.
После Terraform [дополнительный шаг API](../infra/scripts/bound_revision.py) задаёт
не более одного экземпляра и одного запроса на зону. В закреплённом провайдере
эти настройки отсутствуют. Шаг сохраняет образ, секреты, mounts и прочие параметры,
проверяет результат и обновляет состояние Terraform. Повторный deploy не создаёт
новую ревизию, если лимиты уже применены. При прерывании ожидания сохраняется
идентификатор операции; следующий запуск сначала проверяет её завершение.
Эти ограничения не являются пределом расходов.
YDB ограничена по нагрузке и объёму, buckets — по объёму, логи хранятся семь дней.
Владелец подтвердил настройку бюджета и уведомлений о расходах для выбранного
каталога. Это подтверждение владельца, а не независимая проверка платёжного аккаунта;
deployment identity не получает доступ к общему billing.

Основной мониторинг работает в Grafana: runtime отправляет результат проверки
и её длительность через OTLP. Созданы папка, панель и включённое правило.
Обычное расписание — раз в час. Правило обнаруживает последний отказ или отсутствие
данных более двух часов; условие должно сохраняться пять минут. При намеренном
выключении таймера правило приостанавливают отдельно.
[Шаблоны панели и правила](../infra/grafana/) не содержат настроек стека.
Адрес стека, получатель email и доступ хранятся приватно.

Владелец подтвердил получение тестового письма. Контролируемый отказ реального
probe дал метрику 0 и состояние `firing`, восстановление — метрику 1 и `inactive`.
API канала подтвердил отправку без ошибки. Для короткой проверки выдержка временно
составляла 0 секунд; после неё восстановлены штатные пять минут.

Дублирующий dashboard Яндекса удалён, отправка custom-метрики остановлена.
У deployment-аккаунта и двух runtime-аккаунтов отозван `monitoring.editor`;
отсутствие этих привязок подтверждено API. Диагностические логи runtime
и уведомления о расходах сохранены. Исторические точки API-метрики удаляются
[после 30 дней без новых значений](https://yandex.cloud/en/docs/monitoring/concepts/ttl).

## Проверено

- В Docker проходят 20 тестов HTTP-проверки и экспорта OTLP, Ruff и mypy; 17 тестов сценариев
  проверяют границы deployment, сохранение параметров ревизии, исключение
  credentials из архива, допустимые адреса для передачи токена и настройку
  только принадлежащих проекту объектов Grafana.
- Общая регрессия приложения: 668 тестов, Ruff, mypy, wheel/sdist в Docker.
- Terraform validate и восемь тестов с подставным провайдером проходят.
- Локальный Xray устанавливает разрешённое TLS-соединение. Остановка proxy
  приводит к отказу без прямого обходного соединения.
- Реальный облачный `/smoke` возвращает HTTP 200. Успешный вызов по таймеру
  оставил в журнале подтверждения egress, identity, storage и metric.
- Через gateway API и объект отвечают 401 без пароля и 200 с ним;
  прямые анонимные запросы к контейнеру и bucket — 403.
- Два клиента не могут одновременно менять тестовое состояние Terraform.
  Аварийная остановка сохраняет блокировку; после проверки остановки клиента
  блокировка снимается. Восстановление предыдущей версии проверено на отдельном
  тестовом объекте состояния. Фактическое шифрование и версионирование подтверждены.
- Копирование принятого приложения в облачный registry сохранило исходный digest.
- Ревизия с лимитами прошла smoke. Повторный deploy сохранил её идентификатор,
  Terraform не запланировал изменений ресурсов.
- Архив доказательств сохранён в приватный bucket; KMS-шифрование и версия
  загруженного объекта подтверждены ответом сервиса.
- Отдельное окружение развёрнуто с пустого состояния через первоначальное создание
  registry/Lockbox и полный apply. Использованы отдельные учётные записи, секреты,
  bucket и registry. HTTPS gateway, приватный объект и экспорт метрики проверены;
  пароль рабочего окружения отклонён. После сохранения доказательств проверочный
  стенд удалён, его состояние не содержит управляемых ресурсов. Рабочее окружение
  повторно прошло smoke. Общая первичная инфраструктура и её backend сохранены.

## GitHub Actions

Application release публикуется только из `main`; workflow не обновляет production.
Облачный workflow при обычном push в разрешённую инфраструктурную ветку выполняет
план. Apply включается явно: параметром ручного запуска или префиксом сообщения
коммита `[m1-apply] ` для проверки до публикации workflow в default branch.
GitHub Environment `cloud-dev` должен
разрешать только эти ветки и содержать секреты, перечисленные в workflow.
Реальный запуск через `cloud-dev` подтвердил получение IAM-токена через OIDC,
копирование принятого digest, доступ к состоянию и Terraform plan без изменений
ресурсов. [Успешный запуск](https://github.com/tupoybot/ZontAnalyzer/actions/runs/35020074356).
Зашифрованный архив плана проверен отдельно: облако и каталог совпадают с
разрешённой областью. Ручной workflow apply пока не проверен.

Federated credential использует неизменяемый GitHub subject с ID владельца
и репозитория и точным именем Environment. Это соответствует
[формату GitHub OIDC](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims)
для новых репозиториев. Сам JWT передаётся без завершающего перевода строки;
проверка claims выводит только совпадение с ожидаемыми значениями.

Полные планы, outputs и журналы не публикуются в GitHub artifacts. Сценарий
[архивирования](../infra/scripts/archive_evidence.py) отправляет фиксированный
перечень доказательств в зашифрованный versioned bucket состояния. Файлы токенов,
ключей доступа и содержимое Lockbox в архив не входят. Временные credentials
удаляются с runner в конце выполнения.

## Что остаётся до готовности

1. Ограничить ветки GitHub Environment и проверить явный workflow apply.
   OIDC и реальный план уже проверены.
2. Выполнить итоговую проверку diff и приватности, опубликовать изменения и передать
   этап владельцу. Merge выполняется только после явного принятия.
