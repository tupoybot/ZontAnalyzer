# M2 — облачный запуск и внешние API

Статус: реализация и локальная проверка; облачная проверка ещё не завершена.
Задача: [sub-issue #11](https://github.com/tupoybot/ZontAnalyzer/issues/11).
Критерии: [план M2](./cloud_first_milestone.md#m2--облачный-запуск-и-внешние-api).

## Что запускается

Новый образ запускает HTTP-сервис и Xray. Сервис слушает порт из `PORT`;
он не открывает SQLite, не запускает старый worker и не создаёт отчёты в рабочем
архиве. Расчёт принимает небольшой набор температур и вызывает существующие
функции оценки качества, метрик и событий. Это проверка запуска приложения;
постоянное хранение и полный отчёт остаются задачами М3–М4.

| Вызов | Результат |
| --- | --- |
| `GET /ready` | Готовность процесса и локального Xray, без внешнего API |
| `GET /diagnostics` | Commit, идентификатор запущенного процесса, счётчики результатов заданий |
| `POST /jobs/analytics` | Проверка качества, метрики и события по переданным температурам |
| `POST /jobs/integrations` | Одна явно выбранная проверка соединения |

Все маршруты требуют Basic Auth. Прямой анонимный вызов контейнера запрещает
облачная проверка прав; HTTPS gateway передаёт авторизацию приложению.
Инфраструктурная проверка М1 продолжает контролировать Xray, приватный объект
и отправку метрик раз в час. У приложения отдельный контейнер без таймера.

## Ограничения задания

- Запрос JSON — до 64 КиБ; приём заголовков и тела ограничен общим временем.
- Аналитика принимает до 1000 упорядоченных измерений за период до 24 часов.
  Числа должны быть конечными, время — с часовым поясом, без дубликатов.
- Одновременно в экземпляре выполняется одно задание; пересечение возвращает 409.
  Задание выполняется отдельным процессом. По истечении установленного времени
  процесс завершается, клиент получает 504. Штатный предел — 15 секунд;
  платформа ограничивает весь вызов 30 секундами.
- Некорректные данные возвращают 400; сбой внешней зависимости — 502;
  неготовый Xray — 503. В ответах и журналах есть идентификатор задания,
  но нет тел запросов, токенов и сообщений внешних исключений.
- Повторный завершённый запрос выполняет расчёт заново. Результат расчёта
  воспроизводим; идентификатор задания новый. Постоянного журнала заданий пока нет.
- Временный диск нужен только для конфигурации Xray. Потеря временных файлов
  не означает потерю сохранённых результатов: постоянное хранение в М2 не используется.

После задания отправляются метрики результата и длительности в Grafana.
Экспорт ограничен отдельным коротким сроком и не подменяет результат расчёта.
Счётчики в диагностике относятся только к текущему процессу.

## Проверка внешних соединений

Тело `/jobs/integrations` содержит единственный параметр `service`:

- `zont`: один read-only `devices` с `load_io=false` напрямую к ZONT;
- `openai_tls`: проверка CONNECT и сертификата OpenAI без HTTP-запроса к API;
- `openai`: один запрос метаданных выбранной модели, без генерации и повторов.

OpenAI всегда идёт через локальный Xray. Переменные окружения proxy не меняют
маршрут; перенаправления не выполняются. При отказе proxy прямого обхода нет.
Модель выбирается из конфигурации принятого приложения. До авторизованной проверки
требуется частный параметр `openai_access_confirmed`, отражающий
[решение владельца в M0](./cloud_first_m0.md#что-подтверждено-по-доступу-к-openai).
Проверка метаданных использует [официальный endpoint](https://developers.openai.com/api/reference/resources/models/methods/retrieve).

Обычный deployment выполняет только готовность и синтетическую аналитику.
Он не вызывает ZONT или OpenAI. Реальные проверки запускаются отдельно;
лимит одного реального OpenAI-запроса на пользовательскую итерацию сохраняется.

## Образ и развёртывание

Ветка `stageM2/cloud-runtime` создана от принятого `main` после слияния М1.
Workflow выпуска проверяет исходники в Docker, собирает облачный образ,
проверяет его HTTP-запуск и сохраняет связь commit, digest и CI.
Кандидаты публикуются только из `main` и веток этапов, не из PR-событий.

Облачный workflow дополнительно использует защищённый Environment `cloud-dev`.
В нём разрешаются конкретные принятые к работе ветки: `main` и текущая ветка
этапа. Устаревшие разрешения удаляются. Наличие разрешения в workflow не заменяет
ограничение Environment. Настройки и секреты передаются через прежние имена
`M1_*`; это имена закрытых параметров, общих для облачной инфраструктуры.

Deployment проверяет commit образа, успешный workflow его выпуска и отсутствие
изменений приложения относительно кандидата. Копирование в Yandex Container
Registry сохраняет digest. `infra/deploy.sh` применяет конфигурацию, задаёт
лимиты обоим контейнерам и выполняет короткие проверки. У приложения нет
подключённого каталога публикации и доступа к production-БД.

Старый production закреплён в `old-stable` от проверенного работающего commit
и существующего тега выпуска. `deploy/check-legacy-image.sh` запрещает cloud-образ
и проверяет принадлежность его commit ветке `old-stable` до backup и изменения
конфигурации. Защита ветки и тега через настройки GitHub проверяется отдельно.
Резервная копия конфигурации старого выпуска хранится приватно.

## Как проверить

```sh
deploy/check-local.sh all
docker build --target production -t zont-analyzer:cloud-check .
deploy/smoke-cloud-local.sh zont-analyzer:cloud-check
```

Последний сценарий не использует сеть, реальные API или production-данные.
Он запускает именно собранный образ, проверяет Basic Auth, готовность, повторные
задания, ошибку входных данных и отсутствие импорта SQLite/SQLAlchemy.

До передачи на приёмку остаются облачный smoke, отдельные проверки API,
подтверждение CI deployment и ограничений Environment, защита старого выпуска,
инвентаризация и очистка временных ресурсов через API. М2 не принят и не слит.
